# ADR 0039: CI を速くする

ステータス: 採択

## 文脈

push のたびに CI を待つ時間が長い。
main への push の最近の実行（run 38316473868、2026-10-12）は、ワークフロー全体で 8 分半かかった。
内訳は次のとおりである。

| ジョブ | 段 | 時間 |
|---|---|---:|
| haskell | GHC と cabal の導入（haskell-actions/setup） | 105 秒 |
| haskell | 依存の解決とキャッシュの復元 | 5 秒 |
| haskell | ビルド（`cabal build all`） | 88 秒 |
| haskell | テスト（`cabal test all`） | 233 秒 |
| haskell | 文法の整形と lint、`cabal check` | 2 秒 |
| haskell | Haddock | 31 秒 |
| haskell | ソースのアーカイブからのビルド | 37 秒 |
| haskell | 合計 | 507 秒 |
| editors | Node のテスト | 9 秒 |
| adr | adr-guard | 5 秒 |

haskell のジョブがほぼすべてを占める。
その中で大きいのは、テスト、GHC の導入、ビルドの三つである。

テストの段の 233 秒は、テストスイートの合計ではない。
cabal はテストスイートを並列に動かしており、時間を決めているのは最も長い peg-grammar-test（198 秒）である。
ほかのスイートは長くても 61 秒（Lua の適合性）で、その裏で終わっている。

peg-grammar-test の中のテストは、一つずつ順に動いている。
テストの実行ファイルを `-threaded` でコンパイルしていないためである。
手元（10 コア）で `-threaded` を付け、tasty に `-j4` を渡して計ったところ、スイートの時間は 72 秒から 69 秒にしか縮まなかった。
二つのテストが時間の大半を占めているからである。

| テスト | 時間（手元、並列） |
|---|---:|
| 記法の文法が、ラベルを外した文法と同じ言語を受理する（リポジトリの文法の変異） | 71 秒 |
| 変異のすべてで、回復した構文木がテキストと一致する | 46 秒 |
| 警告のない無作為な文法が、ラベルを外した文法と同じ言語を受理する | 20 秒 |
| 空白と改行が整形の結果を変えない | 15 秒 |

上の二つは、リポジトリのすべての文法ファイルの変異を一つのテストの中で順に調べている。
並列にしても、スイートはこの一つのテストより先には終わらない。

GHC の導入の 105 秒は、毎回 ghcup で GHC 9.10.3 を入れ直している時間である。
cabal のストア（依存のパッケージ）はキャッシュしているが、GHC そのものはキャッシュしていない。
ビルドの 88 秒の大半は、このリポジトリのパッケージ、適合性テスト、生成した大きなモジュールのコンパイルである。
`dist-newstyle` をキャッシュしていないので、変えていないモジュールも毎回コンパイルし直している。

ADR だけを足すコミットや、README だけを直すコミットでも、haskell のジョブが全体を動かしている。
テストは `docs/` と `*.md` のファイルを読まないので、これらだけの変更では結果が変わらない。

## 実装すること

### テストを並列に動かす

- すべてのテストスイートを `-threaded -rtsopts "-with-rtsopts=-N"` でコンパイルする。tasty は、threaded の実行時システムでは、指定がなければコアの数だけテストを並列に動かす（threaded でなければ一つずつ動かす）
- 時間の長い二つのテストを、文法ファイルごとのテストに分ける。記法の文法とラベルを外した文法の受理の一致、回復した構文木の検査の二つである。調べる変異の集合は変えない
- テストが並列に動いても互いに干渉しないことを確かめる。peg-cli のテストは、テストごとに別のディレクトリと別のキャッシュを使っている（[ADR 0036](0036-parse-command.md) のテストのために分けた）。ほかのテストは、ファイルを読むだけか、golden のファイルをテストごとに一つ持つ

### GHC の導入をキャッシュする

- ghcup が GHC と cabal を置くディレクトリ（`~/.ghcup`）を actions/cache で保存し、次の実行で復元する。鍵は、ランナーの OS、GHC の版、cabal の版とする
- 復元した後も haskell-actions/setup を呼ぶ。導入済みの版を見つければ、入れ直さずに PATH を整えるだけで終わる

### ビルドの成果物をキャッシュする

- `dist-newstyle` を actions/cache で保存する。鍵は、ランナーの OS、GHC の版、`cabal.project` とすべての `.cabal` と `.hs` と `.peg` の内容のハッシュとする
- 鍵が一致しない場合は、同じ OS と GHC の版の最新のキャッシュを `restore-keys` で復元する。cabal は変わったモジュールとそれに依存するモジュールだけをコンパイルし直す
- 依存の解決の結果（`dist-newstyle/cache/plan.json`）も同じキャッシュに入るので、依存のストアのキャッシュの鍵の計算は今のままでよい

### Haddock とソースのアーカイブを別のジョブにする

- Haddock の生成と、ソースのアーカイブからのビルドを、`package` という別のジョブに移す。haskell のジョブと並列に動く
- `package` のジョブも、GHC の導入と依存のストアのキャッシュを使う。ソースのアーカイブからのビルドは別のディレクトリで行うので、`dist-newstyle` のキャッシュは使わない

### 文書だけの変更では Haskell と Node のジョブを動かさない

- ワークフローを二つに分ける。adr のジョブは、これまでどおりすべての push と pull request で動く。haskell、package、editors のジョブは、`paths-ignore` に `docs/**` と `**.md` を書いたワークフローに置く
- `docs/syntax.md` や README を変えても、コードとテストの結果は変わらない。テストはどのジョブも `docs/` と `*.md` を読まない

### 古い実行を止める

- pull request のブランチに続けて push したときは、同じブランチの実行中の CI を止める（`concurrency` の `cancel-in-progress`）。main への push は止めない。main の実行は、どのコミットでも結果を残したいためである

### 文書

- CONTRIBUTING（日本語と英語）の CI の説明に、文書だけの変更では Haskell と Node のジョブが動かないことを書く

## 実装しないこと

- テストの件数や変異の数を減らすこと。今のテストの網羅を保つ
- 変えたパッケージに応じてテストを選ぶこと。依存の関係を CI で管理する手間が、見込める短縮に見合わない
- より大きなランナーや自前のランナー。費用と保守の手間がかかる
- GHC を入れたコンテナのイメージでジョブを動かすこと。イメージの版を ghcup の推奨版（[ADR 0013](0013-roadmap-toolchain-memo.md)）にそろえて保守する手間が、キャッシュより大きい

## テスト設計

CI の設定の変更なので、自動テストは書けない。
実装の後に、実際に動かして確かめる。

- **並列のテストの安定**：手元で、すべてのテストスイートを `-N` で 3 回続けて動かし、すべて通ること。peg-grammar-test は tasty の `-j1` と既定の並列の両方で通ること
- **テストを分けた後の網羅**：分けた後のテストが調べる文法ファイルと変異の数が、分ける前と同じであること（テストの名前の一覧と件数で確かめる）
- **キャッシュのない実行**：キャッシュを消した状態の最初の実行が成功し、時間がこれまでと同程度であること
- **キャッシュのある実行**：二回目の実行で、GHC の導入が 30 秒以内に終わり、ビルドの段がキャッシュのない場合より短いこと
- **テストの段の時間**：テストの段が、これまでの 233 秒から縮むこと。peg-grammar-test が最も長いスイートでなくなるか、最も長いままでも 100 秒以内に終わること
- **文書だけの変更**：`docs/adr/` だけを変えた pull request で、adr のジョブだけが動くこと。`.hs` を一つ変えた pull request で、すべてのジョブが動くこと
- **古い実行を止める**：pull request のブランチに二回続けて push し、一回目の実行が止まること
- **記録**：実装の前（この ADR の文脈の表）と後の、キャッシュのない実行とある実行の段ごとの時間を、`docs/benchmarks/` に CI の時間のスナップショットとして置く

## トレードオフ

- キャッシュが増えるので、GitHub のキャッシュの容量（リポジトリあたり 10 GB）を使う。GHC の導入（手元の GHC 9.10.3 で約 2 GB）、依存のストア、`dist-newstyle` を合わせて数 GB になる見込みである。容量を超えると古いキャッシュから消え、その実行はキャッシュのない時間に戻る
- `dist-newstyle` の差分のビルドは、cabal の再コンパイルの判定に頼る。判定の誤りで古い成果物が残ると、手元では起きない失敗が CI でだけ起きうる。キャッシュの鍵に GHC の版を含め、疑わしいときはキャッシュを消して確かめる
- テストを並列に動かすと、テストの出力の順序が実行のたびに変わる。失敗したテストの名前と内容は tasty がまとめて出すので、読みにくさは小さいと見込む
- 文書だけの変更で Haskell のジョブを飛ばすので、文書に書いたコード例の誤りは CI で見つからない。今もコード例はテストしていないので、検出できる範囲は変わらない
- ジョブを分けると、ジョブごとに GHC の導入とキャッシュの復元の時間がかかる。キャッシュがあれば短いが、合計の計算時間は増える。待つ時間を減らすことを優先する
