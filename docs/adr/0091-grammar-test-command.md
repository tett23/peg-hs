# ADR 0091: 文法を入力の例で試すコマンド（peg-hs test）

ステータス: 採択（未実装）

## 文脈

文法を直したとき、前に受理していた入力をまだ受理するかは、いまは文法の作者が自分で確かめるしかない。
`peg-hs parse`（[ADR 0036](0036-parse-command.md)）は、一つの入力の AST か CST を表示する。
表示を目で見るか、作者が Haskell のテストを書いて、生成したモジュールを呼ぶことになる。
入力が十を超えると、目で見る方法は続かない。

このリポジトリの適合性テストは、入力と期待をファイルで並べる形を、すでに二つ取り込んでいる。
JSONTestSuite（`conformance/data/JSONTestSuite/test_parsing/`）は、受理すべき入力に `y_`、拒否すべき入力に `n_`、どちらでもよい入力に `i_` をファイル名の頭に付ける。
toml-test（`conformance/data/toml-test/`）は、`valid/` と `invalid/` のディレクトリで期待を分け、受理する入力 `X.toml` の隣に期待する値 `X.json` を置く。
JSON の文法の誤りの文言は、`conformance/json/errors.golden` に `ファイル名: 1:5: expected ...` の形で一行ずつ並んでいる。
期待をファイル名とディレクトリで表し、入力をそのままのバイト列で置く点が共通している。
入力をほかの形式の中に埋め込まないので、どんな入力でもエスケープせずに置ける。

エディタの tree-sitter の文法（`editors/tree-sitter-hpeg/`）は、tree-sitter の corpus の形式でテストしている。
`test/corpus/notation.txt` は、`=` の行で挟んだ見出し、入力、`-` の行、期待する構文木（S 式）を一つのファイルに続けて書く。
`tree-sitter test --update` は、期待する構文木を現在のパーサーの出力で書き換える（tree-sitter-cli 0.27.0 の `tree-sitter test --help` で確かめた）。
期待する木を手で書かずに、出力を確かめて受け入れる流れは取り入れたい。
一方で、入力を区切りの行の間に置くので、区切りに見える行を含む入力の扱いを決める必要がある。

[ADR 0090](0090-grammar-interpreter-without-ghc.md) は、GHC を使わずに文法を解釈するインタプリタを加える。
インタプリタは、受理か拒否か、拒否した位置と期待した字句の集合、ロスレスな構文木（CST、[ADR 0019](0019-lossless-syntax-tree.md)）を返す。
Haskell のアクションは評価できないので、AST は返さない。
入力の例を試すのに要るのは、受理か拒否か、拒否の位置と期待、CST の三つであり、どれもインタプリタが返す。
`peg-hs parse` と違い、GHC のコンパイルを待たずに済む。

例を試す道具は、ラベルの挿入の確認にも使える。
`peg-hs label` が挿入するラベルは、受理する言語を変えない（[ADR 0054](0054-automatic-label-insertion.md)、[ADR 0086](0086-inserted-labels-pass-the-label-check.md)）。
この約束は検査で保っているが、ラベルを手で書いたときと、挿入の後で文法を手で直したときには、作者が確かめるしかない。
挿入の前後で同じ例を流せば、作者の手元の入力の範囲で、受理する言語が変わっていないことを確かめられる。

## 実装すること

### コマンド

```sh
peg-hs test [GRAMMAR.hpeg|DIR...] [--accept]
```

- 文法 `NAME.hpeg` の例は、同じディレクトリの `NAME.cases/` に置く。例の置き場所を選ぶオプションは持たない
- 引数の選び方は `fmt` と `lint` と同じとする（[ADR 0032](0032-grammar-formatter.md)、[ADR 0050](0050-hpeg-extension.md)、[ADR 0077](0077-fixes-of-the-security-audit.md)）。引数がなければ現在のディレクトリの下の `.hpeg` を、ディレクトリを渡せばその下の `.hpeg` を探す
- 探して見つけた文法のうち、`NAME.cases/` のないものは黙って飛ばす。名指しした文法に `NAME.cases/` がなければ誤りとする
- `--accept` は、比べる代わりに、いまの結果で期待のファイルを書く（後述）

### 例の置き方

例は、文法の隣のディレクトリに、一つの例を一つの入力のファイルとして置く。

```text
Expr.hpeg
Expr.cases/
  sum.in        入力
  sum.cst       sum.in を受理し、この CST になることを期待する
  dangling.in
  dangling.err  dangling.in を拒否し、この誤りになることを期待する
  Term/         %entry の規則 Term で解析する例
    digit.in
    digit.cst
```

- **入力**：`*.in` のファイルである。中身をそのまま入力とし、エスケープも区切りもない。終わりの改行も入力の一部である。文字コードはほかのコマンドと同じく UTF-8 とし、先頭のバイト順マークは読み飛ばす（[ADR 0045](0045-fixes-before-v0-1-0.md)）
- **期待**：入力と同じ名前で拡張子だけが違うファイルである。`*.cst` は受理を、`*.err` は拒否を期待する。どちらを置くかで、受理と拒否のどちらを期待するかが決まる
- **入口**：`NAME.cases/` の直下の例は、開始規則で解析する。`NAME.cases/RULE/` の例は、`%entry` に挙げた規則 `RULE` で解析する
- 一つの `*.in` に `*.cst` と `*.err` の両方があれば誤りとする。どちらもなければ、期待のない例として失敗にする
- 対応する `*.in` のない `*.cst` と `*.err` は誤りとする。入力の名前を変えて期待を残したまま、という取り違えを見つけるためである
- `NAME.cases/` の直下のディレクトリのうち、`%entry` にない名前のものは誤りとする。その下のディレクトリも誤りとする
- そのほかの拡張子のファイルは無視する。例の説明を書いた文書を置ける

### 期待のファイルの中身

`*.cst` は、`peg-hs parse --format cst` が表示するものと同じ形の CST である。
`debugTree nameOfSyntaxKind` の形で、各行に種類、バイトの範囲、トークンならその文字列を書く。

```text
Expr@0..3
  a: Term@0..1
    d: TEXT@0..1 "1"
  TEXT@1..2 "+"
  b: Expr@2..3
    Term@2..3
      d: TEXT@2..3 "2"
```

`*.err` は、拒否した位置と期待した字句を、`renderParseError` と同じ一行の形で書く。

```text
1:3: expected [0-9]
```

`*.err` が空なら、位置と期待を比べず、拒否したことだけを確かめる。
誤りの文言は、文言を改善する ADR で変わることがある。
受理する言語だけを確かめたい例は、空の `*.err` にしておけば、文言の変更で落ちない。

比べるときは、期待のファイルの終わりの改行の有無を無視する。
ほかの差は、空白も含めてすべて差とする。

### 解析の仕組み

例の解析は [ADR 0090](0090-grammar-interpreter-without-ghc.md) のインタプリタで行い、GHC を使わない。
文法に `%syntax` がなくても、CST を得る（`peg-hs parse` が `%syntax` を加えて生成するのと同じ扱い）。

インタプリタが扱えない文法（[ADR 0090](0090-grammar-interpreter-without-ghc.md) が扱わないと決めた意味述語などを含むもの）では、`peg-hs parse` と同じく生成したパーサーを GHC でコンパイルして使う。
コンパイルの仕組み、キャッシュ、`--ghc-arg` は `peg-hs parse` のものを使う。
`ghc` が `PATH` になければ、`peg-hs parse` と同じ文言で失敗する。

どちらで解析するかは、文法だけで決まる。
`ghc` の有無で道を変えたり、インタプリタが扱えない例を飛ばしたりはしない。
同じ文法と同じ例は、どの環境でも同じ道を通り、同じ結果になる。

`%env` を宣言した文法は、[ADR 0090](0090-grammar-interpreter-without-ghc.md) のインタプリタが扱える場合（`_env` をアクションでしか読まない場合）だけインタプリタで解析し、それ以外は誤りとする。
コンパイルする道では環境の値を渡せない（[ADR 0036](0036-parse-command.md)）ので、コンパイルする道には回さない。

### 出力

通った例は表示しない。
失敗した例ごとに、標準出力に次の形で報告する。

```text
Expr.cases/sum.cst:3: the syntax tree differs
  expected:   TEXT@1..2 "+"
  actual:     TEXT@1..2 "-"
Expr.cases/dangling.err: expected a rejection, but the input was accepted
Expr.cases/three.cst: expected acceptance, but 1:4: expected end of input
Expr.cases/new.in: no expectation; run peg-hs test --accept to record the result
```

- CST の差は、最初に違う行だけを、期待のファイルの行の番号とともに示す。片方が先に終わったときは、その側を `(end of file)` と書く。差分の全体は、`--accept` で書いた後に `git diff` で見られる
- `*.err` の差は、期待と結果の行をそのまま並べる
- 最後に、例の数を `3 passed, 1 failed` の形で一行書く

文法の誤り、読めないファイル、例の置き方の誤りは、ほかのコマンドと同じく標準エラー出力に `ファイル:行:桁: error: 文言` か `peg-hs: 文言` の形で書く（[ADR 0037](0037-cli-subcommands.md)）。

### 終了状態

- 0：すべての例が通った。`--accept` で期待のファイルを書き終えた
- 1：通らない例がある。期待のない例がある。文法の誤り、例の置き方の誤り、読み書きできないファイル、扱えない文法（`%env`、`ghc` のない環境でのコンパイル）
- 2：使い方の誤り

CI では、`peg-hs test` をそのまま流せば、例が一つでも落ちれば失敗する。

### 期待の更新（--accept）

`--accept` は、各例を解析し、結果で期待のファイルを書く。

- 受理した例は `*.cst` を書き、`*.err` があれば消す。拒否した例は `*.err` を書き、`*.cst` があれば消す
- 拒否した例の `*.err` が空なら、空のまま残す。空の `*.err` は、作者が文言を比べないと決めた印だからである
- 結果が期待と同じ例のファイルは書き直さない
- 書いたファイルと消したファイルを、標準出力に一行ずつ書く

例を足す手順は、`*.in` を置いて `peg-hs test --accept` を流し、書かれた期待を読んで確かめる、となる。
書かれた期待が正しいかを判断するのは作者であり、`git diff` で確かめてからコミットする。

### 文書

README の「Commands」の表に `test` を加え、「### test」の節を書く。
`docs/specifications.md` の「文法ファイルの道具」に、例を試すコマンドを加える。
ラベルの挿入の節（README の「### label」）に、挿入の前後で `peg-hs test` を流せば手元の例で言語が変わっていないことを確かめられる、と書く。

## 実装しないこと

- **文法のファイルへの例の埋め込み**：`.hpeg` の記法は、tree-sitter と TextMate の文法、整形器、言語サーバーと共有している。例の構文を足すと、それらをすべて直すことになる。入力をエスケープなしに置ける区切りも、記法の中には作りにくい。例を文法の隣のファイルに置けば、記法に手を入れずに済む
- **一つのファイルに複数の例を書く形式**：tree-sitter の corpus のような形式は、入力の中に区切りと同じ行が現れたときの扱いが要る。一つの例を一つの入力のファイルとすれば、この問題が起きない
- **AST（アクションの値）の比較**：インタプリタは AST を返さない。AST を確かめたい作者は、生成したモジュールを Haskell のテストから呼ぶ
- **回復するモード（[ADR 0021](0021-error-recovery.md)）の結果の比較**：`peg-hs parse` も回復の結果を表示しない。回復した構文木と回復した誤りの一覧を比べたくなったら、`*.recover` のような期待を加える ADR を起こす
- **言語サーバーとエディタからの例の実行**：言語サーバーは文法のファイルだけを扱い、例のディレクトリを読まない。コマンドをエディタのタスクとして流せば足りる
- **WebAssembly への公開**：`peg-hs test` はファイルシステムの上の例を読むコマンドであり、[ADR 0078](0078-grammar-analysis-in-wasm.md) の WebAssembly の境界には加えない
- **例の置き場所を選ぶオプション、例の名前で絞り込むオプション、並列の実行、JSON などの機械向けの出力**：必要になったら ADR を起こす
- **インタプリタとコンパイルの道を選ぶオプション**：道は文法だけで決まる

## テスト設計

テストは `packages/peg-cli/test/Main.hs` に、一時ディレクトリに文法と例を書いて `peg-hs test` を流す形で書く。
実装の前に書き、すべて落ちることを確かめてから実装する。

- **受理の例**：`*.cst` が一致すれば終了状態 0 で、通った例を表示せず `1 passed, 0 failed` を書くこと。CST の行を一つ変えると終了状態 1 で、`FILE:行:` と期待と結果の行を報告すること。期待のファイルが先に終わる場合と結果が先に終わる場合に `(end of file)` を示すこと
- **拒否の例**：`*.err` の文言が一致すれば通り、位置か期待が違えば落ちること。空の `*.err` は、どの位置の拒否でも通ること。受理する入力に `*.err` を置くと落ち、拒否する入力に `*.cst` を置くと落ちること
- **期待の終わりの改行**：期待のファイルの終わりの改行の有無で結果が変わらないこと
- **入力のバイト列**：終わりの改行の有無で結果が変わる文法（`!.` で終わる規則）で、`*.in` の改行が入力に含まれること。先頭のバイト順マークを読み飛ばすこと
- **置き方の誤り**：期待のない `*.in` が `--accept` を案内して落ちること。`*.cst` と `*.err` の両方がある例、`*.in` のない期待、`%entry` にない名前のディレクトリ、二段目のディレクトリを誤りとすること。ほかの拡張子のファイルを無視すること
- **入口**：`NAME.cases/RULE/` の例を `%entry` の規則で解析すること
- **`--accept`**：期待のない例に結果を書くこと。受理と拒否が入れ替わった例で、古い期待を消して新しい期待を書くこと。空の `*.err` を空のまま残すこと。一致する例のファイルを書き直さないこと（中身と更新時刻が変わらない）。書いた後の `peg-hs test` が通ること
- **文法の選び方**：引数なしで現在のディレクトリを探し、`NAME.cases/` のない文法を飛ばすこと。名指しした文法に `NAME.cases/` がなければ誤りとすること
- **GHC のない解析**：インタプリタが扱える文法の例を、`PATH` に `ghc` のない環境で流して通ること
- **コンパイルの道**：インタプリタが扱えない文法の例を、`ghc` のある環境で流して通ること。`ghc` のない環境では、`peg-hs parse` と同じ文言で終了状態 1 になること
- **`%env`**：`%env` の文法を誤りとすること
- **二つの道の一致**：JSON の文法（`conformance/json/Json.hpeg`）と JSONTestSuite の入力で、インタプリタとコンパイルしたパーサーの `*.cst` と `*.err` の中身が一致すること。テストからは内部の関数で両方の道を呼ぶ。この検査は `ghc` の要るテストとして、CI の Haskell のジョブで動かす
- **ラベルの挿入**：例を置いた文法に `peg-hs label --write` をかけた後も、`*.cst` の例と空の `*.err` の例が通ること
- **終了状態と使い方の誤り**：未知のオプションが終了状態 2 になり、`peg-hs help test` を案内すること。文法の誤りが `ファイル:行:桁: error:` の形で終了状態 1 になること
- **ヘルプ**：`peg-hs help test` の出力を golden ファイル（`test/golden/help-test.txt`）と比べること。コマンドの一覧に `test` があること

## トレードオフ

- 例ごとに二つのファイルを置くので、ファイルの数が増える。代わりに、入力はエスケープも区切りもないそのままのバイト列になり、`cat` や `diff` などのほかの道具でそのまま扱える
- `*.in` の終わりの改行は入力の一部なので、終わりに改行を足すエディタで保存すると、入力が変わる。期待のファイルでは終わりの改行を無視するが、入力では無視できない。改行の有無で解析が変わる文法があるからである
- 期待を `--accept` で書く流れは、誤った結果をそのまま期待にしてしまう余地がある。書かれた期待を読んで確かめるのは作者の仕事であり、コマンドはそれを代われない
- CST の期待はバイトの範囲を含むので、規則の名前を変えたり、入力の前のほうを一文字変えたりすると、多くの行が変わる。その場合は `--accept` で書き直し、`git diff` で確かめる
- インタプリタの扱えない文法ではコンパイルを待つので、意味述語を使う文法（Lua の文法など）では、初回の `peg-hs test` が遅い。例を飛ばさずに確実に試すことを、速さより優先した
- `*.err` の文言は、誤りの文言を改善するたびに変わる。文言の変更の後は、`--accept` で書き直すか、文言を比べない例を空の `*.err` にしておく
- 例の置き場所を `NAME.cases/` に固定したので、文法をパッケージの `src/` に置くと、例も `src/` に並ぶ。置き場所を選ぶオプションを持たないことで、`peg-hs test` を引数なしで流すだけで、どの文法の例も見つかる
