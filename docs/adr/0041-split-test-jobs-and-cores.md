# ADR 0041: テストスイートを別のジョブに分け、ジョブの中ではコアを一つのスイートに渡す

ステータス: 採択

## 文脈

[ADR 0039](0039-faster-ci.md) で、すべてのキャッシュが当たる CI はワークフロー全体で約 3 分 45 秒になった（[計測](../benchmarks/2026-10-13-ci-duration.md)）。
残りの大半はテストの段（133〜177 秒）である。
[ADR 0039](0039-faster-ci.md) が目安にした「peg-grammar-test が最も長いスイートでなくなるか、100 秒以内に終わること」は満たさなかった。
peg-grammar-test は 111 秒と 150 秒だった。

テストを並列にしても、手元ほど縮まなかった。
peg-grammar-test は、手元（10 コア）では 147 秒（一つずつ）から 66 秒（並列）になったが、CI では 198 秒から 111〜150 秒にとどまった。
ほかのスイートの一部（Lua、TOML、JSON の適合性）は、かえって遅くなった。

原因は、コアの取り合いである。
CI のランナー（公開リポジトリの `ubuntu-latest`）は 4 コアである。
`cabal test all` は 10 個のテストスイートをほぼ同時に起動する。
[ADR 0039](0039-faster-ci.md) で、各スイートは `-N`（コアの数だけの実行スレッド）で動き、tasty はコアの数だけテストを並列に動かす。
4 コアを、10 個のスイートがそれぞれ 4 スレッドで奪い合う。

スイートの重さは偏っている。
すべてのキャッシュが当たった実行で、スイートが報告した時間は次のとおりだった。

| スイート | 時間 |
|---|---:|
| peg-grammar-test | 150 秒 |
| lua-conformance | 85 秒 |
| toml-conformance | 54 秒 |
| json-conformance | 49 秒 |
| peg-cli-test | 23 秒 |
| peg-lsp-test | 7 秒 |
| peg-codegen-test | 2 秒 |
| commonmark-conformance、complexity、peg-runtime-test | 1 秒未満 |

同時に動いた時間なので、どれも単独で動かしたときより長い。
peg-grammar-test が 4 コアを独占できれば、手元の並列の結果から見て、テストの時間は大きく縮む見込みである。

コアの取り合いを減らす方法は二つある。

- **ジョブを分ける**：重いスイートを別のジョブ（別のランナー）で動かす。ランナーごとに 4 コアがあるので、コアの総数が増える。ジョブごとに、GHC の導入、依存の解決、キャッシュの復元の時間（キャッシュが当たって約 30 秒）がかかる
- **ジョブの中でコアを分ける**：同じランナーの中で、スイートを同時に動かさず一つずつ動かし、各スイートに 4 コアを渡す。あるいは、スイートごとに使うコアの数を決めて同時に動かす。コアの総数は増えないが、取り合いによる無駄（文脈の切り替え、GC の競合）がなくなる

二つは両立する。
ジョブを分けたうえで、各ジョブの中ではスイートを一つずつ動かし、コアを一つのスイートに渡す。

## 実装すること

### テストのジョブ

`haskell` のジョブからテストの段を外し、テストを三つのジョブに分ける。
三つのジョブと `haskell`、`package`、`editors` のジョブは並列に動く。

| ジョブ | スイート | 単独の時間の見込み |
|---|---|---|
| `test-grammar` | peg-grammar-test | 最も重い。4 コアを独占する |
| `test-conformance` | lua-conformance、toml-conformance、json-conformance、commonmark-conformance、complexity | 合計で peg-grammar-test と同程度 |
| `test-packages` | peg-cli-test、peg-lsp-test、peg-codegen-test、peg-runtime-test | 軽い。peg-cli-test は `peg-hs parse` のために GHC を呼ぶ |

- 分け方は、ジョブの時間がそろうように、[ADR 0039](0039-faster-ci.md) の計測をもとに決めた。スイートを加えるときは、計測をもとにどのジョブに入れるかを決める
- 各ジョブは、`haskell` のジョブと同じキャッシュ（GHC、依存のストア、`dist-newstyle`）を復元する。`dist-newstyle` の保存は `haskell` のジョブだけが行い、テストのジョブは復元だけを行う（`actions/cache/restore`）。同じ鍵を複数のジョブが保存し合うのを避けるためである
- 各ジョブは、担当するスイートだけをビルドして動かす（`cabal test peg-grammar:test:peg-grammar-test` など）
- `haskell` のジョブには、ビルド、文法の整形と lint、`cabal check` を残す。テストのジョブより先に終わるので、ワークフローの時間には効かない

### ジョブの中ではスイートを一つずつ動かす

- テストのジョブでは、担当するスイートを先にビルドし（`cabal build -j`、ビルドは並列）、その後 `cabal test -j1` で一つずつ動かす。cabal は `-j` の数だけテストスイートを同時に動かすので、`-j1` で同時に動くスイートを一つにする
- 各スイートは、これまでどおり `-N` でランナーのすべてのコアを使う
- 手元の `cabal test all` は変えない。開発者の機械はコアが多く、[ADR 0039](0039-faster-ci.md) の並列のままで速い

### 計測と文書

- [ADR 0039](0039-faster-ci.md) と同じ方法で、すべてのキャッシュが当たる実行の段ごとの時間とスイートの時間を計測し、`docs/benchmarks/` にスナップショットとして置く
- CONTRIBUTING（日本語と英語）の CI の説明に、テストのジョブの分け方と、スイートを加えるときの決め方を書く

## 実装しないこと

- スイートごとにコアの数を決めて同時に動かすこと。ランナーのコアの数（4）とスイートの重さの比が変わるたびに数を見直すことになる。一つずつ動かすほうが、数の調整が要らない
- スイートの中のテストを複数のジョブに分けること（シャーディング）。peg-grammar-test が単独で目安に届かない場合に、別の ADR で検討する
- より大きなランナーや自前のランナー（[ADR 0039](0039-faster-ci.md) と同じ理由）
- テストの件数や変異の数を減らすこと

## テスト設計

CI の設定の変更なので、自動テストは書けない。
実装の後に、実際に動かして確かめる。

- **すべてのスイートが動くこと**：テストのジョブのログに、10 個のテストスイートのすべてが一度ずつ現れること。どのジョブにも入らないスイートがないこと
- **キャッシュのある実行の時間**：すべてのキャッシュが当たる実行で、ワークフロー全体が [ADR 0039](0039-faster-ci.md) の約 3 分 45 秒より短いこと。目安は 2 分 30 秒以内とする
- **peg-grammar-test の時間**：`test-grammar` のジョブで、peg-grammar-test が 100 秒以内に終わること（[ADR 0039](0039-faster-ci.md) の目安）
- **ジョブの時間のそろい方**：三つのテストのジョブの時間の差が、最も長いジョブの半分以内であること。偏っていれば分け方を見直す
- **キャッシュの保存**：`dist-newstyle` のキャッシュを保存するのが `haskell` のジョブだけであること（キャッシュの一覧で確かめる）
- **記録**：上の計測を `docs/benchmarks/` に置く

## トレードオフ

- ジョブが三つ増えるので、ジョブごとの準備（GHC と依存のキャッシュの復元、依存の解決）の時間がかかり、CI の合計の計算時間は増える。公開リポジトリの標準のランナーは費用がかからないので、待つ時間を減らすことを優先する
- テストのジョブは、`haskell` のジョブのビルドを待たずに、それぞれが必要なものをビルドする。変更したモジュールのビルドは、ジョブの数だけ重複する。`dist-newstyle` のキャッシュがあれば重複は差分だけである
- スイートを一つずつ動かすので、軽いスイートの時間がジョブの中で積み重なる。重いスイートを別のジョブに出したので、積み重なる時間は小さいと見込む
- スイートの重さが変わると、ジョブの分け方が古くなる。スナップショットの計測と、テスト設計の「ジョブの時間のそろい方」で見直す
