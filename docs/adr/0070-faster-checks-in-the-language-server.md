# ADR 0070: 言語サーバーの検査を速くする

ステータス: 採択（未実装）

## 文脈

文法の検査は、コマンドでは十分に速い。
リポジトリの文法と Golem の文法（723 行）で、`peg-hs lint --verbose`、`peg-hs gen`、`peg-hs fmt --check` は、どれも 1 回 0.1 秒以内で終わった（Apple M1 Max、GHC 9.10.3）。

エディタで効くのは、言語サーバー（[ADR 0035](0035-language-server.md)）が編集のたびに行う検査である。
言語サーバーは、文書が変わるたびに、回復する構文解析（概要）、静的検査、ラベルの安全性の検査、lint を行い、診断を送る。
Golem の文法の全文を 51 回続けて送ると（`didOpen` と 50 回の `didChange`）、言語サーバーは 2.33 秒かかった。
1 回の編集につき約 46 ms である。

この時間は、一回の編集では目立たないが、二つの点で遅さとして現れる。

- 速く打鍵すると、編集の通知が言語サーバーの処理より速く届く。言語サーバーは通知を順に処理するので、最後の編集の診断は、それより前のすべての編集の検査の後になる。10 回の打鍵が溜まれば、最後の診断は約 0.5 秒遅れる
- 文法が大きくなるほど、1 回の検査が長くなる

どの段に時間がかかっているかは、まだ測っていない。

## 実装すること

### 溜まった編集の間引き

- 言語サーバーは、文書の変更の通知を受けたとき、入力にほかのメッセージが届いているかを調べる。届いていれば、検査をせずに次のメッセージを読む
- 届いているメッセージをすべて読んだ時点で、変更のあった文書ごとに、最後の版だけを検査して診断を送る
- 診断以外の要求（ホバー、定義への移動、semantic tokens、整形、コードアクション）は、その時点の最新の版に対して答える。要求に答えるときに、検査の済んでいない版があれば、答えの前にその版の概要を作る
- 間引くのは診断の計算だけで、メッセージの順序と、要求への応答の順序は変えない

### 段ごとの計測と速くすること

- 言語サーバーの検査の段（概要、静的検査、ラベルの安全性の検査、lint、semantic tokens の計算）ごとの時間を測る計測を、ベンチマーク（`conformance/bench-main`）に加える。入力は Golem の文法の形を写したリポジトリの文法とし、外部のリポジトリには頼らない
- 計測の結果、時間の大きい段から順に速くする。目安は、Golem の文法の大きさの文法で 1 回の編集の検査を 20 ms 以内にすることとする
- 同じ版の文書について、概要と検査の結果は一度だけ計算し、診断、semantic tokens、ホバー、コードアクションで共有する。いまも文書ごとに概要を保持しているが、検査の結果も保持する
- 速くする変更は、検査の結果（診断の内容と順序）を変えない

### 計測の記録

- 実装の前と後に、上の計測と、Golem の大きさの文法の 51 回の編集の時間を測り、`docs/benchmarks/` に記録する

## 実装しないこと

- 増分の構文解析（変更のあった部分だけを解析し直すこと）。PEG のメモ表を版の間で再利用する仕組みが要り、変更が大きい
- 検査を別のスレッドで行い、古い版の検査を途中で止めること。間引きで足りなければ、別の ADR で検討する
- コマンド（`peg-hs lint`、`gen`、`fmt`）の高速化。いまの時間は 0.1 秒以内で、編集のたびに動くものではない

## テスト設計

先に書き、いまの実装で失敗させる。

- **間引き**：一つの文書に 10 回の `didChange` を続けて送ると、言語サーバーが送る診断が、最後の版の診断を含み、途中の版の診断を 10 回は送らないこと（peg-lsp のテスト）。最後の版の診断が、間引かずに一回ずつ処理した場合の最後の診断と同じであること
- **要求への応答**：変更の通知の直後にホバーや semantic tokens の要求を送ると、最新の版に対する答えが返ること
- **結果が変わらないこと**：リポジトリのすべての文法と、その変異（[ADR 0035](0035-language-server.md) の一致のテストの変異）で、診断の内容と順序が、速くする前と同じであること
- **計測**：自動テストにはしない。実装の前後の計測を記録し、目安（20 ms 以内）に届いたかを書く。届かなければ、届かなかった段と理由を記録に書く

## トレードオフ

- 間引くと、途中の版の診断は送られない。エディタが表示するのは最新の版の診断なので、利用者が失うものはない
- 入力にメッセージが届いているかを調べるので、標準入力の読み方が、いまの一つずつ読む形より複雑になる
- 目安の 20 ms は、打鍵の間隔（数十から百数十 ms）より短く、間引きと合わせて、打鍵中も診断が遅れないことを狙った値である。計測の機械によって変わる
