# ADR 0007: 計算量の保証を明文化し、性能規律は回帰検出のみとする

ステータス: 採択

## 文脈

計算量の保証は選択の問題ではなく、採用済みの機構から従う。
決めるべきは性能目標の立て方だった。
絶対値目標（「1MB を 1 秒」など）はハードウェアに依存して腐り、未達成時に目標と実装のどちらを直すのかという不毛な議論を呼ぶ。
Golem の思想に沿うなら、意味のある信号は「前の版より遅くなったか」である。

## 保証する計算量

- **非左再帰の文法**：全規則メモ化（ADR 0006）により、規則本体の評価回数は位置×規則あたり高々一回。入力長に線形
- **左再帰に関与する規則**：成長ループの各反復は一致長を最低 1 伸ばすため、呼び出しあたりの反復は最悪 O(n)。全体では最悪二乗。実用文法では成長が演算子の連鎖長で止まるため、実測は線形近傍になることが多い

この保証は評価回数についてのものであり、壁時計時間の保証ではない。

## 実装すること

- criterion によるベンチマークスイートを整備し、開発順序の早い段階（peg-codegen の非左再帰版が動いた直後）に置く
- 計測対象は次を含む
  - 自己記述の `.peg` 文法の解析
  - 書籍規模の合成入力（Golem 相当の文法で MB 級のテキスト）
  - 左再帰の病的ケース（成長反復が入力長に比例する文法）
- 計測項目は経過時間とメモ表の常駐メモリとし、後者は `%nomemo` 実装の判断材料（ADR 0006）を兼ねる
- 病的な左再帰文法について、評価回数が二乗の定数倍に収まることをプロパティテストで確認する（保証の裏取り）

## 実装しないこと

- 絶対値の性能目標は置かない
- ベースライン数値のリポジトリへの記録はしない。計測値はハードウェアに依存するため、回帰判定は同一マシンでの変更前後の比較で行う
- CI での自動性能ゲートは設けない。共有ランナーの計測は分散が大きく、閾値が誤検出と見逃しの両方を生むためである

## テスト設計

- ベンチマーク自体は計測であってテストではない。テストとして持つのは評価回数のプロパティ（線形性は ADR 0006、二乗上界は本 ADR）のみとする
- ベンチマーク対象の文法と入力はリポジトリに固定し、計測条件の再現性を保つ

## トレードオフ

- 絶対値の基準がないため、「Golem の用途に十分速いか」の判断は Golem 側の体感と実測に委ねられる。不足が観測されたら、そのときの実測を根拠に最適化の ADR を起こす
- 回帰検出が開発者の手元での比較に依存するため、計測を怠ると退行が入り込む。ベンチマーク実行を変更時の慣行として README に明記する
