# ADR 0002: スタンドアロン生成器と純関数の生成コア

ステータス: 採択

## 文脈

PEG 定義から Haskell コードを得る方式には、`.peg` ファイルを読んで `.hs` を出力するスタンドアロン生成器（happy / alex 方式）と、Haskell ソースに文法を埋め込む Template Haskell quasiquoter がある。
quasiquoter は記述が快適だが、生成コードが不可視でレビューできず、コンパイル時間も増える。
最初の利用者である Golem は決定性と生成物のレビュー可能性をハード制約としており、生成物がリポジトリにコミットできることに価値がある。

## 実装すること

- `.peg` ファイルを読み、Haskell モジュールを書き出す CLI（peg-cli）を実装する
- 文法 AST から Haskell ソースへの変換（peg-codegen）は `Grammar -> Text` の純関数として実装する。ファイル入出力と診断表示は peg-cli に隔離する
- 生成は決定的とする。同一の文法からバイト単位で同一のソースを生成し、タイムスタンプ、生成器のバージョン文字列、環境依存の情報を出力に含めない
- 生成コードの実行時依存は peg-runtime のみとする

## 実装しないこと

- Template Haskell quasiquoter は v1 では実装しない。生成コアが純関数であるため、必要になった時点でフロントエンドとして追加できる
- 生成コードの整形品質は追求しない。人間が読める程度のインデントは保つが、整形器としての品質保証はしない

## テスト設計

- **golden テスト**：代表的な文法ごとに生成ソースのスナップショットを保持し、意図しない生成変化を検出する
- **コンパイルテスト**：生成ソースが GHC でコンパイルでき、生成されたパーサーが期待する構文木を返すことを、文法・入力・期待結果の三つ組で検証する
- **決定性テスト**：同一の文法から二回生成した結果がバイト一致すること

## トレードオフ

- 利用者は生成ステップをビルドに組み込む手間を負う（happy / alex と同等の手間であり、Haskell のビルドエコシステムには前例がある）
- 文法とアクションの Haskell コードが `.peg` ファイル内にあるため、エディタ支援（型検査、補完）はアクション断片には効かない。生成後のコンパイルエラーを `.peg` 側の行番号へ写像する仕組みは未決事項とする
