# ADR 0054: 安全と示せる位置へのラベルの挿入と、言語サーバーでの回復の提案

ステータス: 採択

## 文脈

ラベル（[ADR 0021](0021-error-recovery.md)）は、文法の作者が一つずつ手で書く。
[ADR 0021](0021-error-recovery.md) はこの手間をトレードオフとして認め、ラベルの自動挿入を実装しないことに挙げた。
仕様書は、これを未決事項に残している。

手間の大きさは、リポジトリの文法を見ると分かる。
JSON の文法（`conformance/json/Json.hpeg`）と Lua の文法（`conformance/lua/Lua.hpeg`）は、ラベルを一つも持たない。
そのため、誤りの報告は最遠の位置と期待した字句の集合だけで、`parseErrorLabel` は常に空である。
JSON には回復を試すために手でラベルを付けた派生版（`conformance/bench/JsonRecover.hpeg`）があるが、Lua にはない。
ラベルを付けたくても、どこなら付けてよいかを確かめる作業が、作者の側に残っている。

### 文献の二つの方式

Medeiros, Alvez, Mascarenhas（2020）は、文法を解析してラベルを挿入する方式を二つ示した。

**Standard** は、FIRST と FOLLOW の集合を使い、手で付けるのに近い位置にラベルを付ける。
逐次の中で、すでに字句を読んだ後の要素（空文字列に一致しない非終端か選択）にラベルを付ける。
選択の前の選択肢は、その FIRST が後の選択肢の FIRST と交わらない場合に限って中を調べる。
各ラベルには、FOLLOW に属する字句まで読み飛ばす回復の式 `(!FOLLOW eatToken)*` を自動で与える。
しかし Standard は、規則の中の FIRST と FOLLOW だけを見て、その規則を呼ぶ側の選択が LL(1) でない場合を考えない。
そのため、正しい入力を拒否するラベルを付けることがある。
論文の評価では、Java の文法で 181 個のうち 32 個のラベルが誤りであり、手で取り除く必要があった。

**Unique** は、Standard より控えめに付け、誤ったラベルを付けない。
文法が「ある位置で一致しうる字句は一つだけ」という性質（unique token prefix property）を持つことを前提にする。
そのうえで、ただ一つの構文規則の中で一度だけ使われる字句の規則（unique な字句）に一致した後に限ってラベルを付ける。
unique な字句に一致した後は、後戻りしても同じ字句を同じように読み直すだけなので、続く要素の失敗は入力全体の失敗になる、という理屈である。
その代わり、付けるラベルは手で付けた数よりずっと少なく（Java で 175 個に対して 80 個）、回復の質も手で付けた場合に及ばない。

### peg-hs の文法にそのまま当てはまらない理由

どちらの方式も、字句の規則と構文の規則の区別を前提にしている。
peg-hs の文法は字句解析器を持たず、文字の単位で書く。
空白もリテラルも識別子も、ほかの規則と同じ規則である。
unique token prefix property は字句の列を前提にした性質なので、peg-hs の文法では定義そのものができない。

自動の回復の式も使えない。
文字の単位の FOLLOW は文字の集合であり、`(!FOLLOW .)*` は FOLLOW に英字が含まれれば次の英字ですぐに止まる。
字句の単位で読み飛ばす `eatToken` に当たるものは、文法から機械的には作れない。
さらに peg-hs の回復の規則は、ラベルを付けた式と同じ型の値を返さなければならない（[ADR 0021](0021-error-recovery.md)）。
利用者の AST のどの構成子で誤りを表すかは、生成器には決められない。

### peg-hs にあるもの

一方で、peg-hs にはどちらの論文の方式にもない道具がある。
ラベルの安全性の検査（[ADR 0028](0028-label-safety-check.md)、[ADR 0029](0029-label-safety-implementation-deviations.md)、[ADR 0038](0038-label-check-precision-and-strip-labels-entries.md)）である。
この検査は健全であり、安全と判定したラベルは受理する言語を変えない。
失敗を規則の呼び出し元まで追うので、Standard が見落とした「呼ぶ側の選択」も調べる。
そして各ラベルを、ほかのラベルをすべて外した文法の上で判定する（[ADR 0029](0029-label-safety-implementation-deviations.md)）。
個々に安全と判定したラベルを何個加えても、すべてのラベルが安全である限り、ラベルを付けた文法と外した文法は同じ言語を受理する。

それなら、候補の位置は Standard のように広く取り、どれを残すかは安全性の検査に決めさせればよい。
Standard の候補のうち、検査が安全と示せたものだけを残す。
残ったラベルは Unique のように言語を変えず、しかも unique な字句という前提を要らない。

### 仕様書の「自動のエラー回復」との関係

仕様書は「意図的に採用しなかったもの」に、自動のエラー回復を挙げている。
同期の位置を生成器が自動で探す回復と、ラベルの自動挿入をしない、回復の位置は作者が決める、という項である。
根拠は [ADR 0021](0021-error-recovery.md) にあり、自動で同期の位置を探す方式では、どこで再開するかを作者が制御できず、Golem の局所性の要件（誤りを段落の外に広げない）を保証できない、というものだった。

この根拠は、生成器が生成のたびに暗黙にラベルと回復を加える方式に向けたものである。
この ADR の方式はそれと違い、次の三点で作者が制御を保つ。

- 生成器（`peg-hs gen`）は、ラベルを挿入しない。挿入は、作者が明示的に実行する別のコマンドが行う
- コマンドは文法ファイルのテキストに `^label` を書き込む。挿入したラベルはふつうのラベルとして文法に残り、作者が差分を読み、名前を変え、消せる
- 回復の規則は生成しない。回復の位置（どのラベルで回復し、どこまで読み飛ばすか）は、これまでどおり作者が `%recover` で決める

したがって、仕様書の項の根拠は保たれる。
変わるのは項の書き方であり、「ラベルの自動挿入はしない」を「生成器による暗黙の挿入はしない」に狭める。

### 回復するモードでの危険

ラベルを挿入しても、回復しないモードの受理は変わらない。
しかし回復するモードでは、回復の規則のないラベルが、既存の回復を素通りさせることがある。

peg-hs の実行時ライブラリで、`e ^l` が回復するのは `e` の普通の失敗だけである。
`e` の中で送出された別のラベルは、`l` の回復の規則を通らずにそのまま外へ伝わる（`labeledWith` は `Fail` だけを扱い、`Throw` はそのまま返す）。
たとえば `Block <- (Heading / Para) ^block` に `%recover block SkipBlock` があるとする。
`Para` の中に回復の規則のないラベル `m` を挿入すると、`Para` の中の誤りは `m` の送出になる。
`m` は `block` の回復を通り越して外へ伝わり、開始規則まで回復されなければ入力の全体が一つの構文エラーになる。
挿入の前なら、その誤りは `SkipBlock` で次のブロックまで読み飛ばされ、局所的に回復していた。

挿入したラベルは回復の規則を持たないので、回復の規則の付いたラベルの内側には挿入できない。

## 実装すること

### コマンド

`peg-hs` にサブコマンド `label` を加える（[ADR 0037](0037-cli-subcommands.md) の形に従う）。

```sh
peg-hs label GRAMMAR.hpeg [--write] [--rule RULE]...
```

- 既定では、ファイルを書き換えず、挿入するラベルを標準出力に一行ずつ書く。形は `ファイル:行:桁: ^名前` とし、位置はラベルを付ける式の始まりとする
- `--write` を指定すると、ファイルを書き換え、同じ一覧を標準出力に書く
- `--rule RULE` を指定すると、その規則の中の位置だけを対象にする。複数回指定できる。文法にない規則を指定すると、`undefined rule R` の誤りにする
- 対象は指定した一つのファイルだけとする。`fmt` と `lint` のようなディレクトリの探索はしない
- 文法に誤りがある（記法の誤り、静的検査の誤り）場合は、誤りを報告して何も挿入しない
- 終了状態とヘルプは [ADR 0037](0037-cli-subcommands.md) の共通の約束に従う。挿入するラベルがあってもなくても、成功は 0 とする

### 挿入するラベル

挿入するのは、次の「アルゴリズム」の節で選んだ位置のラベルだけである。
どのラベルも、安全性の検査が安全と判定したものであり、受理する言語を変えない。
回復の規則（`%recover`）と `%safe` は書かない。
既存のラベル、`%recover`、`%safe` は変えない。

### ソースの書き換え

- 書き換えは、選んだ式の直後に ` ^名前`（空白一つと `^` と名前）を挿入することだけとする。コメント、空白、改行（CRLF を含む）、ほかのすべての字句はそのまま残す
- 式の終わりの位置は、整形が使うロスレスな構文木（[ADR 0032](0032-grammar-formatter.md) の `PegSyntax.hpeg`）から得る
- 書き換えた結果を解析し直し、元の AST に選んだラベルを加えたものと一致することを確かめる。一致しなければ内部の誤りとして報告し、ファイルを書かない

### ラベルの名前

名前は `規則名_対象` とする。
規則名はラベルを付ける式がある規則の名前であり、対象はラベルを付ける式から次のように決める。

| 式 | 対象 |
|---|---|
| 規則の参照 `R`、`R(args)` | 規則名 `R` |
| 識別子の文字だけでできたリテラル `'end'` | リテラルの文字列 `end` |
| 一文字の記号のリテラル `')'` `']'` `'}'` `','` `';'` `'='` など | 固定の表の名前（`rparen`、`rbracket`、`rbrace`、`comma`、`semi`、`eq` など） |
| そのほかのリテラル | `lit` |
| 文字クラス | `class` |
| `.` | `any` |
| グループ | `group` |
| `e+`、`$e` | `e` の対象 |

- 同じ名前が二つ以上になる場合は、ソースの順で二つめから `_2`、`_3` を付ける
- 文法にすでにあるラベルの名前、`%recover` と `%safe` に書かれた名前とは重ならないようにする。重なる場合も同じく番号を付ける
- 記号の表は peg-cli の Haddock とヘルプに載せる

名前は作者が後で変えることを前提にした仮の名前である。
同じ位置に別々のラベルを付けるのは、`%safe` と `%recover` がラベルの名前で効くためである（[ADR 0038](0038-label-check-precision-and-strip-labels-entries.md) の文脈）。

### ライブラリ

- 候補の列挙、安全性による選別、名前の決定を、peg-grammar の純粋な関数として実装する。peg-cli はその薄いラッパーとする（仕様書の「生成コアの純粋性」）
- 安全性の判定は、`labelWarnings` と同じ検査を、仮に置いたラベル一つについて行う関数として `Peg.Grammar.Labels` に加える。文字の集合の抽象（`abstractions`）はラベルを無視して計算するので、候補ごとに作り直さず一度だけ計算する

### 言語サーバーでの提案

ラベルを付けた後に作者がすることは、回復したいラベルに `%recover` と回復の規則を書くことである。
どのラベルに回復の規則がなく、回復の規則に何を書けばよいかは、文法を開いて編集している最中に知りたい。
そのため、言語サーバー（[ADR 0035](0035-language-server.md)）に、二つのコードアクションを加える。
どちらも、作者が選んだときだけ文法を書き換える。

- **ラベルを付ける**：カーソルの位置の式が、上の「アルゴリズム」で選ばれる候補なら、` ^名前` を挿入するアクションを出す。名前の決め方はコマンドと同じとする。ファイル全体の候補をまとめて挿入するアクションも出す
- **`%recover` を加える**：回復の規則を持たないラベル（`%recover` に書かれていないラベル）の上で、`%recover 名前 Recover_名前` の指示と、回復の規則の雛形を加えるアクションを出す
  - 回復の規則の型は、ラベルを付けた式の値の型とする。規則の参照なら、その規則の型注釈の型である。リテラル、文字クラス、`.` なら `()` である（[ADR 0030](0030-unit-values-are-not-counted.md)）。型を決められない式（グループなど）には、このアクションを出さない
  - 回復の規則の本体は、同じ逐次の中でラベルを付けた式の次にあるリテラルの手前まで読み飛ばす `(!'x' .)*` とする。次にリテラルがなければ、行の終わりの手前まで読み飛ばす `(![\n] .)*` とする
  - 回復の規則のアクションは、型の穴 `{ _ }` とする。回復したときの値は文法の意味によって決まり、道具には決められない。生成したモジュールのコンパイルで、GHC が穴の型を文法の行で示すので、作者はそれを見て値を書く
  - 指示は文法の指示の並びの末尾に、回復の規則はラベルのある規則の直後に加える
- 回復の規則に覆われた位置（次の「アルゴリズム」の節）にあるラベルには、`%recover` を加えるアクションを出さない。加えても、外側の回復に受け止められないためである
- 言語サーバーは、これまでコードアクションを持たない。`initialize` の応答の `codeActionProvider` に加え、`textDocument/codeAction` に応える
- 診断（警告）としては出さない。候補は多く、どれを付けるかは作者が決めることなので、警告にすると警告を抑制できない lint（[ADR 0033](0033-grammar-linter.md)）と同じ問題が起きる

### 文書

採択と同じコミットで、次の文書を改める。

- 仕様書の「文法ファイルの道具」にコマンド `peg-hs label` を加える（六つから七つになる）
- 仕様書の「意図的に採用しなかったもの」の自動のエラー回復の項を、「同期の位置を生成器が自動で探す回復、生成器による暗黙のラベルの挿入、回復の規則の自動の生成はしない。回復の位置は文法の作者がラベルと回復の規則で決める」に改める
- 仕様書の未決事項からラベルの自動挿入を外し、この ADR が残す課題（回復の規則に覆われた位置への挿入）を加える
- 仕様書の言語サーバーの機能に、二つのコードアクションを加える。README のエディタの節にも書く
- README のコマンドの一覧
- [docs/syntax.md](../syntax.md) の「ラベルの安全性の検査」の節に、`peg-hs label` で安全なラベルを挿入できることを加え、冒頭の反映している ADR の一覧にこの ADR を加える

## アルゴリズム

### 候補の列挙

逐次（規則の選択肢と、グループの選択肢）ごとに、要素を左から順に見る。
逐次の中で、それより前に**必ず入力を読む要素**（空文字列に一致しない要素）があるとき、その要素は「すでに字句を読んだ後」にある。
Standard の `seq` の条件にあたる。
空文字列に一致するかは、検査が使う `nullableExpr` で判定する。

すでに字句を読んだ後にある要素のうち、次のすべてを満たすものを候補とする。

- 式が空文字列に一致しない。空文字列に一致する式（`e*`、`e?` など）は失敗しないか、失敗しても入力を読まずに済むので、ラベルの意味が薄い
- 式がリテラル、文字クラス、`.`、規則の参照、グループ、`e+` のどれか、またはそれに `$` を付けたものである。`$e` に付けると `$(e ^l)` と読まれるが、値はキャプチャの文字列のままで変わらない
- 先読み（`&e`、`!e`）と意味述語ではない。先読みに付けたラベルは先読みの中に入り、効果を持たない（[ADR 0033](0033-grammar-linter.md) の ineffective-label）
- すでにラベルが付いていない
- 先読みの中、回復の規則の中、雛形の定義の中、雛形の呼び出しの引数の中にない。回復の規則の中の送出は回復の失敗になり（[ADR 0021](0021-error-recovery.md)）、雛形は展開した位置ごとに安全性が変わるためである
- 次の「回復の規則に覆われた位置」ではない

逐次の先頭の要素は候補にしない。
そこでの失敗は、後戻りして別の選択肢を試すための普通の失敗であることが多く、Standard も付けない。
規則の本体の選択の全体にもラベルを付けない。
Standard が選択の全体に付けるラベルは、peg-hs では呼び出し元の参照 `R` に付けるラベルと同じ働きをするので、参照の側の候補で代える。

Standard の FIRST と FOLLOW の交わりの条件は使わない。
その判断は、次の選別が行う。

### 安全性による選別

候補ごとに、その位置だけにラベルを仮に置き、ラベルの安全性の検査で判定する。
安全と判定した候補だけを残す。
危険（`may reject valid input`）と検査できない（`cannot be checked`、間接の左再帰で成長する選択肢の中）は、どちらも捨てる。

各候補は、ほかのラベル（既存のものも、ほかの候補も）をすべて外した文法の上で判定される（[ADR 0029](0029-label-safety-implementation-deviations.md)）。
したがって、残した候補をまとめて挿入しても、判定は変わらない。
挿入の後の文法では、挿入したラベルについて `peg-hs gen` は警告を出さない。
既存のラベルへの警告は、挿入の前と同じである。

### 回復の規則に覆われた位置

回復の規則を持つラベル（`%recover` に名前のあるラベル）を付けた式 `e ^l` について、次を**覆われた位置**とする。

- `e` の中の位置
- `e` の中から規則の呼び出しをたどって到達できる規則の、すべての位置

覆われた位置は、候補から除く。
到達できるかは規則の単位で判定するので、実際には `l` の内側でしか呼ばれない規則も、外側から呼ばれる規則も、どちらも除かれる。
安全側に倒した近似である。
`%recover` を持たない文法では、覆われた位置はない。

### 例

次の文法に `peg-hs label` を実行するとする。

```hpeg
List :: [Int]
List <- '[' v:Num vs:(',' n:Num { n })* ']' !. { v : vs }

Num :: Int
Num <- d:$[0-9]+ { read (unpack d) }
```

候補は、`'['` の後の `Num`、グループの中の `','` の後の `Num`、`']'` の三つである。
`'['` と `','` と `Num` の `$[0-9]+` は逐次の先頭なので候補にならず、`(...)*` は空文字列に一致し、`!.` は先読みなので候補にならない。
三つとも安全と判定され、次のように書き換わる。

```hpeg
List <- '[' v:Num ^List_Num vs:(',' n:Num ^List_Num_2 { n })* ']' ^List_rbracket !. { v : vs }
```

`S <- 'a' 'b' { () } / 'a' 'c' { () }` では、候補は `'b'` と `'c'` である。
`'b'` に付けると、`ac` を二つめの選択肢で受理できなくなるので、検査が危険と判定して捨てる。
`'c'` は、そこで失敗すれば後に試す道がないので残る。

## 実装しないこと

- 生成器による挿入。`peg-hs gen` にラベルを挿入するオプションは設けない。生成物の元になる文法と、作者が読む文法を一致させるためである
- コマンドでの回復の規則の生成と、値まで含んだ回復の規則の生成。文字の単位の FOLLOW では読み飛ばす範囲を正しく決められず、回復したときの値も決められない（文脈）。言語サーバーが出すのは、作者が値を書き入れる前提の雛形だけである
- 安全と示せない候補の挿入。Standard のように広く付けて作者に消させる動作は、オプションとしても持たない。誤ったラベルは、作者がテストで見つけるまで受理する言語を変えたままになるためである
- 既存のラベルの変更、削除、名前の変更。危険と警告された既存のラベルの修正
- 回復の規則に覆われた位置への挿入。そのためには、回復の規則のないラベルの送出を外側のラベルの回復で受け止めるよう、[ADR 0021](0021-error-recovery.md) の実行時の意味論を変える必要がある。別の ADR で検討する
- 挿入しなかった候補の理由の報告（危険、検査できない、覆われている）
- unique な字句の条件そのもの。字句の層のない peg-hs の文法には当てはまらない
- ディレクトリの再帰的な探索と複数のファイル

## テスト設計

テストを先に書き、`label` の実装がない状態で失敗させる。
単体のテストは peg-grammar のテスト（ラベルの安全性のテストの隣）に、コマンドのテストは peg-cli のテストに置く。

### 候補の列挙

- 「例」の節の二つの文法で、候補がその節に書いたとおりになること
- 候補にならない位置：逐次の先頭、`e*` と `e?`、`&e` と `!e` と意味述語、すでにラベルのある式、先読みの中、回復の規則の中、雛形の定義の中と雛形の呼び出しの引数、空文字列に一致する規則の参照とグループ
- 字句を読む要素が前にあっても、それが空文字列に一致する（`'a'? 'b'` の `'b'`）なら候補にならないこと

### 選別

- [ADR 0028](0028-label-safety-check.md) の危険な例（`unsafeSnippets`）を、ラベルを外した形で与えたとき、そのラベルの位置に挿入しないこと
- [ADR 0028](0028-label-safety-check.md) と [ADR 0038](0038-label-check-precision-and-strip-labels-entries.md) の安全な例を、ラベルを外した形で与えたとき、その位置に挿入すること
- 間接の左再帰で成長する選択肢の中には挿入しないこと
- 挿入の後の文法で、`labelWarnings` が挿入したラベルに警告を出さないこと。既存のラベルへの警告が挿入の前と同じであること

### 覆われた位置

- `%recover` のあるラベルを付けた式の中と、そこから呼び出しをたどって到達できる規則の中には挿入しないこと。到達できない規則には挿入すること
- `%recover` のないラベルの内側には挿入すること
- codegen の Recover の fixture に挿入し、fixture の入力で `parseRecover` と `parseSyntaxRecover` の結果（値、木、構文エラーの列）が挿入の前と同じであること

### 健全性

- **無作為な文法**：[ADR 0028](0028-label-safety-check.md) のプロパティテストの文法の生成器とインタプリタを使う。ラベルのない無作為な文法に挿入し、短い入力の全列挙で、挿入の前と後の受理と拒否が一致すること
- **JSON**：`conformance/json/Json.hpeg` に挿入して生成し、JSONTestSuite の全件で受理と拒否が挿入の前と一致すること
- **Lua**：`conformance/lua/Lua.hpeg` に挿入して生成し、Lua の適合性テストの入力の全件で受理と拒否が挿入の前と一致すること
- 誤りの位置と期待した字句の集合は比べない（トレードオフ）。拒否した入力のうち `parseErrorLabel` に挿入したラベルが入ったものの数を、実装の PR に記録する

### 名前

- 規則の参照、識別子のリテラル、記号の表のリテラル、そのほかのリテラル、文字クラス、`.`、グループ、`e+`、`$e` のそれぞれの名前
- 同じ名前の二つめからの番号。既存のラベル、`%recover`、`%safe` の名前との重なりを番号で避けること
- どの名前も識別子として読めること（書き換えた結果を解析し直せること）

### 書き換え

- コメント、不揃いの空白、CRLF の改行、束縛 `x:e`、キャプチャ `$e` を含む文法の golden テスト
- 書き換えの前と後のテキストの差が、` ^名前` の挿入だけであること（プロパティテスト。無作為な文法を印字して挿入する）
- 挿入の前に `peg-hs fmt --check` が成功する文法は、挿入の後も成功すること
- `peg-hs lint` の警告が、挿入の前と後で同じであること
- 冪等性：挿入した結果にもう一度実行すると、何も挿入しないこと
- 決定性：同じ入力から同じ出力になること

### コマンド

- 既定ではファイルを書き換えず、一覧を標準出力に書くこと。`--write` で書き換えること
- `--rule` で対象を絞れること。文法にない規則を指定すると誤りになること
- 文法に誤りがあれば、誤りを報告して何も書き換えず、終了状態が 1 になること
- 未知のオプションと引数の不足で終了状態が 2 になること。`peg-hs help label` が例を含むこと

### 言語サーバー

- `initialize` の応答に `codeActionProvider` があること
- 候補の位置で「ラベルを付ける」アクションが出て、適用した結果がコマンドの `--write` と同じ文になること。候補でない位置では出ないこと
- 回復の規則のないラベルの上で「`%recover` を加える」アクションが出ること。規則の参照、リテラル、文字クラスの三つで、回復の規則の型が上の決め方のとおりになること。グループのラベルと、回復の規則に覆われた位置のラベルでは出ないこと
- 「`%recover` を加える」を適用した文法が、記法の解析と静的検査を通ること。生成したモジュールのコンパイルが、型の穴の誤りだけで失敗し、その位置が回復の規則のアクションの行であること
- 読み飛ばしの本体が、次のリテラルがある場合とない場合で、上の決め方のとおりになること

### 性能

自動テストにはしない。
リポジトリで最大の文法（記法の文法 `Peg.hpeg`）と Lua の文法で実行時間を計り、実装の PR に記録する。
候補ごとに検査を行うので、`peg-hs gen` の検査より遅くなる。
10 秒を超える場合は、候補の判定を共有する工夫を別の ADR で検討する。

## トレードオフ

- 挿入するラベルの数は、安全性の検査の偽陽性の分だけ減る。意味述語で文字を判定する規則の近くは、安全でも挿入されない。記法の文法の 21 個の `%safe`（[ADR 0029](0029-label-safety-implementation-deviations.md)）は、この種の位置である。Standard より少なく、手で付けるよりずっと少なくなる見込みだが、付けたラベルが言語を変えることはない
- 覆われた位置を除くので、Golem の文法のように、ほとんどの規則が回復の規則を持つラベル（`^block` など）の内側にある文法には、ほとんど挿入しない。このコマンドが最も役に立つのは、まだラベルのない文法か、回復を持たないラベルだけの文法である
- コマンドは回復の規則を生成しないので、挿入しただけでは回復するモードの結果は良くならない。回復しないモードで、誤りの報告にラベルの名前が載るようになるだけである。作者は言語サーバーの「`%recover` を加える」アクションで回復の規則の雛形を加え、値を書き入れる
- 回復の規則の雛形の読み飛ばしは、次のリテラルか行の終わりまでという単純なものである。文法によっては適切な同期の位置にならないので、作者が見直す必要がある
- ラベルは送出した位置で解析を止めるので、回復しないモードの誤りの位置と期待した字句の集合は、挿入の前と変わりうる。lint（[ADR 0033](0033-grammar-linter.md)、[ADR 0049](0049-lint-false-positive-test-and-expected-sets.md)）は「直しても誤りの位置は変わらない」と約束するが、このコマンドは受理と拒否が変わらないことだけを約束する
- ラベルのない文法に挿入すると、生成するモジュールに回復の入口（`parseRecover` など）が加わり、生成物の差分が大きくなる。既存の入口は変わらない
- 名前は機械的に決まり、文法の意味を表さない。作者が名前を変えるときは、`%recover` や利用者のメッセージの対応表も合わせて変える必要がある
- 仕様書の「ラベルの自動挿入はしない」を狭める。生成器が暗黙に挿入しないことと、回復の位置を作者が決めることは保つが、挿入そのものを道具が行うことは認める
