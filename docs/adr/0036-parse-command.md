# ADR 0036: 文法で入力を解析して AST と CST を表示するコマンド（peg-hs parse）

ステータス: 採択

## 文脈

文法を書いている途中で、ある入力がどう解析されるかを確かめたいことが多い。
いまは、文法からモジュールを生成し、それを読み込むプログラムを書き、コンパイルして実行する必要がある。
Lua と TOML の文法（[ADR 0022](0022-lua-conformance.md)、[ADR 0023](0023-toml-conformance.md)）を書いたときも、確かめるたびに使い捨ての実行ファイルを作った。

文法と入力のファイルを渡せば、解析の結果を表示するコマンドがあれば、この手間がなくなる。
表示したいものは二つある。

- **AST**：アクションが作る、文法の作者の型の値
- **CST**：ロスレスな構文木（[ADR 0019](0019-lossless-syntax-tree.md)）。空白とコメントを含む、規則の呼び出しの木

AST はアクション（Haskell の式）の値なので、文法を解釈するだけでは得られない。
意味述語、規則の引数、解析環境（[ADR 0012](0012-context-sensitive-extensions.md)）も Haskell の式である。
そのため、生成したパーサーを GHC でコンパイルして実行する。

コンパイルには peg-runtime が要る。
peg-runtime は GHC に付属するパッケージ（base、containers、text、array）だけに依存する（[ADR 0015](0015-implementation-deviations.md)）。
peg-runtime のソースを peg-hs の実行ファイルに含めておけば、利用者の環境に peg-runtime を入れなくても、`ghc` だけでコンパイルできる。

## 実装すること

### コマンド

```sh
peg-hs parse GRAMMAR.peg INPUT [--format ast|cst|all] [--entry RULE] [--ghc-arg ARG]...
```

- `--format` の既定は `ast` とする
  - `ast`：開始規則（`--entry` があればその規則）の値を表示する
  - `cst`：構文木を表示する
  - `all`：AST と CST を、見出しを付けて続けて表示する
- `--entry RULE` は、開始規則の代わりに使う規則を選ぶ。`%entry` に挙げた規則に限る
- 入力を解析できなければ、解析の失敗（`renderParseError` の文言）を標準エラー出力に書いて失敗する
- 文法の誤りと静的検査の誤りは、生成のコマンドと同じ形で報告して失敗する

### 表示の形

- **AST**：値を `Show` で文字列にし、括弧とレコードの構造に沿って字下げして表示する。字下げの整形は、`show` の出力を字句に分けて組み直す小さな整形器で行う（再実装の方針。pretty-simple などに依存しない）
- **CST**：`debugTree nameOfSyntaxKind`（[ADR 0019](0019-lossless-syntax-tree.md)）の形で表示する。各行に種類、範囲、トークンならその文字列を書く

### 実行の仕組み

- peg-hs は、文法から生成したモジュールと、入力を読んで結果を表示する主モジュールを、一時ディレクトリに書き出す
- CST を表示するために、文法に `%syntax` がなくても、`%syntax` を加えた文法から生成する。`%token` と `%trivia` は文法に書いたとおりとする。型付きの値の入口と構文木の入口の両方を使う
- peg-runtime のソースを peg-hs に含めておき、一時ディレクトリに書き出す。含めるソースは、再生成のスクリプトが peg-runtime から写し、テストが peg-runtime のソースとの一致を検査する
- `PATH` の `ghc` でコンパイルして実行する。`--ghc-arg` で渡した引数を `ghc` に加える。文法の verbatim ブロックが利用者のモジュールを import する場合は、`--ghc-arg -isrc` のように探索のパスを渡す。cabal のプロジェクトのパッケージを使う場合は、`cabal exec -- peg-hs parse ...` で実行すると、プロジェクトのパッケージの環境（`GHC_ENVIRONMENT`）が `ghc` に渡る
- コンパイルの結果をキャッシュする。鍵は、文法の内容、`--entry`、`--ghc-arg`、peg-hs の版、`ghc --numeric-version` の出力の組のハッシュとし、`$XDG_CACHE_HOME/peg-hs/parse/`（なければ `~/.cache/peg-hs/parse/`）に置く。同じ文法で入力だけを替える場合は、コンパイルを省く

### 制約と誤り

- AST の表示には、開始規則の型の `Show` のインスタンスが要る。インスタンスがない場合は、GHC の誤りを示したうえで、`--format cst` なら表示できることを伝える
- `%env` を宣言した文法は、入口が環境の値を必要とするので、扱わずに誤りとする
- `ghc` が見つからない場合と、GHC の版が peg-runtime の対応する版（base の範囲）の外の場合は、その旨を報告して失敗する

## 実装しないこと

- 文法の解釈による解析（GHC を使わない方式）。アクション、意味述語、引数を評価できないため
- 回復するモード（[ADR 0021](0021-error-recovery.md)）の結果の表示。必要になったら `--recover` を加える ADR を起こす
- `%env` の文法への環境の値の受け渡し
- 標準入力からの入力の読み込み、複数の入力ファイル、入力の一部（範囲）の解析
- JSON などの機械向けの出力の形式

## テスト設計

- **表示**：小さな文法と入力について、`ast`、`cst`、`all` のそれぞれの出力を golden ファイルと比べる。既定が `ast` であること
- **`--entry`**：`%entry` の規則で解析できること。`%entry` にない規則を指定すると誤りになること
- **誤り**：解析できない入力で失敗し、`renderParseError` の文言を出力すること。`Show` のインスタンスのない型で、`--format cst` を勧める誤りになること。`%env` の文法を誤りとすること
- **`%syntax` のない文法**：`%syntax` を書いていない文法でも `cst` を表示できること
- **利用者のモジュール**：verbatim ブロックが別のモジュールを import する文法を、`--ghc-arg -i...` で解析できること
- **キャッシュ**：同じ文法での二回目の実行が `ghc` を呼ばないこと。文法を変えるとコンパイルし直すこと
- **含めた peg-runtime のソース**：peg-hs に含めたソースが、peg-runtime のソースと一致すること
- **整形器**：`show` の出力の字下げの整形が、字句を変えず（空白を除いて元の文字列と一致する）、入れ子に沿って字下げすること（プロパティテスト）
- テストは CI の Haskell のジョブで動かす。ジョブには `ghc` がある

## 実装の段階

CLI のサブコマンドの構成（`fmt`、`lint`、`lsp`）がそろった後に、`parse` を同じ形で加える。

## トレードオフ

- 初回の実行は GHC のコンパイルを待つ（数秒）。入力だけを替える二回目以降はキャッシュで速い
- 利用者の環境に `ghc` が要る。peg-hs で生成したモジュールを使う利用者は GHC を持っているので、制約は小さいと見込む
- peg-runtime のソースを実行ファイルに含めるので、peg-runtime を変えるたびに含めたソースも再生成する必要がある。再生成のスクリプトと一致の検査がこれを保証する
- AST の表示は `Show` のインスタンスに頼るので、利用者が `Show` を独自に定義した型は、その定義のとおりに表示される
