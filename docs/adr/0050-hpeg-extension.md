# ADR 0050: 文法ファイルの拡張子を .hpeg にする

ステータス: 採択

## 文脈

peg-hs の文法ファイルは、拡張子 `.peg` を使ってきた（[ADR 0004](0004-peg-notation.md)）。
この拡張子は、ほかの PEG の道具も使っている。
C の peg/leg（Ian Piumarta）と、Go の pointlander/peg は、文法ファイルに `.peg` を使う。
ほかにも、PEG の文法を `.peg` という名前で置く道具は多い。
記法はどれも別物で、互換はない。

拡張子が重なると、次のことが起きる。

- **エディタ**：VS Code、Neovim、Helix は、拡張子から言語を決める。ほかの道具の拡張機能が同じ `.peg` を受け持つと、どちらの文法でハイライトするかが入れ替わり、言語サーバーも取り違える
- **GitHub の言語判定**：GitHub Linguist が `.peg` を別の言語と判定すると、リポジトリの言語の統計と、ファイルの表示のハイライトが誤る
- **ファイルの探索**：`peg-hs fmt` と `peg-hs lint` は、引数がなければ現在のディレクトリの下の `.peg` ファイルをすべて扱う（[ADR 0032](0032-grammar-formatter.md)、[ADR 0033](0033-grammar-linter.md)）。同じリポジトリにほかの道具の `.peg` があると、それを peg-hs の文法として読んで誤りを報告する

言語の識別子も同じ問題を持つ。
VS Code の拡張機能、tree-sitter の文法、TextMate の文法は、言語の名前を `peg`、スコープを `source.peg` としている（[ADR 0034](0034-syntax-highlighting.md)）。
ほかの PEG の拡張機能が同じ名前を使うと、設定や問い合わせが衝突する。

拡張子を変えるのは、利用者が少ないうちがよい。
いまの利用者は Golem だけで、文法はリポジトリの中の 39 個と Golem の数個である。
v1 では記法と道具の互換を保つ約束をするので、変えるなら v1 より前に行う。

新しい拡張子は `.hpeg` とする。
「Haskell の PEG」を表し、知られている道具とは重ならない。

## 実装すること

### 拡張子

- 文法ファイルの拡張子を `.hpeg` とする
- `peg-hs fmt` と `peg-hs lint` が、引数がない場合と、ディレクトリを渡された場合に探すのは、`.hpeg` のファイルだけとする。`.peg` のファイルは探さない。ほかの道具の文法を誤って読まないためである
- ファイルを直接渡した場合は、拡張子を見ない。`peg-hs gen Grammar.peg` のように `.peg` のファイルも、これまでどおり扱う。移行の途中の利用者が困らないためである
- `peg-hs gen` の出力の既定のパスは、これまでどおり、文法のパスの拡張子を `.hs` に替えたものとする
- `peg-hs Grammar.hpeg` のように、コマンドを書かずに文法のファイルを渡したときの案内（[ADR 0037](0037-cli-subcommands.md)）は、`.hpeg` と `.peg` のどちらでも出す

### 言語の識別子

- VS Code の拡張機能の言語の id、tree-sitter の文法の名前とスコープ、TextMate の文法のスコープを `hpeg`（スコープは `source.hpeg`）にする
- tree-sitter の文法のディレクトリを `editors/tree-sitter-hpeg` に改める。生成されるパーサーの関数の名前も `tree_sitter_hpeg` になる
- VS Code の拡張機能、tree-sitter、TextMate、Helix と Neovim の設定の例の、受け持つ拡張子を `.hpeg` にする
- 言語サーバーは拡張子を見ないので、変えない

### リポジトリの文法

- リポジトリの 39 個の `.peg` のファイルを `.hpeg` に改める。生成したモジュールは文法のパスを記録するので、すべて生成し直す（[ADR 0046](0046-docs-cli-and-ci-before-v0-1-0.md)）
- 文法を読むスクリプトとテスト（`scripts/regen-fixtures.sh`、各パッケージのテストの文法の探索、`editors/test/`、適合性のテスト、ベンチマーク）のパスと拡張子を改める
- `.cabal` の `extra-source-files` のパターンを改める

### 文書

- README、CONTRIBUTING、docs/specifications.md、docs/syntax.md の拡張子と言語の名前を改める。syntax.md の題を「.hpeg 記法」とし、冒頭の「反映している ADR」に本 ADR を加える
- 書き換えられる文書（README、CONTRIBUTING、docs/specifications.md、docs/syntax.md）のコードブロックの言語の印を `peg` から `hpeg` に改める。コミット済みの ADR は変えない。文書の完全な文法の例を取り出すテスト（[ADR 0046](0046-docs-cli-and-ci-before-v0-1-0.md)）は、言語の印ではなく `%module` で始まることで例を見分けるので、影響しない
- CHANGELOG の「Changed」に、拡張子と言語の識別子の変更と、移行の手順を書く
- 移行の手順として、`git mv` で拡張子を改めること、エディタの設定の言語の名前を改めること、生成し直すことを README に書く
- docs/specifications.md の未決事項から、この項目を除く

## 実装しないこと

- 記法の名前（「.peg 記法」の呼び方を除く）、パッケージの名前（`peg-runtime` など）、コマンドの名前（`peg-hs`）の変更。どれも拡張子の重なりとは関係がなく、変えると Hackage の名前と利用者のビルドの設定が変わる
- `.peg` を探索の対象に残すこと、または探索で `.peg` を見つけたときの警告。ほかの道具の `.peg` を誤って読むことを防ぐのが目的なので、探索からは外す
- `.peg` を渡されたときの非推奨の警告。直接渡されたファイルは利用者の意図であり、拡張子で扱いを変えない
- GitHub Linguist への `.hpeg` の登録の申請。[ADR 0034](0034-syntax-highlighting.md) と同じく行わない

## テスト設計

先に書き、失敗させてから実装する。

- **探索**：`fmt` と `lint` の探索のテストで、`.hpeg` のファイルを扱い、`.peg` のファイルを扱わないこと。ディレクトリを渡した場合も同じであること
- **直接渡したファイル**：`gen`、`fmt`、`lint`、`parse` に `.peg` のファイルを直接渡すと、これまでどおり扱うこと
- **コマンドのない文法の案内**：`peg-hs Grammar.hpeg` と `peg-hs Grammar.peg` のどちらも、`peg-hs gen` を案内する使い方の誤りになること
- **リポジトリの文法**：生成物の一致のテストが、改めたパスで通ること。リポジトリに `.peg` のファイルが残っていないこと（テストで確かめる）
- **エディタ**：tree-sitter のコーパスとハイライトのテスト、TextMate のスナップショット、三つの文法の範囲の一致のテスト（[ADR 0034](0034-syntax-highlighting.md)）が、改めた名前とパスで通ること。VS Code の拡張機能の `package.json` が `.hpeg` を受け持ち、言語の id が `hpeg` であることをテストで確かめる
- **Neovim の設定の例**：README の新しい設定の例で、Neovim が `.hpeg` のファイルを開いてハイライトすることを、実際に動かして確かめる

## トレードオフ

- Golem の文法と設定も改める必要がある。Golem は peg-hs の版を上げるときに、ファイルの名前とエディタの設定を改める
- 生成したモジュールがすべて変わるので、差分が大きくなる。拡張子の変更だけのコミットに分けて、レビューしやすくする
- 言語の識別子を変えるので、利用者のエディタの設定（`filetype`、`languages.toml` など）も改める必要がある。拡張子だけを変えて識別子を `peg` のまま残す案もあるが、衝突の原因の半分が残るので採らない
- `.peg` を直接渡せば扱うので、拡張子を改めない利用者もしばらくは使える。ただし `fmt` と `lint` の探索からは外れる
