# ADR 0005: エラー報告は最遠位置と期待集合、ラベル構文は予約のみ

ステータス: 採択→ラベルの意味論は [ADR 0021](0021-error-recovery.md)

## 文脈

失敗の表現がラベル付き失敗（Maidl et al. 2016）の型を持つことは仕様書で決めたが、二つの決定が残っていた。
利用者が文法中にラベルを書く構文をいつ確定するかと、v1 の farthest failure が何を報告するかである。

ラベルの意味論（送出、回復、メッセージへの対応付け）は、実装経験なしに固めると外しやすい。
一方、記法は [ADR 0004](0004-peg-notation.md) で確定済みであり、将来の演算子追加が記法の再設計（結合の強さの表の改訂）にならないよう、席だけは今確保しておきたい。
Golem がマクロ構文 `[!` で採った「予約のみ行い、実装しない」パターンをここでも使う。

報告内容には規則トレース（どの規則の途中で失敗したか）という選択肢もあるが、パックラットと構造的に相性が悪い。
メモ表にヒットした評価では呼び出しスタックが再現されないため、トレースが実際の解析過程と食い違う。
期待集合はメモエントリに載せられるため、この問題を持たない。

## 実装すること

### `^label` の予約

- 記法に後置の `^label`（`label` は小文字識別子）を追加する。結合は接尾辞（`*` `+` `?`）より弱く、接頭辞（`&` `!` `$`）より強い
- peg-grammar は `^label` を受理して文法 AST に保持する
- peg-codegen は `^label` に遭遇したら「未実装」のエラーで停止する。黙って無視しない

### v1 の失敗報告

- 失敗値は最遠到達位置（バイトオフセットと行・桁）と、その位置の**期待集合**を持つ
- 期待集合の要素は終端の記述（リテラルの原文、文字クラスの原文、任意の一文字）とする
- より遠い位置の失敗は既存の失敗を置き換え、同じ位置の失敗は期待集合を合併する
- メモエントリは失敗情報を含めて記録し、メモ表へのヒットの有無が報告内容を変えないようにする

## 実装しないこと

- ラベルの意味論（送出・回復・メッセージ対応表）はこの ADR では定めない。実装経験を得てから後続 ADR で確定する
- 規則トレースは実装しない。上記の構造問題のためであり、将来も採らない
- 否定先読み `!e` の失敗は期待集合に項目を追加しない。「そこに何が来てはならなかったか」を期待の語彙で表せないためで、`!e` だけで失敗した位置の報告は位置のみに縮退する
- 規則名を人間向けの名前で表示する仕組み（PEG.js の human-readable name に相当）は、ラベル意味論の ADR と合わせて将来検討する

## テスト設計

- **予約の検証**：`^label` を含む文法が peg-grammar を通過して AST に残り、peg-codegen が未実装エラーで停止すること
- **期待集合の合併**：同じ最遠位置で複数の選択肢が失敗する文法で、期待集合が合併されること（`expected '+' or [0-9]` の形）
- **メモ化との整合**：同一の文法と入力に対し、メモ化の有無（テスト用に無効化した評価器との比較）で失敗報告が変わらないこと
- **位置の正確さ**：複数行入力での行・桁と、マルチバイト文字を跨いだバイトオフセットの整合

## トレードオフ

- 期待集合の粒度は終端レベルであり、「式が来るはず」のような規則レベルの説明はできない。規則レベルの命名はラベル意味論の確定に委ねた
- `!e` 由来の失敗の説明力は弱い。禁則的な文法（コメントの閉じ忘れ等）のエラーメッセージ品質は、将来のラベルで補う前提である
- `^` を演算子として確保したため、この文字をリテラル外の他の用途に使えない
