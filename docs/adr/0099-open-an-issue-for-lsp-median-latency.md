# ADR 0099: 編集応答時間の中央値が 16 ms を超えたら CI から issue を立てる

ステータス: 採択

## 文脈

[ADR 0071](0071-incremental-parsing-in-the-language-server.md) は、Golem 規模の文法を編集したときの応答時間に 16 ms の目安を置いた。
[ADR 0098](0098-measure-pr-86-lsp-latency-in-ci.md) で測った PR #86 のヘッドでは、12 件の平均時間の最大は 14.2744 ms だった。
今後は main の編集応答時間を継続して測り、目安を超えた操作を issue で追う。

## 調査した事項

既存の CI の `lsp-latency` は PR 番号 86 に限って起動する。
`scripts/lsp-latency.mjs` は Criterion の JSON の `reportAnalysis.anMean.estPoint` を読み、操作ごとの平均を判定する。
Criterion 1.6 の実出力には、各標本の値を並べた `reportMeasured` と各列の名前を並べた `reportKeys` があり、経過秒数 `time` と反復数 `iters` を取り出せる。

## 実装すること

main への push で、ベンチマークの実行ファイル、入力文法、計測スクリプト、依存関係、ツールチェーン、または監視ワークフローに影響する変更を検出したとき、そのコミットを GitHub Actions で測る。
監視ワークフローは各 push の差分でこの判定を行う。
既存 CI が使う拡張子とディレクトリによる文書判定は流用しない。
対象は [ADR 0098](0098-measure-pr-86-lsp-latency-in-ci.md) と同じ Memo と Golem の 2 文法、先頭、中ほど、末尾の 3 か所、診断までと診断に続いて semantic tokens を返すまでの 2 操作とする。
Golem の入力の版、GHC、最適化、RTS の設定も [ADR 0098](0098-measure-pr-86-lsp-latency-in-ci.md) の計測条件を引き継ぐ。

中央値はケースごとに求める。
各標本の経過秒数をその標本の反復数で割り、得た値を昇順に並べる。
標本数が奇数なら中央の一つ、偶数なら中央の二つの算術平均を取る。
判定には表示用に丸める前の秒数を使う。

12 件の結果と、対象コミット、入力の版、ランナー、GHC、計測オプションをジョブサマリーに残す。
中央値が 0.016 秒を超えたケースが一つでもあれば、そのケースと中央値、コミット、実行へのリンクを一件の issue にまとめる。
この監視用の issue が開いていれば、同じ issue に新しい超過を追記する。
通知処理だけに issue の書き込み権限を付ける。
通知処理は直列に実行し、同じコミットの同じ実行を再試行したときは記録を重複させない。
一度の超過で通知し、ランナー間の揺れを含む観測値として扱う。

## 実装しないこと

16 ms の超過を理由に PR のマージを止めることや、平常値に戻ったときに開いている issue を自動で閉じることは対象外とする。

## 不変条件

1. 12 件の各ケースが一つずつあり、各ケースに一つ以上の標本があり、各経過時間が有限の正の数、各反復数が正の整数であるときに判定する。欠測や不正な入力は計測エラーとしてジョブを失敗させる。
2. 判定できた実行で、中央値が 0.016 秒を超えたケースの集合が空なら通知しない。空でなければ、その集合の全ケースを通知する。
3. 通知を完了した一つの実行について、監視用 issue に残るその実行の記録は一つである。

| 境界（ほかのケースは 16 ms 以内） | 期待する結果 | 番号 |
| --- | --- | --- |
| 一件欠測、標本が空、反復数が 0 | 計測エラー。性能超過の issue を作らない | 1 |
| 一ケースの標本が 32 ms / 2 回だけ | 中央値 16 ms。通知なし | 1, 2 |
| 1 回あたり 15、16、40 ms | 中央値 16 ms。通知なし | 2 |
| 1 回あたり 15、17.002 ms | 中央値 16.001 ms。このケースを通知 | 2 |
| 二つのケースが同じ実行で超過 | 一つの記録に両方を含める | 2, 3 |
| 記録済みの実行を再試行 | 同じ記録は一つ | 3 |

## テスト設計

不変条件の番号を付け、表の標本から中央値と通知対象を検査する。
Criterion の JSON の列順を変え、名前から必要な列を取り出せることも検査する。
issue の作成、既存 issue への追記、再試行、API エラーを模したテストを行う。
通知に失敗した場合はジョブを失敗させ、再試行で記録を完了できるようにする。

## トレードオフ

ランナーによる揺れで超過を通知することがある。
計測結果には環境と実行へのリンクを添え、コードの変更が原因かどうかは issue で調べる。
中央値をケースごとに取るので、軽い操作の標本が重い操作の超過を隠すことはない。
