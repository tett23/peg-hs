# ADR 0053: 大文字のない文字で始まる規則名から、%syntax の型名を作る

ステータス: 採択

## 文脈

規則名と束縛には、Unicode の文字を使える（[ADR 0020](0020-unicode-identifiers-self-hosted.md)）。
`数式` や `_項` のような規則名も、`%syntax` のない文法なら生成して使える。

`%syntax` の文法では、生成器が規則ごとに構文木の型（[ADR 0019](0019-lossless-syntax-tree.md)）を作る。
型名は、規則名の先頭の文字を大文字にして `Syntax` を付けたものである（`expr` から `ExprSyntax`）。
漢字、仮名、`_` には大文字がないので、`数式` からは `数式Syntax` という名前ができる。
Haskell の型名は大文字で始まらなければならないので、生成したモジュールのコンパイルが GHC の誤りになる。

```text
Example/Japanese.hs:10:5: error: [GHC-18208]
    Expecting a type constructor but found a variable, ‘数式Syntax’.
```

`peg-hs parse` は、構文木を表示するために、`%syntax` を書いていない文法でも `%syntax` を有効にして生成する（[ADR 0036](0036-parse-command.md)）。
そのため、`%syntax` を書いていない文法でも、こうした規則名があれば `parse` が失敗する。
docs/syntax.md の例 `Example.Japanese` がこれに当たる。

同じ型名の作り方には、もう一つの穴がある。
`expr` と `Expr` の二つの規則があると、どちらも `ExprSyntax` になり、型名が重なる。
これも、生成器は検出せず、GHC の誤りになる。

規則名から作るほかの名前（`syntaxKind数式`、取り出し関数の `数式右` など）は、小文字で始まる名前の位置に置かれる。
GHC は、大文字のない文字を小文字として扱うので、これらは正しい名前である。
問題は、大文字で始まらなければならない型名と構成子の名前だけにある。

## 実装すること

### 型名の作り方

- 規則名の先頭の文字を大文字にした結果が大文字（`isUpper`）なら、これまでどおりその名前に `Syntax` を付ける（`expr` から `ExprSyntax`、`Expr` から `ExprSyntax`）
- 大文字にできない場合（漢字、仮名、`_` などで始まる規則名）は、規則名の前に `Rule'` を付け、後ろに `Syntax` を付ける（`数式` から `Rule'数式Syntax`、`_項` から `Rule'_項Syntax`）。`'` は Haskell の型名の二文字目以降に使える
- 型名から作る名前（`cast数式Syntax` など）は、作った型名に従う（`castRule'数式Syntax`）
- 構成子の名前は、これまでどおり型名と同じにする

### 型名の衝突

- `%syntax` の文法で、二つの規則が同じ型名になる場合は、静的検査の誤りにする。文言は「the rules expr and Expr have the same type name ExprSyntax in the syntax tree; rename one of them」とし、後に定義した規則の位置で報告する
- `Rule'` を付けた名前と、もともと `Rule'` で始まる規則名の衝突（`数式` と `Rule'数式`）も、同じ誤りになる

### peg-hs parse

- 型名の作り方を直せば、`parse` は大文字のない文字で始まる規則名の文法も扱える。`parse` が `%syntax` を有効にして生成する作りは変えない
- 型名が衝突する文法では、`parse` も上の誤りを報告する。`%syntax` を書いていない文法でも、`parse` は `%syntax` を有効にするので、`expr` と `Expr` を持つ文法は `parse` で扱えない。この制限を `peg-hs help parse` と README の既知の制限に書く

### 文書

- docs/syntax.md の `%syntax` の節に、型名の作り方と衝突の誤りを書く。冒頭の「反映している ADR」に本 ADR を加える
- README の既知の制限と、docs/specifications.md の未決事項から、漢字や仮名で始まる規則名の項目を除く

## 実装しないこと

- `%syntax` のない文法での型名の衝突の検査。型を作らないので衝突しない
- 型名を利用者が指定する指示（`%syntaxname` のようなもの）。名前の作り方を固定し、衝突は誤りにすれば足りる
- 取り出し関数の名前の衝突の検査。取り出し関数は「規則名＋束縛名」で作るので、型名の衝突と同じ組み合わせでしか衝突しない。型名の衝突を誤りにすれば起きない

## テスト設計

先に書き、失敗させてから実装する。

- **型名**：規則名から型名を作る関数の単体のテスト。`expr`、`Expr`、`数式`、`_項`、`Ä`（大文字にできる ASCII 以外の文字）、`ǅ`（タイトルケースの文字）の結果を確かめる
- **生成とコンパイル**：漢字で始まる規則名と `_` で始まる規則名を含む `%syntax` の文法を codegen の fixture に加え、生成したモジュールが警告なしでコンパイルでき、構文木を取り出せること
- **衝突**：`expr` と `Expr` を持つ `%syntax` の文法、`数式` と `Rule'数式` を持つ `%syntax` の文法が、上の文言の誤りになること。`%syntax` のない同じ文法は誤りにならないこと
- **peg-hs parse**：docs/syntax.md の `Example.Japanese` の文法で、`peg-hs parse` が AST と CST を表示できること（peg-cli のテスト）
- **生成物**：リポジトリのすべての生成物が変わらないこと。リポジトリの文法の規則名は、どれも大文字にできる文字で始まるためである

## トレードオフ

- `Rule'` を付けた型名は、利用者のコードから書くときに長い。大文字のない文字で始まる規則名を使う利用者は少ないと見込み、確実に正しい名前になることを優先する
- 型名の衝突を誤りにするので、これまで `%syntax` なしで生成できていた文法が、`peg-hs parse` で扱えなくなる場合がある。もともと `parse` は GHC の誤りで失敗していたので、誤りの文言が分かりやすくなるだけである
