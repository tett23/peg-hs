# ADR 0011: CommonMark パーサーを生成し、表現力の限界を測る

ステータス: 採択

## 文脈

JSON（ADR 0010）は、生成器が実用文法を端から端まで処理できることを確かめる。
しかし JSON は文脈自由で行の概念を持たず、PEG にとって易しい部類の言語である。
peg-hs の最初の利用者である Golem の記法は、ブロック層に行指向の構文（見出し、リスト、定義リスト）を持つ。
行頭や字下げの扱いで PEG の表現力が足りなくなるなら、Golem の実装に入る前に知っておきたい。

CommonMark は、この種の難しさを網羅的に含む言語であり、652 件の例（仕様 0.31.2）で正解が与えられている。
ただし、v1 の peg-hs（ADR 0004 の記法、純粋なアクション、状態も引数も持たない規則）で CommonMark に完全適合できる見込みは低い。
仕様を読む限り、少なくとも次の四つが PEG の外側にある。

- **字下げの状態**：リスト項目の継続行に要る字下げ幅は、項目の開始記号の幅で決まる。入れ子のコンテナ（引用とリスト項目）では、各行がコンテナの接頭辞の列全体に照合し直される。幅と入れ子の深さに上限がないため、固定の規則では書けない。遅延継続行（lazy continuation line）はこれをさらに複雑にする
- **前方参照**：`[foo]` がリンクになるかは、文書のどこか（後方を含む）に `[foo]: /url` の定義があるかで決まる。リンクになるかどうかは、角括弧と強調の結合の優先にも影響するため、解析後の変換だけでは復元しきれない
- **タブの桁**：タブはブロック構造の判定において 4 桁ごとのタブ位置まで空白に展開されたものとして扱われる。照合の判断に桁位置が要る
- **後読み**：強調の区切り記号の扱い（left-flanking / right-flanking）は、記号の直前の文字に依存する。ただしこれは、仕様自身が区切り記号の列に対する後処理のアルゴリズムとして定めており、その形に従えば PEG の外に出さずに済む見込みがある

したがって本 ADR は、CommonMark への適合を目標にしない。
適合率を測り、失敗の原因を分類し、記法の拡張（意味述語、引数付き規則、利用者状態など）を検討する後続 ADR の根拠資料を作ることを目的とする。

## 前提

- ADR 0010 が完了していること（`peg-conformance` パッケージと生成物の扱いを流用する）

## 実装すること

### 構成の制約

測定の意味を保つため、入力の照合はすべて生成パーサーが行う。

- ブロック構造の文法と、インラインの文法を、別々の `.peg` として書いてよい。葉ブロックの生テキストをインラインのパーサーに渡す二段構成は、仕様の構造に沿ったものとして認める
- 解析後の AST に対する純粋な変換は認める。強調の区切り記号の処理（仕様の process emphasis の手順）はこの形で実装する
- 入力文字列を手書きのコードで走査、加工、分割すること（行単位の前処理、字下げの正規化、タブの展開など）は認めない
- 構成の制約の外に出なければ通せない例は、失敗として記録する

### 文法の範囲

- 仕様の全節について文法を書く。難しい節を黙って飛ばさない。書けなかった構文は、その旨と理由を失敗分類に記録する
- HTML の文字参照の表は、WHATWG の `entities.json`（CC BY 4.0）を取り込み、出典を併記する
- Unicode の句読点と空白の分類は GHC の `Data.Char.generalCategory` を使う

### 判定

- HTML の出力は `peg-conformance` 内に手書きする。比較は、仕様の例の HTML との完全一致とする（仕様の `→` 記号はタブに戻してから比較する）。HTML の正規化は行わない
- 適合した例の番号を `conformance/commonmark/passing.txt` に記録する。テストは、記録された例が一つでも失敗したら失敗し、記録にない例が新たに通った場合も失敗する。後者は記録の更新を強制し、記録を常に実態と一致させるためである
- 節ごとの適合率と、失敗の原因分類（上記の四分類と、それ以外の原因）を、スナップショットとして `docs/conformance/commonmark/` に置く。スナップショットはコミット後に変更しない。記録は、本 ADR の完了時と、記法を拡張する ADR の実装時に追加する

### テストデータ

- 仕様 0.31.2 の `spec.txt` を `conformance/data/commonmark-spec-0.31.2/` に取り込み、ライセンス（CC-BY-SA 4.0）を同じディレクトリに置く
- 例の抽出（区切り行で囲まれた入力と期待出力の組）は Haskell で再実装する

## 完了条件

適合率を完了条件にしない。
次の四つがそろった時点で本 ADR を完了とする。

1. 仕様の全節について、文法を書いたか、書けない理由を記録したこと
2. 652 件すべてを実行する判定の仕組みと、`passing.txt` による退行検出が動くこと
3. 失敗のすべてが原因分類のどれかに割り当てられていること
4. 初回のスナップショットを `docs/conformance/commonmark/` に置いたこと

## 実装しないこと

- 適合率の目標値は置かない
- GFM の拡張（表、取り消し線、タスクリスト）
- ソース位置の出力（`data-sourcepos`）
- 既存の Markdown 処理系（cmark、commonmark-hs）との出力比較や性能比較
- 記法の拡張そのもの。本 ADR は v1 の記法での測定までとし、拡張は ADR 0012 で扱う。ADR 0012 の実装後に二回目のスナップショットを記録し、拡張の効果を適合率の差として残す

## テスト設計

- **適合性**：上記「判定」の `passing.txt` による双方向の検査
- **例の抽出**：抽出した例が 652 件であること、各例の番号と仕様上の節名が対応していること
- **決定性**：ブロックとインラインの両文法について、再生成した生成物がコミット済みのものとバイト単位で一致すること（ADR 0010 と同じ）
- **後処理の単体テスト**：強調の区切り記号の処理を、仕様の該当節の例から切り出した区切り記号の列に対して単体で検査する

## トレードオフ

- 失敗の大半は、上記の四分類のうち字下げの状態と前方参照に集中すると予想している。ここを通すために考えられる拡張（引数付き規則、利用者状態、意味述語）は、いずれもパックラットのメモ表の鍵を「規則と位置」から「規則と位置と状態」へ広げることを要求し、メモ化の効率と ADR 0001 の成長ループの前提（同じ規則と位置の評価は同じ結果を返す）に触れる。拡張は、この衝突を避ける形で ADR 0012 が設計する
- HTML を正規化せずに比較するため、空白や属性の順序といった描画の些事でも失敗になる。出力の形式を仕様の例に合わせることで抑えるが、失敗分類では描画由来の失敗を独立の分類として区別する
- GHC が持つ Unicode のデータの版と、仕様が想定する版がずれると、句読点の判定が一部の例で食い違う可能性がある
- 仕様本文は CC-BY-SA 4.0 であり、継承条項を持つ。取り込むのは公開しない `peg-conformance` に限り、MIT の公開パッケージには含めない
- JSON と同様、CommonMark の文法も左再帰を必要としない。左再帰の実用文法での検証は、本 ADR でも得られない
