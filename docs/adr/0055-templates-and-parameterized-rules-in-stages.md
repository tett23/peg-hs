# ADR 0055: 雛形と引数付き規則の組み合わせを段階に分けて入れる

ステータス: 採択→雛形の引数をそのまま別の雛形に渡すときの扱いは [ADR 0056](0056-label-insertion-and-template-deviations.md)

## 文脈

規則の雛形（[ADR 0031](0031-rule-templates.md)）は、引数付き規則（[ADR 0012](0012-context-sensitive-extensions.md)）と組み合わせられない。
[ADR 0040](0040-templates-with-parameterized-rules.md) は、この組み合わせを一度に入れる提案だった。
内容に誤りはなかったが、記法、展開、静的検査、整形、lint、tree-sitter と TextMate の文法、言語サーバーを同時に変える範囲の広さを理由に却下した。
仕様書の未決事項には、この組み合わせが残っている。

[ADR 0040](0040-templates-with-parameterized-rules.md) が挙げた使い道は二つある。

- **使い道 A**：雛形の引数が、呼び出し元の規則の値の引数を使う。`B(ind :: Int)` の中の `Lines<Item(ind)>` である。いまは生成はできるが、展開した規則 `Lines'0` には `ind` がなく、GHC が `Variable not in scope: ind` で失敗する
- **使い道 B**：雛形そのものが値の引数を持つ。`Indented<p>(n :: Int)` のように、本体の中で字下げの深さ `n` を使う雛形である。いまは「the template Indented cannot take parameters」で拒否される

Golem の文法（`modules/golem-parser/grammar/Golem.hpeg`）では、「空行を挟んで同じものが続く」形が、字下げの深さを変えて何度も現れる。

```
Blocks <- Block(ind) (BlankLines? &(Ind(ind) !BlankLine .) Block(ind))* { () }
BulletList <- ListItem(ind, 0) (BlankLines? ListItem(ind, 0))* { () }
OrderedList <- ListItem(ind, 1) (BlankLines? ListItem(ind, 1))* { () }
DefList <- DefGroup(ind) (BlankLines? &(Ind(ind) '=' [ \t]) DefGroup(ind))* { () }
DefBody <- &(Ind(ind + 2) ![ \t] !BlankLine .) Block(ind + 2) (BlankLines? &(Ind(ind + 2) ![ \t] !BlankLine .) Block(ind + 2))* { () }
```

一見すると、この五つをまとめるには使い道 A と B の両方が要る。
要素（`ListItem(ind, 0)`）は呼び出し元の `ind` を使い、続きの判定（`&(Ind(ind) …)`）は字下げの深さを値として使うからである。

ところが、続きの判定も式である。
雛形の引数には、先読みを含む任意の式を渡せる（[ADR 0031](0031-rule-templates.md)）。
判定を引数として渡せば、値の引数を持つ雛形がなくても五つの形を書ける。

```
Run<p, more> :: ()
Run<p, more> <- p (BlankLines? more p)* { () }

Blocks <- Run<Block(ind), &(Ind(ind) !BlankLine .)>
BulletList <- Run<ListItem(ind, 0), &.>
DefList <- Run<DefGroup(ind), &(Ind(ind) '=' [ \t])>
DefBody <- &(Ind(ind + 2) ![ \t] !BlankLine .) Run<Block(ind + 2), &(Ind(ind + 2) ![ \t] !BlankLine .)>
```

これが動かない理由は、使い道 A だけである。
判定の式も呼び出し元の `ind` を使うので、展開した規則から `ind` が見えない。
使い道 B が減らすのは、`DefBody` のように同じ判定を呼び出しごとに書く手間であり、書けるかどうかではない。

この非対称は、変更の範囲にもそのまま現れる。
使い道 A の呼び出し `Lines<Item(ind)>` は、いまの記法ですでに書ける。
自己記述の文法（`grammar/Peg.hpeg`）も、tree-sitter の文法も、この形を雛形の呼び出しとして読む。
直すべきは展開の結果だけで、整形、lint、ハイライト、言語サーバーは展開の前の文法を読むので、触らずに済む。
使い道 B は、値の引数を渡す呼び出し `Name<args>(vals)` を記法に加えなければ書けない。
型注釈の側（`Indented<p>(n :: Int) :: ()`）は、自己記述の文法の `Declaration` も tree-sitter の文法もすでに受け付けており、展開が「cannot take parameters」で拒否しているだけである。

そこで、変更を三つの段階に分ける。
段階 1 は記法を変えずに使い道 A を解く。
段階 2 は呼び出しの記法だけを、記法を読むすべての道具に入れる。
段階 3 は値の引数の意味を入れ、使い道 B を解く。
それぞれの段階は、単独で採択、実装、リリースできる。
段階 1 だけでも Golem の五つの形は書ける。
しかし peg-hs は Golem に依存しない汎用のライブラリなので、雛形が自分の値の引数を持つ使い方（使い道 B）も支える。
三つの段階はすべて入れる。
段階に分けるのは、入れるかどうかを後で決めるためではなく、変更の範囲を段階ごとに閉じて確かめるためである。

本 ADR の採択は、[ADR 0040](0040-templates-with-parameterized-rules.md) の採択を意味しない。
[ADR 0040](0040-templates-with-parameterized-rules.md) は却下のままとし、その設計（取り込む引数の判定、展開の鍵、引数の並び、誤りの扱い）のうち、各段階に必要なものを本 ADR で改めて定める。
文言や規則が [ADR 0040](0040-templates-with-parameterized-rules.md) と違う箇所は、本 ADR に従う。

### 段階の進め方

本 ADR は三つの段階を一つの ADR に書き、三つをまとめて採択する。
実装は段階 1、2、3 の順に行い、段階ごとに一つの pull request にする。
各段階の終わりで、すべてのテストが通り、リリースできる状態にする。
段階の中身を変えたくなったときは、新しい ADR を作る。

## 実装すること

### 段階 1：呼び出し元の引数を取り込む

記法は変えない。
雛形の引数が呼び出し元の規則の引数を使うとき、展開した規則がその引数を受け取る。

```
B(ind :: Int) :: ()
B <- Lines<Item(ind)> { () }
```

は、次のように展開する。

```
B <- Lines'0(ind) { () }

Lines'0(ind :: Int) :: ()
Lines'0 <- Item(ind) ('\n' Item(ind))* { () }
```

#### 取り込む名前の判定

- 雛形の引数の中の Haskell の断片（規則の呼び出しの引数と、意味述語の式）を字句に分け、呼び出し元の規則の引数の名前と一致する識別子を取り込む。雛形の引数の中の雛形の呼び出しは先に展開されるので、その呼び出しの引数も断片として数える
- 字句の分け方は、修飾名（`M.ind`）を一つの字句とし、文字列と文字のリテラルの中を数えない。修飾名の `ind` は呼び出し元の引数ではないからである
- 予約束縛（`_env`、`_col`、`_span`）は取り込まない。`_env` はどこでも同じ値であり、`_col` は評価の位置の桁なので、展開した規則の中で評価しても値が変わらない
- 取り込んだ引数の型は、呼び出し元の型注釈に書いた型とする
- 展開した規則の引数の並びは、取り込んだ引数を名前の順に並べたものとする。呼び出しは、同じ順に同じ名前を渡す普通の規則の呼び出しに置き換える
- 展開の鍵（いまは雛形の名前と、位置を除いた引数の組）に、取り込んだ引数の名前と型の組を加える。別の規則から同じ字句の引数で呼んでも、取り込んだ引数の型が同じなら同じ展開した規則を使い、型が違えば別の規則にする

#### 雛形が雛形を呼ぶ場合

雛形の本体が雛形を呼ぶとき、内側の呼び出しの「呼び出し元の規則」は外側の展開した規則である。
外側の展開した規則が取り込んだ引数は、内側の雛形の引数からも取り込める。
展開の実装では、保留中の展開した規則を本体ごと展開するとき（`drain`）、その規則の引数を呼び出し元の引数として渡す。

#### 誤り

- 雛形の引数が、呼び出し元の選択肢の束縛を使う場合は誤りにする。束縛の型は、束縛した式から推論しないと分からないからである。文言は「the argument of the template T uses the binding x, which a template cannot take」とする。いまは GHC の `Variable not in scope` になる文法が、生成器の誤りになる
- 取り込む名前が、雛形の本体の束縛またはコードの識別子と同じ場合は誤りにする。雛形の引数は本体に埋め込まれるので、本体の束縛 `x:N` の後ろに置かれた引数の `x` は、呼び出し元の引数ではなく本体の束縛を指してしまう。文言は「the template T uses the name x in its body, so its argument cannot take the parameter x of the rule R; rename the parameter」とする
- 誤りの位置は、ほかの雛形の誤りと同じく、雛形の呼び出しの位置とする

#### 使われない取り込んだ引数

雛形が引数を本体で使わない場合（`T<p> <- 'x' { () }`）、取り込んだ引数は展開した規則の中で使われない。
生成コードの未使用の変数の警告を避けるため、展開した規則の本体のコードに現れない取り込んだ引数は、`_ind'` のように前に `_`、後ろに `'` を付けた名前で受ける。
後ろの `'` は、`env` や `col` という名前の引数が予約束縛 `_env`、`_col` と重ならないようにするためである。

#### 静的検査と他の機能

- 取り込んだ引数を持つ展開した規則は引数付き規則なので、引数付き規則の制約がそのまま掛かる。左再帰に加わると、引数付き規則の左再帰の誤り（[ADR 0012](0012-context-sensitive-extensions.md)）になる。誤りは展開した規則の定義の位置、つまり雛形の定義の位置で報告し、`templateNotes` が展開元の呼び出しを添える
- 取り込まない雛形の呼び出しは、これまでどおり引数を持たない規則に展開し、左再帰に加われる
- `%syntax` の文法では、展開した規則はこれまでどおり `%inline` として扱う
- ラベルの安全性の検査（[ADR 0028](0028-label-safety-check.md)、[ADR 0038](0038-label-check-precision-and-strip-labels-entries.md)）は展開した後の文法に対して行うので、引数付き規則の呼び出しの引数の置き換えがそのまま働く
- 自己記述の文法、AST、整形、lint、tree-sitter と TextMate の文法、言語サーバーは変えない。どれも展開の前の文法を読み、`Lines<Item(ind)>` はすでに読めるからである。言語サーバーの診断は展開と静的検査の結果を使うので、これまで GHC でしか分からなかった誤りが消え、上の新しい誤りが出るようになる

#### 文書

- [docs/syntax.md](../syntax.md) の雛形の節で、「雛形は、引数付き規則の引数を取れない」を、雛形の引数が呼び出し元の引数を使えることと、束縛を使えないことに書き換える。よくある誤りの表に、上の二つの誤りを加える。冒頭の「反映している ADR」に本 ADR を加える
- 仕様書の未決事項の「雛形と引数付き規則の組み合わせ」を、段階 1 で解けたことと、残る使い道 B に書き換える。README に雛形の制約の記述があれば、同じく直す
- [ADR 0031](0031-rule-templates.md) のステータスを「採択→雛形と引数付き規則の組み合わせは ADR 0055」に変える

### 段階 2：値の引数を渡す呼び出しの記法

段階 2 は記法だけを入れる。
値の引数の意味（展開）は段階 3 で入れるので、段階 2 の時点では、値の引数を渡す呼び出しはすべて誤りになる。
記法を読む道具を一つの段階で揃え、意味を入れる段階 3 では記法を読む道具に触れずに済むようにするためである。

#### 記法

- 雛形の呼び出しの `>` の直後に、引数付き規則の呼び出しと同じ値の引数（`(...)`）を書ける（`Indented<Block(ind + 2)>(ind + 2)`）
- `>` と `(` の間に空白を置かない。`Lines<p> (x)` は、これまでどおり雛形の呼び出しと括弧のグループの逐次として読む。引数付き規則の呼び出し（`Name(args)`）と同じ規則である
- 雛形の型注釈の値の引数（`Indented<p>(n :: Int) :: ()`）は、すでに読めるので変えない

これまで `T<a>(b)` と空白なしで書いた逐次は、段階 2 から値の引数を渡す呼び出しとして読む。
リポジトリの文法と Golem の文法には、この形がないことを確かめた。
整形（[ADR 0032](0032-grammar-formatter.md)）は逐次の要素の間に空白を置くので、整形済みの文法にもこの形は現れない。

#### 変える道具

- 自己記述の文法（`grammar/Peg.hpeg`）の `Primary` の雛形の呼び出しに、省略できる値の引数を加える。[ADR 0027](0027-switch-to-self-hosted-parser.md) の二回に分けた生成の手順に従う
- AST の `ETemplate` に値の引数（`[Located Text]`）を加える。`ETemplate` を調べる箇所（展開、静的検査、ラベルの検査、lint、整形、codegen）は、値の引数を持たない呼び出しについて、これまでと同じ結果を返すように合わせる
- 展開は、値の引数を渡す呼び出しを誤りにする。文言は「the template T takes no value arguments」とする。雛形の型注釈の値の引数は、これまでどおり「the template T cannot take parameters」で拒否する
- 整形は、値の引数を持つ雛形の呼び出しを、空白を入れずに書き出す
- ハイライト（[ADR 0034](0034-syntax-highlighting.md)）の範囲は無損失の構文木から作る。値の引数は引数付き規則の呼び出しと同じ `CallArgs` の節点になるので、同じ種類（Haskell の断片）の範囲になる
- tree-sitter の文法の `template_call` に、`token.immediate('(')` で始まる値の引数を加える。TextMate の文法の `template-call` も同じく加える
- 言語サーバー（[ADR 0035](0035-language-server.md)）の semantic tokens と定義への移動は、ハイライトと概要（`Outline`）から作るので、雛形の名前は値の引数があっても `macro` になる。動作は変えず、テストで確かめる

#### 文書

- [docs/syntax.md](../syntax.md) の雛形の節に、値の引数を渡す呼び出しの形と、`>` と `(` の間に空白を置けないことと、雛形がまだ値の引数を取れないことを書く。よくある誤りの表に「the template T takes no value arguments」を加える
- `T<a>(b)` の読み方が変わるので、リリースノートの「変更」に書く

### 段階 3：雛形の値の引数

段階 3 は、雛形が値の引数を持てるようにし、使い道 B を解く。
記法は段階 2 で揃っているので、記法を読む道具は変えない。

```
Indented<p>(n :: Int) :: ()
Indented<p> <- &(Ind(n) ![ \t] !BlankLine .) p (BlankLines? &(Ind(n) ![ \t] !BlankLine .) p)* { () }

DefBody <- Indented<Block(ind + 2)>(ind + 2) { () }
```

- 雛形の型注釈に値の引数を書ける（`Name<p :: a, sep>(n :: Int) :: T`）。定義には書かない。引数付き規則と同じである。「the template T cannot take parameters」の誤りをなくす
- 雛形は、雛形の引数（`<...>`）を一つ以上持つ。値の引数だけを持つものは引数付き規則であり、雛形ではない
- 展開した規則は、雛形の値の引数を引数に持つ引数付き規則になる。引数の並びは、雛形の値の引数（宣言の順）の後に、段階 1 で取り込んだ引数（名前の順）を置く
- 呼び出しは、値の引数と取り込んだ引数をこの順に渡す普通の規則の呼び出しに置き換える。値の引数の式は呼び出し元で評価するので、引数付き規則の呼び出しと同じく、呼び出し元の引数、左にある束縛、`_env`、`_col` を参照できる。束縛の値を雛形に渡したいときは、値の引数で渡す
- 展開の鍵に値の引数は含めない。値は実行時に渡るからである
- 値の引数の数が合わない呼び出しは誤りにする。文言は「the template T expects 1 value argument(s), but got 2」とする。雛形の引数の数の誤り（「the template T expects 2 argument(s), but got 1」）と区別するため、「value」を入れる
- 段階 2 の「the template T takes no value arguments」は、値の引数を宣言していない雛形に値の引数を渡したときの誤りとして残す。値の引数を宣言した雛形を値の引数なしで呼ぶと、上の数の誤りになる
- 段階 1 の束縛の誤りの文言の末尾に「; pass it as a value argument」を加える
- 段階 1 の名前の衝突の誤りは、雛形の値の引数の名前にも掛かる。値の引数 `n` を持つ雛形の引数が、呼び出し元の引数 `n` を取り込むと誤りになる
- lint（[ADR 0033](0033-grammar-linter.md)）の使われない束縛の判定は、値の引数の断片の中の識別子も束縛の使用とみなす

#### 文書

- [docs/syntax.md](../syntax.md) の雛形の節に、雛形の値の引数の宣言と、展開した規則の引数の並びを書く。段階 2 で書いた「雛形がまだ値の引数を取れない」を消す。よくある誤りの表を合わせる
- 仕様書の未決事項から「雛形と引数付き規則の組み合わせ」を消す

## 実装しないこと

- 雛形の展開を高階の Haskell 関数に置き換えること（[ADR 0031](0031-rule-templates.md) と同じ理由）
- 雛形の引数の中で、呼び出し元の選択肢の束縛を使うこと。束縛の型を推論しないと、展開した規則の引数の型が書けない。段階 3 からは値の引数で渡せる
- 取り込んだ名前と本体の名前の衝突を、名前の付け替えで避けること。衝突は誤りにし、利用者に引数の名前を変えてもらう（トレードオフを参照）
- 段階 1 の左再帰の誤りの文言から、展開した規則の内部の名前（`Lines'0`）を消すこと。`templateNotes` が雛形の名前と展開元の呼び出しを添えるので、誤りの場所は分かる
- 雛形を雛形の引数として渡すこと（高階の雛形）と、雛形の部分適用。`DefBody` の `ind + 2` を一度だけ書くにはこれが要るが、Golem の文法を含め、それ以上の場面が見つかっていない
- 値を使う雛形の引数の型の推論（[ADR 0031](0031-rule-templates.md) と同じ）
- `%entry`、`%start`、`%recover` などに雛形を指定すること（[ADR 0031](0031-rule-templates.md) と同じ）
- 雛形を一つも定義していない文法での雛形の呼び出しが、内部の誤りで止まる問題（仕様書の未決事項）。展開の入口の別の問題であり、本 ADR の段階とは独立に直せる（提案中の [ADR 0052](0052-template-calls-in-grammars-without-templates.md) が扱う）

## テスト設計

各段階で、次のテストを先に書いて失敗させてから実装する。
前の段階のテストは、後の段階でも通り続けること。

### 段階 1

展開（`peg-grammar` のテストの雛形の群）：

- `B(ind :: Int)` の中の `Lines<Item(ind)>` が、引数 `ind :: Int` を持つ展開した規則になり、呼び出しが `Lines'0(ind)` になること
- 意味述語を含む引数（`Lines<(&{ ind > 0 } Item(ind))>`）からも取り込むこと
- 呼び出し元に引数が二つ（`a`、`b`）あり、引数が `b` だけを使うとき、`b` だけを取り込むこと。両方を使うとき、名前の順に並ぶこと
- 修飾名（`M.ind`）、文字列リテラルの中（`"ind"`）、予約束縛（`_col`、`_env`）を取り込まないこと
- 二つの規則から同じ字句の引数で呼ぶと、取り込んだ引数の型が同じなら展開した規則が一つになり、型が違えば二つになること
- 雛形が雛形を呼ぶとき（`Outer<p> <- Lines<p>` を `Outer<Item(ind)>` で呼ぶ）、外側と内側の両方の展開した規則が `ind` を持つこと
- 引数の中の雛形の呼び出し（`Lines<Sep<Item(ind)>>`）で、内側と外側の両方が `ind` を取り込むこと
- 引数を使わない雛形の呼び出しで、取り込んだ引数が `_ind'` の名前になること
- 呼び出し元の引数を使わない雛形の呼び出しの展開が、これまでと変わらないこと

誤り：

- 雛形の引数が呼び出し元の選択肢の束縛を使うと、上の文言の誤りになること
- 本体に束縛 `x:N` を持つ雛形の引数が、呼び出し元の引数 `x` を取り込むと、名前の衝突の誤りになること。本体のコードの識別子との衝突も同じであること
- 引数を取り込んだ展開した規則が左再帰に加わると、引数付き規則の左再帰の誤りになり、雛形の定義の位置と展開元の呼び出しで報告されること

生成と実行（`peg-codegen` の fixture）：

- Golem の形を写した fixture を加える。字下げの深さを引数で渡し、空行を挟んで同じものが続く入れ子のリストと定義リストを、段階 1 の雛形（上の `Run<p, more>`）で書く。生成コードが警告なしでコンパイルでき、入れ子の深さごとに期待どおりの値を返すこと
- 同じ fixture に、雛形を使わずに書き下した同じ文法を `%entry` で並べ、無作為な入力に対する受理と値と最遠の失敗の位置が一致すること（プロパティテスト）
- 同じ文法に `%syntax` を付けた fixture で、構文木がロスレスであること
- 引数を使わない雛形を含め、生成コードに未使用の変数の警告が出ないこと

記法を読む道具が変わらないこと：

- 新しい fixture がハイライトの範囲の golden（[ADR 0034](0034-syntax-highlighting.md)）に加わり、tree-sitter の文法で `ERROR` なく読めて、三つの文法の範囲が一致すること。tree-sitter と TextMate の文法は変えない
- 新しい fixture を整形しても変わらず、lint の警告が出ないこと

既存の文法：

- `scripts/regen-fixtures.sh` を実行して、リポジトリのすべての文法の生成物が変わらないこと

### 段階 2

- 記法の文法：`Name<args>(vals)` が値の引数を持つ `ETemplate` になること。`Name<args> (vals)`（空白あり）が雛形の呼び出しと括弧のグループの逐次になること。自己記述の文法の生成物を、二回に分けた手順で作り直しても固定点になること
- 展開：値の引数を渡す呼び出しが「the template T takes no value arguments」の誤りになること。値の引数を持たない呼び出しの展開と誤りが変わらないこと
- 整形：golden に値の引数を持つ雛形の呼び出しを加え、空白が入らないこと。整形を二回掛けても変わらないこと
- ハイライト：値の引数の範囲が、引数付き規則の呼び出しの引数と同じ種類になること
- tree-sitter：コーパスとハイライトのテストに値の引数を持つ呼び出しを加え、`ERROR` なく読めること。TextMate のスナップショットの入力（`editors/test/sample.txt`）にも加えること。範囲の一致のテストはリポジトリの文法を読むが、段階 2 では値の引数を持つ呼び出しを生成できないので、fixture には加えない。リポジトリの文法での範囲の一致は段階 3 の fixture で確かめる
- 言語サーバー：値の引数を持つ雛形の呼び出しで、雛形の名前の semantic token が `macro` であり、定義への移動が雛形の定義を指すこと。診断に段階 2 の誤りが出ること
- 既存の文法の生成物が変わらないこと

### 段階 3

- 展開：値の引数を持つ雛形（`Indented<p>(n :: Int)`）の展開した規則が `n` を引数に持つこと。値の引数と取り込んだ引数を持つとき、値の引数（宣言の順）、取り込んだ引数（名前の順）の順に並ぶこと
- 展開の鍵：同じ雛形の引数で値の引数だけが違う二つの呼び出しが、一つの展開した規則を使うこと
- 値の引数の式が、呼び出し元の左にある束縛と `_col` を参照できること
- 誤り：値の引数の数の誤りの文言。値の引数を宣言していない雛形に値の引数を渡したときの誤り。雛形の定義に値の引数を書くと、引数付き規則と同じ誤りになること。値の引数の名前と取り込む名前の衝突。束縛の誤りの文言に「pass it as a value argument」が付くこと
- 左再帰：値の引数を持つ雛形の展開した規則が左再帰に加わると、段階 1 と同じ報告になること
- lint：値の引数の断片の中でだけ使う束縛を、使われない束縛として警告しないこと。lint の偽陽性のテスト（[ADR 0049](0049-lint-false-positive-test-and-expected-sets.md)）が通ること
- 生成と実行：段階 1 の fixture に、`Indented<p>(n :: Int)` で書いた版を `%entry` で加え、書き下した版との受理と値の一致のプロパティテストが通ること。生成コードが警告なしでコンパイルできること
- 記法を読む道具：値の引数を持つ呼び出しを含む fixture が、ハイライトの範囲の golden に加わり、tree-sitter の文法で `ERROR` なく読めて、三つの文法の範囲が一致すること。整形しても変わらないこと
- 既存の文法の生成物が変わらないこと

## トレードオフ

- 段階 1 の取り込みは、字句の一致で判定する。引数の断片の中で呼び出し元の引数と同じ名前を局所的に束縛すると（`\ind -> …`）、不要な引数を取り込み、生成コードに未使用の変数や名前の隠蔽の警告が出うる。Haskell の構文解析を持ち込まずに済ませるため、この稀な場合は受け入れる
- 名前の衝突を誤りにすると、利用者は引数の名前を変えなければならない。展開器が名前を付け替えれば誤りは不要になるが、引数の断片を書き換えることになり、展開した規則の中の GHC の誤りが利用者の書いた名前と食い違う。衝突は、本体の束縛と同じ名前の引数を持つ規則から雛形を呼ぶ場合に限られるので、誤りで足りると見込む
- 取り込んだ引数の型を展開の鍵に含めるので、同じ字句の引数でも型の違う規則から呼ぶと、展開した規則とメモ表が増える。雛形を書き下した場合と同じ数であり、それより増えはしない
- 引数を取り込んだ展開した規則は引数付き規則になり、左再帰に加われない。呼び出し元の引数を使う雛形の呼び出しは、書き下しても引数付き規則の呼び出しになるので、雛形のために失うものはない
- 段階 2 は、意味を持たない記法をリリースする。値の引数を渡す呼び出しは、段階 3 まで常に誤りになる。代わりに、段階 3 で記法を読む道具を変えずに済み、tree-sitter と TextMate の文法と範囲の一致のテストを段階 3 の fixture の前に揃えられる。段階 2 と 3 を一つにまとめれば、[ADR 0040](0040-templates-with-parameterized-rules.md) とほぼ同じ範囲の変更になる
- 段階 2 から、空白なしの `T<a>(b)` の読み方が変わる。いまある文法にこの形はなく、整形済みの文法にも現れないが、手で書いた文法が誤りになりうる。リリースノートで知らせる
- 段階 1 で止めた場合、`DefBody` のように同じ判定を呼び出しごとに書く形が残る。字下げの深さの式（`ind + 2`）が判定と要素に二度現れるのは、段階 3 でも変わらない（高階の雛形を入れないため）
