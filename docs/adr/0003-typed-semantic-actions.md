# ADR 0003: 型付きセマンティックアクションと規則別メモレコード

ステータス: 採択

## 文脈

生成パーサーの出力には二つの立場がある。
汎用の具象構文木（CST）を返して変換を利用者に委ねるか、happy のように各規則へ結果型とアクションを持たせて利用者の AST を直接返すか。
CST 方式は生成器を単純にするが、利用者は CST から AST への変換を別途書くことになり、型の検査も変換層まで届かない。

型付きアクションには実装上の難所が一つある。
パックラットのメモ表は「位置 × 規則 → 結果」の表だが、規則ごとに結果型が異なるため、単一の表に入れると型が消える（`Dynamic` などでの消去が必要になる）。
コード生成であればこの問題は解け、規則ごとのフィールドを持つメモレコードを文法から生成すればよい。
これはコンビネータライブラリでは綺麗に書けず、生成器の存在理由そのものである。

## 実装すること

- 各規則は結果型の注釈（`Expr :: Int` の形）を持ち、選択肢ごとに純粋な Haskell 式のアクションを持つ
- アクションは部分式の束縛（`名前:`）を参照して結果を構築する
- メモ表は文法から生成する。規則ごとにフィールドを持つレコード型を生成し、各フィールドは「位置 → その規則の結果型の結果」の表とする。型消去（`Dynamic`、`unsafeCoerce`）は使わない
- アクションを省略した選択肢の既定動作（マッチした部分文字列を返す、など）を定める。詳細は記法の確定（未決事項）と合わせて後続 ADR で決める

## 実装しないこと

- 位置情報付きの汎用 CST を返す層は実装しない。fmt / LSP のような CST を要する用途が現れた場合は、CST を利用者の AST として文法に書けるため、専用の層は不要と判断した
- アクション内での IO や状態は許さない。アクションの型は純粋な式に限る（ADR 0001 の成長ループがアクションを再実行するため）

## テスト設計

- **異種型の文法**：結果型が規則ごとに異なる文法（`Int`、`Text`、利用者定義の代数的データ型の混在）から生成したコードがコンパイルでき、正しい値を返すこと
- **メモ化の正しさ**：同一位置・同一規則の二度目の評価がメモ表から返ること（評価回数を数える計測用フックをテスト時のみ挿し、パックラットの線形性を確認する）
- **束縛の検査**：アクションが参照する束縛名が選択肢内に存在しない場合、生成前の静的検査でエラーになること

## トレードオフ

- 生成コードの型はユーザーの型注釈に依存するため、注釈の誤りは生成後の GHC のエラーとして現れる。`.peg` 側の行番号への写像（ADR 0002 の未決事項）が解決するまで、エラーの読み替えは利用者の負担になる
- メモレコードは規則数に比例してフィールドを持つ。規則数の多い文法でのメモリ消費は、メモ化の選択制御（未決事項）とセットで将来評価する
