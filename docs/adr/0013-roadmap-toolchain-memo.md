# ADR 0013: 実装の順序、ツールチェーン、メモ表のデータ構造

ステータス: 採択

## 文脈

ADR 0001〜0012 は設計の決定を記録しているが、実装の手順にはなっていない。
/goal は ADR を連番の順に実装するが、ADR 0001（左再帰）は peg-runtime がない段階では実装できず、ADR 0002（生成器）は ADR 0004（記法）がなければ動かない。
コミット済みの ADR は書き換えられないため、実装の順序を本 ADR で別に定める。

あわせて、実装に入る前に決まっていなかった二つを決める。
ツールチェーン（コンパイラ、ビルドツール、テストの道具立て）と、peg-runtime のメモ表のデータ構造である。
後者は生成コードが呼ぶ peg-runtime の API を決めるため、生成器より先に決めなければならない。

メモ表は、ADR 0001 の成長ループが項目を上書きするため、Ford のパックラットのような遅延評価による不変の表は使えない。
上書きの手段としては、ST モナドの可変参照と、State モナドで永続的な表を引き回す方式がある。
パックラットのメモ表はバックトラックで巻き戻す必要がない（一度書いた項目は、成長ループの上書きを除いて有効であり続ける）ため、永続性から得るものがない。
ST モナドを採る。

ただし ST モナドの採用だけでは解決しない問題が一つある。
間接左再帰の成長中に、関与する他の規則が、途中の種の値を使った結果をメモ表に書く。
この項目が次の反復で読まれると、古い種に基づく結果が返り、成長が誤る。
ADR 0001 はこの扱いを定めていなかったので、本 ADR で定める。

## 実装すること

### 実装の順序

ADR 0001〜0012 を設計の決定とし、/goal は次の順で実装する。
各段階で実装する内容は、括弧内の ADR に従う。

1. リポジトリの骨格。`cabal.project`、四つの公開パッケージと `peg-conformance` の空のパッケージ、CI のビルドとテストのジョブ（本 ADR）
2. peg-runtime の非左再帰部分。入力、位置（ADR 0008）、失敗と期待集合（ADR 0005）、メモ表（本 ADR）、評価回数のフック（ADR 0003）
3. peg-grammar。手書きの記法パーサー（ADR 0004）、予約構文の受理（ADR 0005、ADR 0006）、静的検査
4. peg-codegen の非左再帰部分（ADR 0002、ADR 0003、ADR 0008）
5. peg-cli の最小限の実装（ADR 0002）
6. JSON の適合性テスト（ADR 0010）。合格をもって最初の Hackage 公開の判定基準とする（ADR 0009）
7. ベンチマーク（ADR 0007）
8. 左再帰（ADR 0001 と、本 ADR の成長中の項目の破棄）
9. CommonMark の表現力測定（ADR 0011）
10. 文脈依存の拡張と再測定（ADR 0012）
11. 自己記述化（仕様書の設計原則）

本 ADR より後の ADR が実装の段階を加える場合は、この順序のどこに入るかを自身に明記する。

### ツールチェーン

- コンパイラとビルドツールは、ghcup が recommended とする版を使う。本 ADR の時点では GHC 9.10.3、cabal-install 3.16.1.0、HLS 2.14.0.0 である
- `cabal.project` の `with-compiler` で GHC の版を固定する。CI も同じ版を使う
- recommended が更新されたら追従する。追従は `cabal.project` と CI の版の書き換えで行い、ADR を要しない
- 手元では、ghcup が入れたバイナリを `mise.toml` でプロジェクトの PATH に加える。開発者の大域的なシェル設定には依存しない
- `text` は 2.0 以上とする。ADR 0008 のバイトオフセットは、`text` の内部表現が UTF-8 であることを前提にしている
- テストは tasty を基盤とし、単体テストに tasty-hunit、プロパティテストに tasty-quickcheck、golden テストに tasty-golden を使う
- ベンチマークは ADR 0007 のとおり criterion を使う

### メモ表のデータ構造

- 解析は ST モナドの中で行い、公開する入口は `runST` で閉じた純粋な関数とする。ST の型は peg-runtime の外に出さない
- 生成コードは、規則ごとに一つのフィールドを持つレコードを ST の中に確保する（ADR 0003）。各フィールドは `STRef (IntMap (Entry a))` で、鍵はバイトオフセット、`a` はその規則の結果型である
- `Entry` は成功の結果と、失敗の情報（最遠位置と期待集合、ADR 0005）の両方を表す
- 引数付き規則（ADR 0012）のフィールドは、`IntMap` の値をさらに引数を鍵とする `Map` にする
- 入力長と規則数の積の大きさの配列は確保しない。パックラットのメモ表は実際の解析では疎であり、密な配列は 1MB の入力と 100 規則で約 1 億スロットになるためである

### 成長中の項目の破棄

- 成長ループは、反復ごとにメモ表への書き込みを記録する
- 反復の終わりに、成長中の規則自身の種を除いて、その反復で書かれた項目をすべて破棄する
- 成長ループが入れ子になる場合（間接左再帰が別の左再帰を呼ぶ場合）、記録は入れ子ごとに積む

破棄する項目には、種に依存しないものも含まれる。
依存の有無を追跡せずに一律に破棄するのは、正しさを単純な規則で保つためである。

## 実装しないこと

- 密な配列によるメモ表
- 永続データ構造を State モナドで引き回す方式
- 種への依存を追跡して、依存する項目だけを破棄する最適化。ベンチマーク（ADR 0007）で成長ループの再計算が問題になったときに、新たな ADR で検討する
- stack によるビルド。cabal に一本化する
- GHC の複数の版での CI。recommended の一つだけを検査する

## テスト設計

- **骨格**：CI で全パッケージのビルドとテストが通ること。`cabal.project` の `with-compiler` と CI の GHC の版が一致すること
- **純粋な入口**：生成パーサーの入口の型に ST が現れないこと（型を固定するコンパイルテスト）
- **疎なメモ表**：長い入力に対して、メモ表の項目数が実際に評価した規則と位置の組の数に一致すること（評価回数のフックで数える）
- **成長中の項目の破棄**：破棄を無効にした評価器が誤った結果を返す間接左再帰の文法と入力を、少なくとも一つ用意する（ADR 0001 の `L <- P '.x' / 'x'`、`P <- P '(n)' / L` を候補とし、これで差が出なければ別の例を探す）。その例で、破棄を有効にした評価器が論文の意味論どおりの結果を返すこと。破棄が実際に効いていることの確認である
- **メモ化との整合**：ADR 0005 のメモ化整合テスト（メモ化を無効にした評価器との比較）を、左再帰を含む文法にも適用すること

## トレードオフ

- `IntMap` の参照は O(log n) であり、密な配列の O(1) より遅い。メモリと速度の交換であり、ベンチマークの結果で見直す
- 成長中の項目を一律に破棄するため、種に依存しない規則も反復ごとに評価し直す。左再帰の規則の評価は定数倍遅くなるが、ADR 0007 の計算量の保証（最悪二乗）は変わらない
- ghcup の recommended に追従する方針は、GHC の更新のたびに依存パッケージの対応状況に引きずられる可能性がある。追従できない場合は、その版を見送り、見送った旨を `cabal.project` のコメントに残す
