# ADR 0045: v0.1.0 の前に直す使い勝手と移植性

ステータス: 採択

## 文脈

v0.1.0 のリリース（[ADR 0044](0044-release-v0-1-0.md)）に向けてリポジトリを調べると、リリースを妨げはしないが、最初の利用者がすぐに出会う問題が見つかった。

- **ファイルの読み込みの誤り**：`peg-hs gen nonexist.peg` は、`openFile: does not exist` に続けて GHC の `HasCallStack backtrace:` を 5 行ほど出す。`gen`、`fmt`、`lint`、`parse` のどれも、ファイルの読み込みの例外を捕まえていない（`packages/peg-cli/app/Command/` の各コマンド）
- **文字コード**：`peg-hs` は、文法のファイルと生成したモジュールを、ロケールの文字コードで読み書きする（`Data.Text.IO`）。`setLocaleEncoding` も `hSetEncoding` も呼んでいない。Linux の C ロケール（コンテナや CI でよくある）では、日本語を含む文法を読むと失敗する見込みである。macOS では `LC_ALL=C` でも成功したが、Linux の C ロケールでは確かめていない。`peg-hs parse` が生成する主モジュールも同じである。言語サーバーは標準入出力をバイナリで扱うので影響しない
- **GHC の版**：すべてのパッケージが `base >=4.20 && <4.21` で、GHC 9.10 でしかビルドできない。Hackage の利用者の多くは、より新しい GHC（9.12、9.14）を使う。手元には ghc-9.14.1 があるが、ビルドできるかは確かめていない。`peg-hs parse` も、PATH の `ghc` が 9.10 でなければ失敗する（[ADR 0036](0036-parse-command.md)）
- **生成したモジュールの使い方**：README は、生成したモジュールが peg-runtime だけに依存することを一文で書くだけである。利用者のプロジェクトの `.cabal` の書き方、Hackage に上がる前の参照の仕方、`parse` を呼ぶコードの例がない
- **tree-sitter の文法の食い違い**：verbatim ブロックの中に `}}%` があると（`f = g {}}%`）、`peg-hs gen` は受理するが、tree-sitter の文法（[ADR 0034](0034-syntax-highlighting.md)）は誤りにする。verbatim の中身を正規表現の一つの字句として読んでおり、閉じの `}%` の直前の `}` を正しく扱えないためである。[ADR 0034](0034-syntax-highlighting.md) の一致のテストはリポジトリの文法しか見ないので、検出されない。どこにも書かれていない

## 実装すること

### ファイルの読み込みの誤り

- `gen`、`fmt`、`lint`、`parse` で、ファイルの読み込みと書き込みの `IOException` を捕まえ、バックトレースの代わりに、何が起きたかと、どうすればよいかを書いた短い誤りを標準エラー出力に書く
- 誤りの一行めは `peg-hs: cannot read FILE: 理由` または `peg-hs: cannot write FILE: 理由` とする。どのコマンドの、どのファイルの、読み込みと書き込みのどちらで失敗したかを分かるようにする。`FILE` は利用者が渡したとおりのパスとする
- 理由と、二行めに添える手がかり（`hint:`）は次のとおりとする

  | 場合 | 理由 | 手がかり |
  |---|---|---|
  | ファイルがない | `no such file` | 渡したパスの親のディレクトリがなければ、そのことを書く。現在のディレクトリを書く |
  | ディレクトリを渡した | `is a directory` | `gen` と `parse` では、文法のファイルを一つ渡すことを書く。`fmt` と `lint` はディレクトリを受け付けるので、この誤りにならない |
  | 権限がない | `permission denied` | なし |
  | 書き込み先のディレクトリがない（`gen -o`） | `directory DIR does not exist` | 生成器はディレクトリを作らないことを書く |
  | UTF-8 として正しくない | `not UTF-8 (at byte N)` | 文法と入力のファイルは UTF-8 で書くことを書く |
  | そのほか | 例外の説明 | なし |

- 終了状態は 1 とする（[ADR 0037](0037-cli-subcommands.md) の「検査で問題が見つかった場合」）。`fmt` と `lint` で複数のファイルを扱う場合は、読めないファイルを報告して、ほかのファイルを続ける
- 誤りの文言は英語とする。CLI のほかの出力と同じである

### 文字コード

- `peg-hs` は、文法のファイル、入力のファイル、生成したモジュールを、ロケールによらず UTF-8 で読み書きする。ファイルをバイト列として読み、UTF-8 として復号する
- UTF-8 として正しくないファイルは、上の「ファイルの読み込みの誤り」の形（`peg-hs: cannot read FILE: not UTF-8 (at byte N)`）で誤りにする。先頭のバイト順マーク（BOM）は読み飛ばす
- 標準出力と標準エラー出力は、UTF-8 で書く（`hSetEncoding`）。言語サーバーは、これまでどおりバイナリで扱う
- `peg-hs parse` が生成する主モジュールも、入力のファイルを UTF-8 で読み、UTF-8 で表示する
- 生成したモジュールの `parse` は `Text` を受け取るので、利用者がファイルをどう読むかは利用者に任せる

### GHC の版

- GHC 9.12 と 9.14 でビルドとテストを試し、通れば `base` の上限を広げる。通らない場合は、通すための変更を加える。`tested-with` に、確かめた版を並べる
- CI に、GHC 9.12 と 9.14 で全パッケージをビルドし、peg-runtime と peg-codegen のテストを動かすジョブを加える。peg-codegen のテストは、生成したモジュールを警告なしでコンパイルできることを確かめる（[ADR 0014](0014-generated-module-api.md)）ので、新しい GHC の警告への対応がここで分かる。ほかのスイートは、これまでどおり 9.10（[ADR 0013](0013-roadmap-toolchain-memo.md) の推奨版）で動かす
- `peg-hs parse` が受け付ける GHC の版を、`base` の範囲に対応する版（9.10 から 9.14）に広げる

### 生成したモジュールの使い方

- README（日本語と英語）に「生成したモジュールを使う」の節を加える。内容は次のとおりである
  - 利用者のプロジェクトの `.cabal` の `build-depends` に `peg-runtime` を加えること
  - Hackage に上がる前、または開発中の版を使う場合の `cabal.project` の `source-repository-package` の書き方
  - 生成したモジュールの `parse` と、誤りを表示する `renderParseError` を呼ぶ短いコード
  - 文法を変えたら `peg-hs gen` で生成し直し、生成したモジュールをコミットすること

### tree-sitter の文法

- verbatim ブロックの中身を、tree-sitter の外部のスキャナー（`src/scanner.c`）で読む。スキャナーは `}%` の直前までを一つの字句とする。`}` がいくつ続いても、`}%` の `}` を中身に含めない
- tree-sitter のコーパスのテストに、`}}%`、`}}}%`、中身が `}` だけの verbatim ブロックを加える
- アクションも要素もない選択肢（`S <- 'a' /`）を tree-sitter が受け付けないことは、README の「既知の制限」の節（[ADR 0046](0046-docs-cli-and-ci-before-v0-1-0.md)）に書き、エディタの節からその節へリンクする。この選択肢は値を持たないので、`peg-hs gen` も必ず誤りにする（[ADR 0030](0030-unit-values-are-not-counted.md)）。tree-sitter が誤りにしても、正しい文法を誤りと表示することにはならない

## 実装しないこと

- ロケールの文字コードに従うオプションと、文字コードを指定するオプション。文法と生成したモジュールはソースコードなので、UTF-8 に決める
- GHC 9.8 以前への対応
- 9.12 と 9.14 での全スイートのテスト。CI の時間を増やさないため、生成したモジュールのコンパイルに関わるものに限る
- tree-sitter の文法の、アクションも要素もない選択肢への対応

## テスト設計

先に書き、失敗させてから実装する。

### ファイルの読み込みの誤り

- 存在しないファイルを `gen`、`fmt`、`lint`、`parse` に渡すと、標準エラー出力が `peg-hs: cannot read FILE: no such file` と手がかりの行だけで、バックトレースを含まず、終了状態が 1 であること（peg-cli のテスト）
- 上の表の場合ごとに、理由と手がかりが表のとおりであること。権限のないファイル、`gen` と `parse` に渡したディレクトリ、`gen -o` の存在しないディレクトリを含む
- 誤りの出力の golden のテストを置き、文言を変えたときに気付けるようにする
- `fmt` と `lint` に、存在しないファイルと正しいファイルを渡すと、存在しないファイルを報告し、正しいファイルを処理すること

### 文字コード

- `LANG=C`、`LC_ALL=C` の環境で、日本語のコメントと日本語の文字クラスを含む文法を `gen`、`fmt`、`lint` で扱えること（peg-cli のテストで、子のプロセスの環境を変えて確かめる）。CI の Linux で失敗せずに通ることで、Linux の C ロケールでの挙動を確かめる
- UTF-8 として正しくないファイルが、上の形の誤りになり、失敗したバイトの位置が正しいこと
- BOM で始まる UTF-8 のファイルを、BOM のないファイルと同じに扱うこと
- `peg-hs parse` が、C ロケールで日本語の入力を解析し、日本語を含む値を表示できること

### GHC の版

- CI の 9.12 と 9.14 のジョブが、全パッケージのビルドと peg-runtime、peg-codegen のテストで通ること
- `peg-hs parse` のテストで、版の判定が 9.10、9.12、9.14 を受け付け、9.8 と 9.16 を拒否すること（版の文字列を判定する関数の単体のテスト）

### 生成したモジュールの使い方

- README の節のコード例を、テストで確かめる。例の文法と Haskell のコードをテストの fixture として持ち、README の例と一致することと、コンパイルして動くことを確かめる

### tree-sitter

- コーパスのテストに加えた `}}%` の例が、ERROR の節なしで解析されること
- 三つの文法の範囲の一致のテスト（[ADR 0034](0034-syntax-highlighting.md)）が通ること

## トレードオフ

- 文字コードを UTF-8 に決めるので、UTF-8 でない文法のファイルは読めない。ソースコードの文字コードとして UTF-8 以外を使う場面は少ないと見込む
- GHC の版を三つに広げるので、新しい GHC の警告や API の変更に追従する手間が増える。CI のジョブで早く気付けるようにする
- 9.12 と 9.14 のジョブが CI に加わり、合計の計算時間が増える。ほかのジョブと並列に動くので、ワークフローの時間はほとんど変わらない見込みである
- tree-sitter の外部のスキャナーは C で書くので、文法の定義が JavaScript と C の二つに分かれる。スキャナーは verbatim ブロックの中身の一つの字句に限る
