# ADR 0068: %syntax の文法で、型注釈のない規則は値を捨てる

ステータス: 採択（未実装）

## 文脈

[ADR 0063](0063-omit-unit-actions.md)、[ADR 0064](0064-unit-rules-always-return-unit.md)、[ADR 0066](0066-omit-unit-type-annotations.md) によって、型注釈のない規則の型は `()` になり、値のない選択肢のアクションは省略できるようになった。
その結果、`%syntax` を付けて、型注釈もアクションも書かない文法が、すでに生成できる。
値はすべて `()` になり、利用者は解析の結果を、`parseSyntax` が返すロスレスな構文木（[ADR 0019](0019-lossless-syntax-tree.md)）から取り出す。

```hpeg
%module Calc
%syntax

Expr <- Expr '+' Sp Term
      / Term

Term <- Term '*' Sp Atom
      / Atom

Atom <- [0-9]+ Sp
      / '(' Sp Expr ')' Sp

Sp <- ' '*
```

ところが、この書き方は、単位でない値を持つ要素を一つでも含むと崩れる。
キャプチャ `$[0-9]+`（値は `Text`）や、型注釈のある規則の呼び出しを、型注釈のない規則の選択肢に一つだけ書くと、アクションを省略した選択肢はその値を返す（[ADR 0004](0004-peg-notation.md)、[ADR 0064](0064-unit-rules-always-return-unit.md)）。
規則の型は `()` なので、生成したモジュールは GHC の型の誤り（`Couldn't match expected type '()' with actual type 'PegRt.Text'`）になる。
値を持つ要素が二つ以上なら、静的検査の誤りになる。

`%syntax` の文法では、要素の値は構文木からも取れる。
キャプチャした文字列は構文木の節の文字列であり、規則の値の代わりに、構文木の節を読めばよい。
構文木を使う利用者にとって、型注釈のない規則の値は意味を持たない。

リポジトリの持ち主は、「型付きの値や速さが要る利用者だけが、型注釈とアクションを書く」という分け方を望んだ。
そこで、この分け方の費用を測った。

### 計測

JSON の文法の四つの変種で、合成の JSON 文書（801,683 文字）を解析した。
変種の一つは、[docs/benchmarks/2026-10-11-json-syntax.md](../benchmarks/2026-10-11-json-syntax.md) の比較に、この ADR の書き方を加えたものである。
型注釈もアクションもキャプチャも書かず、`%syntax`、`%token Ws`、`%trivia Ws` を付けた JSON の文法を、計測のために一時的にベンチマークに加えて測った。
criterion の `--time-limit 15` での計測と、変種ごとに別のプロセスで測った最大の常駐メモリは次のとおりである。
機械は Apple M1 Max、OS は macOS 27.0、コンパイラは GHC 9.10.3（`-O1`）である。

| 文法と入口 | 時間 | 最大の常駐メモリ |
|---|---:|---:|
| `%syntax` なし、型付きの値（いまの `Json.hpeg`） | 636.5 ms | 264,740,432 バイト |
| `%syntax` あり、型付きの値 | 1,229 ms | 297,103,608 バイト |
| `%syntax` あり、構文木（アクションは評価しない） | 1,085 ms | 297,102,872 バイト |
| `%syntax` あり、型注釈とアクションなし、構文木 | 936.6 ms | 296,789,336 バイト |

型注釈とアクションを書かずに構文木を使う書き方は、型付きの値を返す文法（`%syntax` なし）に比べて、時間が約 1.47 倍、メモリが約 1.12 倍になる。
`%syntax` を付けて型付きの値を返す書き方よりは、時間で約 24% 速い。
値を組み立てない分だけ、同じ構文木を作る変種の中では最も速い。
`%syntax` の三つの変種は、ガベージコレクションのために計測のばらつきが大きく、criterion の信頼区間は 700 ms から 1.5 s に広がった。
同じ計測を 5 秒と 15 秒で二回行い、どちらでも順位と比は変わらなかった。

この比は、構文木を作るかどうかで決まる。
アクションを一つずつ省くことで変わる時間は、この差に比べて小さい。
速さが要る利用者は、`%syntax` を付けず、型注釈とアクションを書けば、構文木の費用を払わない。
`%syntax` を付けない文法の生成コードは、この ADR で変わらない。

## 実装すること

### 値を捨てる規則

- `%syntax` の文法で、型注釈のない規則の、アクションを省略した選択肢は、値を持つ要素の数と型によらず、値を `()` とする
  - キャプチャ（`$e`）、型注釈のある規則の呼び出し、単位でない値を持つ要素が、いくつあってもよい
  - 要素は値を捨てる文脈（[ADR 0026](0026-discard-unused-values.md)）で生成する
  - 束縛した要素は、意味述語や引数から参照できるよう、これまでどおり束縛する。構文木の取り出し関数（[ADR 0019](0019-lossless-syntax-tree.md)）も、これまでどおり作る
- 次の場合は変えない
  - `%syntax` のない文法。型注釈のない規則は、[ADR 0066](0066-omit-unit-type-annotations.md) と [ADR 0064](0064-unit-rules-always-return-unit.md) のとおりに扱い、単位でない値を一つ返す選択肢は GHC の型の誤りになる。型付きの値を書く文法では、型注釈の書き忘れを見つけられることを優先する
  - 型注釈のある規則。`:: ()` と書いた規則も、[ADR 0064](0064-unit-rules-always-return-unit.md) のとおりに扱う。型注釈を書くことは、型付きの値を返す意図を示すからである
  - アクションを書いた選択肢
  - 要素のない選択肢（[ADR 0063](0063-omit-unit-actions.md) と同じく、アクションを省略できない）

### lint

- 上の選択肢で、束縛した名前をどこからも使わない場合は、これまでどおり使われない束縛の警告を出さない。`%syntax` の文法では束縛が構文木の取り出し関数の名前になるので、使われない束縛の規則はもともと `%syntax` の文法に出ない（[ADR 0033](0033-grammar-linter.md)）

### ベンチマーク

- 計測で使った、型注釈とアクションを書かない JSON の文法を、`conformance/bench/JsonUntyped.hpeg` としてベンチマークに加える。この ADR の実装の後は、キャプチャを含む形（`Number <- $(...)` など）でも書けるので、`Json.hpeg` から型注釈、アクション、束縛を除いた形とする
- 実装の後に、上の四つの変種の時間と最大の常駐メモリを `docs/benchmarks/` に記録する

### 文書

- [docs/syntax.md](../syntax.md) のロスレスな構文木の節に、「型を書かない文法」として、`%syntax` を付けて型注釈もアクションも書かない書き方と、値を構文木から取り出すことを書く。速さが要るときは `%syntax` を付けずに型注釈とアクションを書くことと、計測の比を添える。冒頭の「反映している ADR」にこの ADR を加える
- README の「最初の文法」の後に、二つの書き方（構文木を使う書き方と、型付きの値を返す書き方）を短く並べる
- docs/specifications.md の生成するコードとロスレスな構文木の節に、この規則を書く
- [ADR 0066](0066-omit-unit-type-annotations.md) のステータスに、`%syntax` の文法の扱いがこの ADR にあることを加える

## 実装しないこと

- `%syntax` のない文法での値の破棄
- 型注釈を `()` と書いた規則での値の破棄
- 値を持つ要素が二つ以上の選択肢で、組を返すなどの既定の値。型付きの値を返す文法では、アクションを書く
- 構文木の作り方の高速化。この ADR は書き方を決めるもので、構文木の費用は変えない

## テスト設計

先に書き、いまの実装で失敗させる。

### 静的検査と生成

- `%syntax` の文法で、型注釈のない規則に、キャプチャだけの選択肢、型注釈のある規則の呼び出しだけの選択肢、単位でない値を持つ要素が二つの選択肢をアクションなしで書くと、静的検査が通り、生成したモジュールが警告なしでコンパイルでき、入口の値が `()` であること
- 同じ選択肢を、`%syntax` のない文法で書くと、これまでどおり、一つなら GHC の型の誤り、二つ以上なら静的検査の誤りになること
- `%syntax` の文法で、`:: ()` と型注釈を書いた規則は、これまでどおりの扱いになること
- 束縛した要素を意味述語で使う選択肢が、アクションなしで書けて、意味述語が働くこと

### 構文木

- `JsonUntyped.hpeg` の `parseSyntax` が、`JsonSyntax.hpeg`（型注釈とアクションを書いた `%syntax` の JSON の文法）の `parseSyntax` と、無作為な JSON の文書と JSONTestSuite の全件で、同じ構文木（`debugTree` の出力が同じ）を返すこと（プロパティテストと適合性テスト）

### ベンチマーク

- 自動テストにはしない。実装の後に四つの変種を測り、`docs/benchmarks/` に記録する。時間の比が、この ADR の計測から大きく外れないことを確かめる

## トレードオフ

- `%syntax` の文法では、型注釈のない規則で、値を返すつもりの選択肢から値を失っても、誤りにならない。構文木を使う書き方では値を使わないので、困るのは型付きの値も使うつもりで型注釈を書き忘れた場合である。入口の値が `()` になるので、型付きの値を使うコードはコンパイルできず、気付ける
- `%syntax` の有無で、型注釈のない規則の扱いが変わる。`%syntax` の文法は構文木を返す書き方、ない文法は型付きの値を返す書き方、と役割が分かれるので、規則もそれに合わせた
- 構文木を使う書き方は、型付きの値を返す文法より、時間で約 1.5 倍、メモリで約 1.1 倍の費用がかかる。速さが要る利用者は、型注釈とアクションを書き、`%syntax` を付けない
