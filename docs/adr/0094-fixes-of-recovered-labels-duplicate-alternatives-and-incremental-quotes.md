# ADR 0094: 回復する失敗ラベルの型、重複した選択肢へのラベルの挿入、増分の構文解析の引用符を直す

ステータス: 採択

## 文脈

互いに独立した三つの不具合を、一つの ADR で直す。
三つとも、既存の ADR が約束したことを実装が守っていない。
一つめは利用者の報告から、二つめと三つめは CI でときどき失敗するプロパティテストの調査から見つかった。

### 値を使わない位置の回復する失敗ラベルで、生成コードがコンパイルできない

[ADR 0021](0021-error-recovery.md) は「ラベルを付けた式が値を持たない場合、回復の規則の値は使われない」とした。
[ADR 0026](0026-discard-unused-values.md) は、値を捨てる文脈が失敗ラベル `^label` の中の式にも及び、回復の規則の値を捨てるとした。

生成器（`packages/peg-codegen/src/Peg/Codegen.hs` の `recoveryCode`）は、値を使わない位置で、回復の規則だけを `PegRt.voidS` か `PegRt.voidP` で包む。
ラベルを付けた式のほう（`exprCodeU` と `exprCodeSU` の `ELabel`）は包まない。
ランタイムの `labeled`、`labeledS`、`labeledMessage`、`labeledMessageS` は、回復の規則と式に同じ型を求める（`Maybe (P r s a) -> P r s a -> P r s a`）。
そのため、値を捨てる文脈でも式が `()` 以外の値を返すと、GHC が型の不一致で生成コードを拒否する。

main（7e718a6）で作った `peg-hs` で、次の文法を確かめた。
入力は `ax;` で、`peg-hs parse --format cst` を使った。

```
%module T.SOpt
%syntax
%recover l Skip
%safe l
S <- 'a' (('x')? ^l) ';'
Skip <- (!';' .)*
```

生成コードのコンパイルが ``Couldn't match type ‘Maybe ()’ with ‘()’`` で失敗した。
同じ形で、次の場合もコンパイルが失敗した。

- `%syntax` の文法で、`?` の代わりに `*` を使った場合（``‘[()]’ with ‘()’``）
- `%syntax` の文法で、`%message l "..."` を加え、`+` を使った場合（`labeledMessageS` を通る）
- `%syntax` のない文法で、値を持つ規則への参照にラベルを付けた場合（`S :: ()`、`S <- 'a' X ^l ';' { () }`、`X :: Int`。``‘Int’ with ‘()’``）
- `%syntax` のない文法で、同じ `X` の肯定先読みにラベルを付けた場合（`S <- 'a' &X ^l 'x' ';' { () }`）

`%syntax` のない文法の `?`、`*`、`+` は、[ADR 0026](0026-discard-unused-values.md) のとおり値を集めない形（`skipOptional` など）で生成されるので、この不具合は起きない。
規則への参照は、[ADR 0026](0026-discard-unused-values.md) が「値を捨てる文脈での規則の呼び出しの変更」をしないと決めたので、値を持ったままである。
`%syntax` の文法の `?`、`*`、`+` は、構文木の生成で `optionalS`、`manyS`、`many1S` になり、値を持ったままである。
回復の規則を `%recover` で与えないラベル（回復の規則が `Nothing`）や、`'x' ^l` のように式の値が `()` である場合は、コンパイルできた。

[ADR 0090](0090-grammar-interpreter-without-ghc.md) のインタプリタは、すべての値を `()` として扱うので、この不具合の影響を受けない。
上の `T.SOpt` の文法は、`peg-hs parse --interpret` で解析できた。
したがって、`peg-hs test` で解釈できる文法の例は通るが、同じ文法から生成したパーサーはコンパイルできない。

### ラベルの挿入が lint の警告 `duplicate-alternative` を消す

プロパティテスト「a formatted grammar stays formatted, and the warnings of lint stay」が、CI でときどき失敗する。
このテストは、[ADR 0054](0054-automatic-label-insertion.md) のテスト設計の「`peg-hs lint` の警告が、挿入の前と後で同じであること」を確かめる。
PR #81 の CI（part 4/4）で、二つのシード `(SMGen 7232420954780118896 15062904101511633367,34)` と `(SMGen 665394402065811642 16577916953842800677,64)` が失敗した。
main で、`--quickcheck-replay` にこの二つを与えると、どちらも失敗した。

最小の例は次の文法である。

```
%module Dup
S <- 'c' 'd' / 'c' 'd'
```

main の `peg-hs lint` は、二つめの選択肢に `duplicate-alternative` を警告する。
`peg-hs label --write` は `S <- 'c' 'd' ^S_d / 'c' 'd' ^S_d_2` と書き換え、その後の `peg-hs lint` は何も警告しない。

lint の `sameAlternative`（`packages/peg-grammar/src/Peg/Grammar/Lint.hs`）は、位置を除いて二つの選択肢を比べ、ラベルも比べる。
挿入の候補を決める `labelCandidates`（`packages/peg-grammar/src/Peg/Grammar/LabelInsertion.hs`）は、[ADR 0056](0056-label-insertion-and-template-deviations.md) のとおり、常に成功する選択肢を候補から外す。
重複した選択肢は外さない。
重複した二つの選択肢の片方か両方に、違う名前のラベルを挿入すると、二つは `sameAlternative` で等しくなくなり、警告が消える。
言語サーバーのコードアクションも同じ候補を使うので、同じことが起きる。

### 増分の構文解析が、複数行にわたる文字リテラルで全体の解析と食い違う

プロパティテスト「a random sequence of edits: every version is the same as its whole parse」が、CI でときどき失敗する。
このテストは、[ADR 0071](0071-incremental-parsing-in-the-language-server.md) の「断片ごとの解析の結果は、文書全体を一度に解析した結果と同じでなければならない」を確かめる。
PR #82 の CI で、シード `(SMGen 9670991169974700572 5874103237226552951,86)` が失敗した。
main で、`--quickcheck-replay` にこのシードを与えると失敗した。

回復する構文解析では、断片に誤りがあり、断片の末尾で括弧や文字列が開いたままなら、次の断片とつないで解析し直す（`packages/peg-grammar/src/Peg/Grammar/Incremental.hs` の `joined` と `open`）。
`open` は字句の簡単な模型で開閉を判定し、「同じ行で閉じた引用符は文字リテラル」とみなす。
同じ行で閉じない引用符は、ただの文字として読み飛ばす。

記法の文法（`packages/peg-grammar/grammar/Peg.hpeg`）は、Haskell のコードの中の文字リテラルを次の規則で読む。

```
HsChar <- '\'' '\\' . (!'\'' .)* ('\'' ^hschar)
       / '\'' . '\''
       / '\'' !'\\'

HsIdent <- c:$. &{ isIdentChar (firstChar c) && firstChar c /= '\'' } IdentChar* { () }
```

逆斜線で始まる文字リテラルは、行をまたいで次の `'` まで読まれる。
`open` はこれを読み飛ばさないので、全体の解析では文字リテラルの中にある括弧を、括弧として数える。
その結果、`open` は「閉じている」と判定し、断片をつながず、全体の解析と違う結果になる。
また、`HsIdent` は `x'` のような識別子の中の引用符を識別子の一部として読むが、`open` は識別子を区別しない。

main で、次の文書を確かめた（Haskell の文字列リテラルで書く）。

```
"%module M\nA <- 'a' { { '\\x ) }\nB <- 'b' } }\n"
```

全体の回復する構文解析には誤りがなく、概要の宣言は `A` だけである。
断片ごとの解析は、誤り（`action` と `topitem`）を二つ出し、概要の宣言は `A` と `B` になる。
CI の反例から調査で縮めた文書でも、概要の構文の誤りが全体の解析では 2 個、断片ごとの解析では 6 個になることを確かめた。

言語サーバーは、診断のための構文解析が失敗した文書で、最初の誤りより後の行にある概要の構文の誤りを診断に加える（`packages/peg-lsp/src/Peg/Lsp/Server.hs` の `diagnoseWith`）。
ハイライト、シンボル、定義への移動も概要を使う。
したがって、この不具合は、余分な構文の誤りの診断や、存在しない宣言を言語サーバーに見せる可能性がある。
実際の LSP のやりとりでは確かめていない。

あわせて、このプロパティテストの反例の表示にも誤りがある（`packages/peg-grammar/test/Incremental.hs`）。
結果の列は版の列と同じ長さで並ぶが、表示では版の列から先頭を落としてから結果と組にしている。
失敗した版の一つ後の版を表示し、最後の版の失敗は表示されない。
判定（`all fst results`）は正しいので、テストの合否は変わらない。

[ADR 0071](0071-incremental-parsing-in-the-language-server.md) は、`open` の規則を定めていない。
定めているのは、断片ごとの結果が全体の解析と同じであることと、食い違ったら全体の解析に戻すことである。
この修正は、その約束を守るための実装の修正であり、[ADR 0071](0071-incremental-parsing-in-the-language-server.md) の決定は変えない。

## 実装すること

### 回復する失敗ラベルの式の値を捨てる

- 生成器は、回復の規則を `%recover` で与えたラベルで、ラベルの位置の値を使わないとき（`recoveryCode` が回復の規則を `voidS` か `voidP` で包むときと同じ条件）、ラベルを付けた式も同じ関数で包む。構文木の生成では `PegRt.voidS`、型付きの値の生成では `PegRt.voidP` を使う
- `%message` のあるラベル（`labeledMessage`、`labeledMessageS`）も同じ扱いにする
- 回復の規則のないラベルの生成コードは変えない
- `voidS` は値を `()` に変えるだけで、構文木の子を変えない。解析の結果と構文木は変わらない
- `scripts/regen-fixtures.sh` で生成物を再生成する。生成物の変化は、`PegRt.voidS (...)` と `PegRt.voidP (...)` の包みが加わることだけである。調査で試した差分では、自己ホストの構文解析器（`SelfHostedSyntax.hs`）、codegen の fixture、適合性テストの生成物の 9 ファイルが変わった
- これで [ADR 0021](0021-error-recovery.md) と [ADR 0026](0026-discard-unused-values.md) の約束が実装に揃う。二つの ADR の決定は変えないので、ステータスの行は変えない

### 重複した選択肢にラベルを挿入しない

- `labelCandidates` は、規則の選択肢のうち、同じ規則の別の選択肢と `sameAlternative` で等しいものの中の位置を、挿入の候補にしない。等しい二つの選択肢の、前の選択肢と後の選択肢の両方を外す。片方にだけ挿入しても、二つは等しくなくなるためである
- 比べるのは、lint の `duplicate-alternative` と同じく、規則の最上位の選択肢どうしである。比べ方は lint と同じ関数を使い、二つの判定がずれないようにする（`Peg.Grammar.Lint` から `sameAlternative` を公開する）
- 重複した選択肢から呼ぶ規則は外さない。`sameAlternative` は規則への参照を名前で比べるので、呼ばれる規則の中のラベルは比べた結果を変えない
- 言語サーバーのコードアクションは同じ候補を使うので、同じく重複した選択肢に挿入しない
- これは [ADR 0054](0054-automatic-label-insertion.md) と [ADR 0056](0056-label-insertion-and-template-deviations.md) の挿入の候補の定義を広げる。実装のプルリクエストで、[ADR 0056](0056-label-insertion-and-template-deviations.md) のステータスの行を `採択→挿入の候補の除外（重複した選択肢）は [ADR 0094](0094-fixes-of-recovered-labels-duplicate-alternatives-and-incremental-quotes.md)` に変える
- `docs/syntax.md` と `docs/syntax.en.md` の、挿入しない位置の説明（常に成功する選択肢の段落）に、重複した選択肢を加える。両方の冒頭の「反映している ADR」の一覧に、この ADR を加える

### 増分の構文解析の `open` を記法の文法の字句に合わせる

- `open` は、逆斜線で始まる文字リテラル（`'\` から）を、行をまたいで次の `'` まで読み飛ばす。次の `'` がなければ、開いているとみなす（`HsChar` の一つめの選択肢に合わせる）
- `open` は、識別子の文字（`isIdentChar`）で始まり `'` で始まらない語を、識別子として読み飛ばす。語の中の `'` は文字リテラルの始まりとみなさない（`HsIdent` に合わせる）
- 逆斜線で始まらない文字リテラルの扱い（同じ行で閉じた引用符は文字リテラル）は変えない
- `open` の注釈を、上の規則と、どの規則に合わせたかを書いたものに改める
- プロパティテストの反例の表示を直す。失敗した版そのものと、その版の番号、断片への区切り、全体の解析との違いを表示する。違いは、その版を解析したときの断片の表を使って求める

## 実装しないこと

- 値を捨てる文脈で、`%syntax` の文法の `?`、`*`、`+` や規則への参照を、つねに値 `()` の形で生成すること。ラベルのない位置ではコンパイルできているので、ラベルの回復の不具合を直すには要らない。生成コードが広く変わり、構文木の生成の関数も増える
- 式の値が `()` かどうかを生成器で判定し、`()` の式だけ `voidS` や `voidP` で包まないこと。値の型を知るのは GHC であり、peg-grammar は Haskell の型を解釈しない（[ADR 0026](0026-discard-unused-values.md) と同じ理由）。包みは値を捨てるだけなので、`()` の式を包んでも結果は変わらない
- lint の `sameAlternative` の比べ方の変更。たとえば、ラベルを除いて比べるようにすれば挿入の後も警告は残るが、ラベルだけが違う二つの選択肢は回復の振る舞いが違いうるので、重複とはみなせない
- 規則の最上位より内側のグループの中の重複した選択肢の扱い。lint の `duplicate-alternative` は内側のグループを比べないので、そこへの挿入は警告を変えない
- `open` で括弧の種類（`(`、`[`、`{`）を区別すること。いまは開き括弧と閉じ括弧を種類を問わず数える。種類の食い違いで全体の解析と結果が違う例は、調査では見つけておらず、確かめていない
- `open` を記法の文法の字句の規則から自動で作ること。`open` は断片の末尾の開閉だけを見る小さな関数であり、食い違いはプロパティテストで見つける（[ADR 0071](0071-incremental-parsing-in-the-language-server.md) のトレードオフのとおり）

## テスト設計

先に書き、いまの実装で失敗させる。

### 回復する失敗ラベル

- **fixture**：codegen の fixture に、回復の規則を与えたラベルを値を使わない位置に置いた文法を加える。`%syntax` の文法で `e? ^l`、`e* ^l`、`e+ ^l`、`%message` を付けた `e+ ^l` を含めること。`%syntax` のない文法で、値を持つ規則への参照 `X ^l` と、その肯定先読み `&X ^l` を含めること。いまの生成器では、fixture の生成コードがコンパイルできず、テストのビルドが失敗する
- **回復の結果**：それぞれの文法で、ラベルの位置が失敗する入力（`T.SOpt` の例なら `ay;` のように `x` の代わりに別の文字がある入力）と成功する入力を、`parseSyntaxRecover`（`%syntax` の文法）か `parseRecover`（`%syntax` のない文法）で解析する。構文の誤りの範囲と、構文木（`%syntax` の文法）が、[ADR 0090](0090-grammar-interpreter-without-ghc.md) のインタプリタの `interpretRecover` と同じであること。`packages/peg-codegen/test/Agreement.hs` の一致のテストに加える
- **既存の生成物**：`scripts/regen-fixtures.sh` で再生成し、既存のすべてのテストと適合性テストが通ること。差分が `voidS` と `voidP` の包みだけであることを、プルリクエストで確かめる

### 重複した選択肢

- **最小の例**：`S <- 'c' 'd' / 'c' 'd'` で、挿入の候補がないこと。いまは `^S_d` と `^S_d_2` を挿入するので失敗する
- **間の選択肢**：`S <- 'c' 'd' / 'x' 'y' / 'c' 'd'` で、一つめと三つめには挿入せず、二つめの選択肢（`'y'` の位置）には挿入すること。重複の判定が選択肢の隣り合いに頼らないことを確かめる。いまは三つの選択肢のすべてに挿入するので失敗する
- **CLI**：peg-cli のテストで、`peg-hs label --write` の後の `peg-hs lint` が、最小の例の `duplicate-alternative` を挿入の前と同じく警告すること。いまは警告が消えるので失敗する
- **CI のシード**：上の二つのシードを `--quickcheck-replay` で与えて、「a formatted grammar stays formatted, and the warnings of lint stay」の part 4/4 が通ることを、実装のときに確かめる。シードは生成器を変えると別の文法を生むので、テストとしては残さない。上の最小の例が、同じ不具合の回帰のテストになる

### 増分の構文解析

- **最小の例**：`"%module M\nA <- 'a' { { '\\x ) }\nB <- 'b' } }\n"` で、断片ごとの解析の結果が全体の解析と同じであること（`sameAsWhole`）。いまは誤りの数と構文木が違うので失敗する
- **CI の反例の概要**：CI の反例から縮めた文書（`"module/\nX <-\n{{ / '\\t)* { () }{ # c\nx -}B\n <- \nT<&p}> : ()\nT<$}}\nX <- 'x'\n}%\n"`）で、断片ごとの解析の概要の構文の誤り（`outlineSyntaxErrors`）が、全体の概要と同じであること。いまは全体の 2 個に対して 6 個になるので失敗する
- **識別子の引用符**：`open` の単体のテストで、`x' ( y'` が開いていると判定されること。いまの `open` は `' ( y'` を同じ行で閉じた文字リテラルとみなして `(` を数えないので、閉じていると判定し、失敗する。`open` を公開していないので、テストのためにモジュールの公開の一覧に加える。断片ごとの解析と全体の解析が、識別子の引用符だけで食い違う文書の例は、調査では確かめていない
- **CI のシード**：上のシードを `--quickcheck-replay` で与えて、プロパティテストが通ることを、実装のときに確かめる。テストとして残さない理由は、重複した選択肢のシードと同じである
- **反例の表示**：自動テストにはしない。実装のときに、わざと失敗させた版の列で、失敗した版そのものが表示されることを確かめる

### 言語サーバーの速さ

回復の規則を持つラベルの修正は、自己記述のパーサー（`SelfHostedSyntax.hs`）の生成コードも変える。
実装のときに、[ADR 0071](0071-incremental-parsing-in-the-language-server.md) の目安（Golem の大きさの文法で、1 回の編集の診断と semantic tokens の要求がそれぞれ 16 ms 以内）を、修正の前と後で同じ方法で測り、結果をプルリクエストに書く。
目安を超えた場合は、修正を入れる前に報告する。

## トレードオフ

- 回復する失敗ラベルの修正は、値が `()` の式も `voidS` や `voidP` で包む。自己ホストの構文解析器の生成コードも変わり、言語サーバーの構文解析の時間（[ADR 0071](0071-incremental-parsing-in-the-language-server.md) の 16 ms の目安）にかかわる。包みは値を写すだけの `fmap` なので、影響は小さいと見込むが、計測はしていない
- 重複した選択肢にラベルを挿入しないので、重複を消すまで、その二つの選択肢の中の位置には自動でラベルが付かない。重複した後の選択肢は決して成功しない（lint の警告のとおり）ので、そこに付くラベルは働かない。前の選択肢には働くラベルが付きえたが、lint の警告を残すことを優先する
- `open` の字句の模型は、記法の文法の `HsChar` と `HsIdent` の写しになる。記法の文法の字句を変えたら、`open` も直す必要がある。食い違いは、全体との一致のプロパティテストで見つける
