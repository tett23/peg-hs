# ADR 0019: ロスレスな構文木を生成する

ステータス: 採択

## 文脈

ADR 0003 は、生成パーサーが型付きの AST を直接返すことにし、位置情報付きの汎用の構文木（CST）は作らないと決めた。
CST が要る用途では、利用者が CST を AST として文法に書けばよい、という判断だった。

Golem の lint と formatter で、空白とコメントを含む構文木が必要になった。
空白やコメントを型付きの AST に持たせることは、利用者が全規則のアクションで空白の規則の結果を拾うことを意味する。
これは手間が大きいうえ、一か所でも拾い忘れれば、木から元の文字列を復元できなくなる。
rust-analyzer は、この種の用途のために、元の文字列を一文字も失わない構文木（ロスレスな構文木）を中心に据えている。
rowan と呼ばれる実装で、要点は次の三つである。

- **green tree**：種類と子だけを持つ不変の木。親や絶対位置を持たないので、部分木を共有できる
- **red tree**：green tree の上を移動するための薄い層。親と絶対位置を必要になったときに計算する
- **型付きの層**：構文の種類ごとの型と、子を取り出す関数を、文法の定義から生成する

PEG の生成パーサーは、この構造と相性がよい。
スキャナを持たない PEG では、消費したすべてのバイトがいずれかの終端の一致に属する。
終端の一致をトークンとして、規則の呼び出しをノードとして記録すれば、入力全体を受理したときの木は自動的にロスレスになる。
rust-analyzer が字句解析器と構文解析器の間で行っている、空白やコメント（トリビア）をどのノードに付けるかの調整は要らない。
空白の規則は、それを呼んだ規則のノードの子になるからである。

## 実装すること

### 記法

次のディレクティブを加える。

- `%syntax`：構文木を生成する。生成モジュールは、型付きの値を返す入口（ADR 0014）に加えて、構文木を返す入口を公開する
- `%token Name`：規則 `Name` の一致を、内部の構造を持たない一つのトークンとする。識別子、数、空白、コメントのような字句の規則に付ける
- `%trivia Name`：`%token` の規則のうち、空白やコメントのようにトリビアとして扱う種類を示す。型付きの層の取り出し関数は、トリビアを読み飛ばす
- `%inline Name`：規則 `Name` の呼び出しをノードにせず、その子を呼び出し元のノードに直接並べる。字下げの判定や接頭辞の照合のような補助の規則に付ける

`%token`、`%trivia`、`%inline` は `%syntax` のない文法ではエラーとする。

### 木の作り方

- 規則の呼び出しは、規則名を種類とするノードになる。`%inline` の規則と `%token` の規則は除く
- `%token` の規則の一致は、規則名を種類とするトークンになる
- それ以外の終端（リテラル、文字クラス、任意の一文字）の一致は、同じノードの直下で連続する一致ごとに一つのトークンにまとめる。種類は無名のテキストとする
- 先読みと意味述語は入力を消費しないので、木に何も加えない。後戻りで捨てた試行も木に残らない
- 束縛（`名前:式`）の付いた式から生じた子には、束縛の名前をラベルとして付ける。型付きの層は、このラベルで子を取り出す
- 左再帰は、成長の各段階の結果を子に持つノードの入れ子になる。`E <- E '+' n / n` は左に深い木になる
- 引数付き規則のノードは、引数を記録しない
- 失敗した解析は木を返さない。仕様書の「エラー回復はしない」を変えない

### 実行時ライブラリ

peg-runtime に、構文木のモジュール（`Peg.Runtime.Syntax`）を加える。
生成コードが依存するのは引き続き peg-runtime だけである（ADR 0002）。

- **green tree**：種類（`SyntaxKind`）、子の列、子ごとのラベル、テキストの長さを持つ不変のノードと、種類とテキストを持つトークン
- **red tree**：`SyntaxNode` と `SyntaxToken`。green tree の要素と、絶対位置（バイトオフセット）と、親への参照を持つ。子への移動、親への移動、兄弟への移動、テキストの範囲、テキスト、`Pos`（ADR 0014 の行と桁）への変換を提供する
- `SyntaxKind` の表現は実行時ライブラリが定め、生成モジュールは規則ごとの種類の定数と、種類の名前を返す関数を公開する
- 木を字下げで表した文字列にする関数（rowan のデバッグ表示に相当）を提供する。golden テストに使う
- 誤りを表す種類（`ERROR`）を予約する。v1 では使わない（エラー回復を実装するときのための席であり、ADR 0005 の `^label` と同じ扱い）

### 生成コード

- 規則の評価は、型付きの値と green な部分木の組を返す。メモ表の項目もこの組を持つ。型付きの値の入口は組の値だけを、構文木の入口は組の木だけを使う
- 型付きの値は遅延評価されるので、構文木の入口ではアクションは評価されない。ただし、意味述語や規則の引数が束縛の値を参照する場合は、その値を計算するためにアクションが評価される
- 構文木の入口は `parseSyntax :: Text -> Either ParseError SyntaxNode` とし、`%entry` の規則には `parseSyntax規則名` を、`%env` の文法には環境の引数を加える（ADR 0014 の入口と同じ規則）
- 型付きの層：`%token`、`%inline` 以外の規則ごとに、ノードを包む型（`ExprSyntax` など）と、`SyntaxNode` からの変換関数を生成する。束縛ごとに取り出し関数（規則 `Expr` の束縛 `l` なら `exprL`）を生成する。取り出し関数の型は、束縛した式が規則の参照なら `Maybe 規則のSyntax`、規則の参照の繰り返しならそのリスト、それ以外なら構文の要素のリストとする。束縛がすべての選択肢にあっても、選択肢ごとに一致したかどうかは実行時に決まるので `Maybe` とする

## 実装しないこと

- エラー回復と、誤りを含む入力に対する部分的な構文木は作らない。LSP のように編集中の誤りを含む文書を扱う用途は、エラー回復の ADR に委ねる
- インクリメンタルな再解析はしない（仕様書）
- green tree の要素の重複の除去（同じ部分木を一つに共有するための表）はしない。メモ表による共有だけで足りるかを、まず計測する
- 構文木の書き換えのための API（rowan の mutable tree に相当）は作らない。formatter は構文木を読んで新しい文字列を作る
- 構文木から型付きの値を作り直す関数は作らない。型付きの値は従来の入口から得る

## テスト設計

- **ロスレス性**：構文木のテキストが入力と一致すること。JSON の適合性テストの受理すべき全件、CommonMark の全例（ブロックの文法とインラインの文法のそれぞれ）、codegen の fixture の文法について確かめる。無作為に生成した JSON 文書でも確かめる（プロパティテスト）
- **木の形**：codegen の fixture に `%syntax` を付けた版を用意し、代表的な入力の構文木のデバッグ表示を golden テストで固定する。左再帰の入れ子、`%inline` の展開、`%token` のまとまり、無名のトークンのまとまりを含める
- **一致の等価性**：同じ入力に対して、型付きの値の入口と構文木の入口が、成功と失敗を同じくし、失敗のときは同じ `ParseError` を返すこと
- **メモ化との整合**：メモ化を無効にした評価器と構文木が一致すること（ADR 0005 のメモ化整合テストの拡張）
- **型付きの層**：束縛の取り出し関数が、選択肢ごとに正しい子を返すこと。トリビアを読み飛ばすこと
- **静的検査**：`%syntax` のない文法での `%token`、`%trivia`、`%inline` がエラーになること。`%trivia` が `%token` でない規則を指したらエラーになること
- **性能**：`%syntax` を付けた文法と付けない文法で、型付きの値の入口の時間とメモリを ADR 0007 のベンチマークで比べ、`docs/benchmarks/` に記録する（ADR 0017）

## ADR 0003 との関係

ADR 0003 の「実装しないこと」にある「位置情報付きの汎用 CST を返す層は実装しない」を、本 ADR で改める。
型付きの AST を直接返す方式（ADR 0003 の主たる決定）は変えない。構文木は、`%syntax` を書いた文法でだけ、もう一つの入口として加わる。
本 ADR を採択するとき、ADR 0003 のステータスの行を「採択→汎用 CST を作らない（実装しないこと）は ADR 0019」に変える。

## 実装の段階

ADR 0016、0017、0018 の後に置く。
Golem の lint と formatter が使い始める前に、ロスレス性のテストを CommonMark の文法で通しておく。

## トレードオフ

- 規則の評価が値と木の組を返すため、`%syntax` を付けた文法では、型付きの値だけを使う場合にも木の分の割り当てが生じる。`%syntax` を付けない文法の生成コードは変わらない
- 無名のトークンを連続する一致ごとにまとめるため、`'<' '/'` のように並んだリテラルは一つのトークン `</` になる。演算子などを個別のトークンとして区別したい場合は、`%token` の規則として書く必要がある
- 取り出し関数を束縛の名前から作るため、束縛の名前の変更は公開 API の変更になる（ADR 0009 の PVP の対象）
- 取り出し関数の名前（`exprL` など）は利用者の verbatim ブロックの名前と衝突しうる。衝突は GHC のエラーとして現れる。名前の規則を syntax.md に明記する
