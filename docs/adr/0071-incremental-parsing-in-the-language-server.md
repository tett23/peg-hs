# ADR 0071: 言語サーバーで、最上位の要素ごとに構文解析を使い回す

ステータス: 採択

## 文脈

[ADR 0070](0070-faster-checks-in-the-language-server.md) は、言語サーバーの検査を速くし、目安を 1 回の編集につき 20 ms 以内とした。
リポジトリの持ち主は、その後、目安を 16 ms 以内に改めた。
16 ms は、毎秒 60 回の画面の更新の 1 回分にあたる。

[ADR 0070](0070-faster-checks-in-the-language-server.md) を実装した後の計測（[2026-11-06-lsp-checks-after.md](../benchmarks/2026-11-06-lsp-checks-after.md)）では、1 回の編集の時間は次のとおりだった。

| 文法 | 編集 1 回（受け取り、検査、送り出し） |
|---|---:|
| Golem の形を写したリポジトリの文法（`conformance/bench/Memo.hpeg`、712 行） | 15.80 ms |
| Golem の文法（723 行、参考） | 17.32 ms |

Golem の文法では 16 ms に届かない。
その 17.3 ms の内訳は、`.hpeg` の構文解析が約 12.7 ms（約 74%）、JSON の受け取りが約 4.3 ms（約 25%）、静的検査とラベルの検査と lint が合わせて約 2.3 ms である。
構文解析の中の時間は、規則ごとの処理に広く散らばっており、一か所を直して縮むものではなかった。
メモ表の作りや最適化の段を変えても、構文解析の時間は変わらなかった。

さらに、semantic tokens を求めるエディタでは、もう一つの構文解析が加わる。
言語サーバーは、診断のための構文解析（`parseTops`）とは別に、ハイライトと定義への移動のために、回復する構文解析で概要（[ADR 0035](0035-language-server.md)）を作る。
この構文解析は約 30.5 ms かかり、semantic tokens の要求は概要を含めて約 25.5 ms かかる。
エディタは編集のたびに semantic tokens を求めるので、ハイライトの更新はこの時間だけ遅れる。

二つの構文解析は、どちらも文書の全体を毎回解析し直している。
一回の編集で変わるのは、ほとんどの場合、最上位の要素（規則の型注釈と定義、指示、verbatim ブロック）のうち一つか二つである。
変わっていない要素の解析の結果を使い回せば、構文解析の時間は、変わった要素の分だけになる。

使い回しの単位を最上位の要素にするのは、記法がそこで区切れるからである。
記法の文法（`Peg.hpeg`）は、文書を最上位の要素の並び（`File <- Ws TopItem* !.`）として読み、回復する構文解析は、誤りのある要素を、次の最上位の要素の始まりまで読み飛ばす（`SkipToTop`）。
構文木の節は位置を持たず、長さだけを持つ（[ADR 0019](0019-lossless-syntax-tree.md)）ので、変わっていない要素の部分木は、そのまま新しい構文木に組み込める。
型付きの AST は行と桁で位置を持つが、要素は行の頭から始まるので、前の要素の行の数が変わっても、後の要素の位置は行の番号がずれるだけである。

## 実装すること

### 目安

- 言語サーバーの目安を、Golem の大きさの文法（`conformance/bench/Memo.hpeg` と Golem の文法）で、次のとおりとする。[ADR 0070](0070-faster-checks-in-the-language-server.md) の 20 ms を改める
  - 1 回の編集の診断（受け取り、検査、送り出し）が 16 ms 以内
  - 編集の後の semantic tokens の要求（概要を含む）が 16 ms 以内

### 文書の区切り

- 言語サーバーは、文書を最上位の要素の並びに区切る。区切りの位置は、回復する構文解析の `SkipToTop` と同じ規則で決める。改行の後に、空白、改行、`/`、`#` 以外の文字が続く位置を、要素の始まりとする
- ただし、verbatim ブロック（`%{` から `}%` まで）の中は区切らない。verbatim ブロックの中の行は、行の頭から書かれることが多いためである
- 区切った一つ一つを「断片」と呼ぶ。断片は、その中の文字列で同一性を判定する

### 断片ごとの構文解析と使い回し

- 言語サーバーは、断片の文字列から、その断片の構文解析の結果への表を持つ。結果は、診断のための構文解析の結果（型付きの最上位の要素）と、概要のための回復する構文解析の結果（構文木の部分木と、構文の誤り）の二つである
- 文書が変わったら、区切り直し、表にない断片だけを解析する。表にある断片は結果を使い回す
- 型付きの結果の位置は、断片の始まりを 1 行目とした相対の行で表に持ち、使うときに断片の始まりの行だけずらす。桁は変わらない
- 構文木の部分木は、そのまま組み合わせて文書全体の構文木にする
- 表の大きさは、直近の版の断片に限る。古い版にしかない断片は捨てる

### 全体の解析との一致

断片ごとの解析の結果は、文書全体を一度に解析した結果と同じでなければならない。
次の場合は、断片ごとの解析をやめ、文書全体を一度に解析する。

- 断片の解析が、構文の誤りで失敗した場合（診断のための構文解析）。誤りの位置と文言を、全体の解析と同じにするためである
- 区切りの規則が記法の文法と食い違う形を見つけた場合。たとえば、複数行のアクションや文字列の中で、行の頭から書かれた行がある場合である。断片の解析が誤りになるので、上の場合に含まれる
- 回復する構文解析では、断片ごとに回復しても全体の回復と同じになるように、断片の境界を `SkipToTop` の境界に合わせている。それでも、断片の境界で始まる誤りの扱いが全体の解析と食い違う場合は、全体の解析に戻す。食い違いは、下のテストで見つける

### JSON の受け取り

- 言語サーバーの文書の同期を、全文を送る形（`TextDocumentSyncKind.Full`）から、変更の部分だけを送る形（`TextDocumentSyncKind.Incremental`）に改める。受け取る JSON が小さくなり、受け取りの時間（約 4.3 ms）が縮む
- 変更の範囲は、言語サーバーの位置の単位（[ADR 0035](0035-language-server.md) の UTF-16 か UTF-8）で解釈する

### 計測の記録

- 実装の後に、[ADR 0070](0070-faster-checks-in-the-language-server.md) の段ごとの計測と、51 回の編集の計測を行い、`docs/benchmarks/` に記録する。編集の場所を、文書の先頭、中ほど、末尾の三つに分けて測る
- 目安に届かなければ、届かなかった段と理由を記録に書く

## 実装しないこと

- 最上位の要素より細かい単位での使い回し（メモ表を版の間で使い回すこと）。PEG の解析は先読みでどこまでも先を読みうるので、要素の中の一部の変更に限って解析し直すには、メモ表の項目ごとに読んだ範囲を記録する必要があり、変更が大きい
- コマンド（`peg-hs gen`、`lint`、`fmt`）での使い回し。コマンドは一度だけ解析する
- 静的検査、ラベルの検査、lint の使い回し。合わせて約 2.3 ms で、文法全体の関係を見るので、要素ごとに分けにくい

## テスト設計

先に書き、いまの実装で失敗させる。

- **区切り**：区切りの関数の単体のテスト。行の頭の規則の定義、指示、コメント、`/` で始まる続きの選択肢、verbatim ブロックの中の行頭の行、複数行のアクション
- **全体との一致（診断）**：リポジトリのすべての文法と、その変異（[ADR 0035](0035-language-server.md) の一致のテストの変異）で、断片ごとの解析と使い回しで得た診断が、文書全体を一度に解析した診断と同じであること
- **全体との一致（概要）**：同じ文法と変異で、断片ごとの回復する構文解析で組んだ構文木（`debugTree` の出力）と構文の誤りが、全体の回復する構文解析と同じであること
- **編集の列**：無作為な編集の列（文字の挿入、削除、行の挿入、削除を、文書の無作為な位置に）を適用しながら、各版の診断と構文木が、その版を全体で解析した結果と同じであること（プロパティテスト）。表の使い回しが前の版の状態に依存しても、結果が変わらないことを確かめる
- **使い回し**：一つの規則の中の一文字の変更で、解析し直す断片が一つか二つであること（表を外から数えられるようにして確かめる）
- **増分の同期**：`TextDocumentSyncKind.Incremental` の変更（範囲と文字列）を適用した文書が、全文を送った場合と同じであること。UTF-16 と UTF-8 の位置、複数の変更を含む通知、範囲が行の末尾を越える場合
- **計測**：自動テストにはしない。実装の後の計測で、目安に届いたかを書く

## トレードオフ

- 言語サーバーは、断片の表の分だけメモリを多く使う。表は直近の版の断片に限るので、文書の大きさのおおよそ数倍にとどまる
- 区切りの規則を、記法の文法と別に持つことになる。記法の文法を変えて、最上位の要素の始まりの形が変わったら、区切りの規則も直す必要がある。全体との一致のテストが、食い違いを見つける
- 構文の誤りのある文書では、診断のための構文解析は全体の解析に戻るので、速くならない。打鍵の途中の文書は誤りを含むことが多い。ただし、概要のための回復する構文解析は断片ごとに行うので、ハイライトの更新は速くなる
- 編集の場所によって、解析し直す範囲は変わらない（変わった断片だけ）が、型付きの結果の位置をずらす処理は、編集の場所より後の要素の数に比例する。この処理は構文解析よりずっと軽い
