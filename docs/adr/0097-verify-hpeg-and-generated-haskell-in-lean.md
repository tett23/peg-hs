# ADR 0097: Lean で hpeg の構文解析と生成した Haskell の構文を検証する

ステータス: 採択（未実装）

## 文脈

peg-hs は、自身の入力記法を `Peg.hpeg` で定義し、その文法から Haskell のパーサーを生成する。
ここで証明したいのは、文法ファイル自体が正しく書けていること、生成器が構文の壊れたモジュールを組み立てないこと、不正な文法を渡すと診断を返して停止することである。
この三つには、それぞれ異なる正しさの基準が要る。

## 調査した事項

- `packages/peg-grammar/grammar/Peg.hpeg` の開始規則 `File` は、空白と最上位の項目を読んだ後、`!.` で入力の末尾を要求する。
- `packages/peg-grammar/src/Peg/Grammar/Parser.hs` の `parseGrammar` は、自己ホストしたパーサーが返した項目を `assemble` に渡す。構文解析と宣言の検査は別の段階にある。
- `packages/peg-codegen/src/Peg/Codegen.hs` の `generateWithWarnings` は import を解決し、テンプレートを展開して規則を検査する。戻り値の `generationModule` 自体がさらに診断か生成テキストを持つ。
- `packages/peg-codegen/test/fixtures/Extensions.hpeg` は、言語拡張、import 宣言、型、意味アクションを指定する。入力に含まれる Haskell も生成モジュールの構文に関与する。

2026 年 11 月 12 日に Lean 4 の公式リリースで確認した最新安定版は v4.35.0 だった。

## 実装すること

Lean 4 のバージョンは elan で管理する。
導入時と更新時に公式リリースの最新安定版を確認し、証明プロジェクトの `lean-toolchain` に `leanprover/lean4:v4.35.0` のように正確なタグを記録する。
ローカルと CI は同じファイルを使う。

Lean 4 に hpeg の字句と構文の帰納的な判定関係を定義する。判定の根拠は記法の仕様とし、実装関数が成功したことを構文の定義に使わない。
順序付き選択、ラベル付き失敗、意味述語、入力末尾を扱い、メタ文法が用いる文字判定と式の深さの上限（256）も判定関係に含める。
構文解析の成功と判定関係の同値を証明し、リポジトリの二つのメタ文法を実ファイルから読み込んで判定する。
構文解析の入口は、宣言を組み立てる前の `parseTops` とする。

宣言の組み立て、import 解決、テンプレート展開、規則検査については、各段階の受理条件を仕様から述語として定める。
拒否条件には、未定義参照、空文字列を受理しうる式の繰り返し、無効なディレクティブなどを含め、仕様の各エラーと対応づける。
入力には有限のテキスト、読み込み済みの有限のライブラリ集合、生成オプションを含める。
各段階が停止することと、拒否条件が成り立つと診断を返すことを証明する。
再帰では入力位置や未訪問の参照先など、減少する量を示す。検査済みと仮定できるのは、検査を通過した後の処理だけである。

生成器については、出力に使う Haskell の構文を Lean で定義し、モジュールを構文木からテキストに印字する過程まで扱う。
埋め込みコードには、指定した言語拡張の下で、挿入箇所が要求する構文カテゴリに属するという前提を置く。
断片の前後でトークンが結合しないこと、コメント、レイアウト、括弧、引用符、行プラグマが周囲の構文を壊さないことは生成側の証明に含める。
使う構文規則と GHC の版および拡張の対応を記録し、GHC のパーサーとの一致を検証していない規則は前提として明示する。

実装と Lean の対応は、公開入口の入力から診断または最終出力テキストまでを結ぶ定理で示す。
既存の Haskell を対象とする段階では、その関数の定義から検査可能な翻訳を作り、翻訳で扱えない構文を検出したら検証を失敗させる。
翻訳器と Haskell の評価規則に置いた仮定を記録する。
独立に書いたモデルだけに定理がある段階は「モデルを検証済み」と報告する。
実装との対応、対象機能、残る前提を定理ごとに記録する。

## 実装しないこと

生成した Haskell の型、ユーザーの意味アクションの停止性や実行時の安全性は対象外とする。
不正入力への保証は文法を読み込んで生成結果を返す純粋な処理を対象とする。
ファイルシステムへのアクセス、バイト列のデコード、実機でのメモリやスタックの上限、生成したパーサーに与える入力は別の検証を要する。

## 不変条件

1. 任意の有限の hpeg テキストについて、`parseTops` が成功することと、入力全体に対する構文導出が存在することは同値である。`Peg.hpeg` と `PegSyntax.hpeg` の現行の内容はどちらも導出を持つ。
2. 任意の対象入力で生成処理は停止する。構文違反または検査対象の拒否条件が成立すれば、一件以上の診断を返し、生成テキストを返さない。警告を伴う結果では内側の `generationModule` まで評価して判定する。
3. 埋め込み Haskell が挿入箇所の構文上の前提を満たす任意の入力で、生成が成功すれば、出力テキスト全体に対象 Haskell モジュールとしての構文導出が存在する。

| 境界の入力 | 確かめる結果 | 番号 |
| --- | --- | --- |
| 空ファイル | 最上位の項目はゼロ件。生成に必要な宣言の検査で診断を返す | 1, 2 |
| 正しい最小の文法、その末尾に解釈できない文字を一つ追加した文法 | 前者は末尾まで受理し、後者は診断を返す | 1, 2 |
| 同じ原子式の前に先読み演算子を 256 個または 257 個置いた文法 | 256 個は構文解析を通り、257 個は深さの診断を返す | 1, 2 |
| 未定義の規則への参照が一つある文法 | 規則検査で診断を返す | 2 |
| 正しい意味アクションが一つある文法 | 生成したモジュール全体が構文を満たす | 3 |
| hpeg の区切りが閉じたアクションで Haskell 式だけが不完全 | 埋め込みの前提が成立しないことを確認する | 3 |

## テスト設計

採択後は各番号を名前に含むテストを先に追加する。
メタ文法の実ファイル、表の入力、既存の生成 fixture を読み、Lean と公開入口の結果を比較する。
生成成功例は対応する拡張を有効にした GHC のパーサーにも渡す。
二つのメタ文法については埋め込みコードの前提も個別に検査し、実際に再生成した自己ホストパーサーのモジュール全体について、埋め込みコードの妥当性を仮定に残さず不変条件 3 を適用する。
比較テストはモデルと実装のずれを発見するために使う。

CI では `lean --version` が `lean-toolchain` の指定と一致することを確かめ、番号ごとの定理と実装との対応定理をカーネルで検査する。
各定理が依存する公理を列挙し、未証明の穴や、証明すべき結論を仮定した公理があれば失敗とする。
メタ文法、生成器、検査器、翻訳器、証明、ツールチェーンのいずれかが変われば再検査する。

## トレードオフ

生成器の出力に絞って Haskell の構文を形式化すると、構文の追加ごとに証明が必要になる。
埋め込みコードを条件付きで扱えば、利用者が使う Haskell 全体を形式化する前に、生成器が組み立てる部分を検証できる。
純粋な処理の停止証明には計算資源の上限が含まれないため、巨大な入力による資源枯渇の評価には別の根拠が要る。
