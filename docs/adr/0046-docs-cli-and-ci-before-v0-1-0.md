# ADR 0046: v0.1.0 の前に文書、CLI の細部、生成物の再現性、CI の残りを直す

ステータス: 採択

## 文脈

v0.1.0 のリリース（[ADR 0044](0044-release-v0-1-0.md)）に向けてリポジトリを調べた結果のうち、[ADR 0045](0045-fixes-before-v0-1-0.md) に入れなかった小さなものをまとめる。
一つ一つは小さいが、放っておくと文書と実態の食い違いとして積み重なる。
最初のリリース（`v0.1.0-rc1`）は利用者が初めて文書を読む機会なので、rc の前に直す。

- **文書の古さ**：README、CONTRIBUTING、docs/specifications.md、docs/syntax.md は、ADR を実装するたびに必要な箇所だけを足してきた。そのため、節の並びが追加の順になっている箇所や、説明が短く、ADR を読まないと分からない箇所がある。利用者が最初に読む README には、導入の手順、生成したモジュールの使い方、コマンドの一覧がそろっていない
- **docs/syntax.md の例**：位置の節の例は、コメント「モジュール名は peg-runtime の実装時に確定する」を残している。`Peg.Runtime` はすでに確定している。同じ例は規則 `Num` を定義しておらず、そのままでは `undefined rule Num` になる。syntax.md と README の例を検査するテストは、誤りの表示の一例（`packages/peg-codegen/test/Main.hs`）しかない
- **docs/syntax.md の反映している ADR**：冒頭の一覧に [ADR 0029](0029-label-safety-implementation-deviations.md) がない。[ADR 0029](0029-label-safety-implementation-deviations.md) はラベルの安全性の定義を変えており、syntax.md のラベルの安全性の検査の節に関わる
- **コミットの言語**：CONTRIBUTING は、コミットの件名を日本語で書くと定めている。実際の最近のコミットは英語で、リポジトリの持ち主の方針も英語である
- **データのライセンス**：`conformance/data/whatwg-entities/` の文字参照の表（CC BY 4.0）は、ライセンスを `SOURCE` に書いているが、LICENSE のファイルがない。CONTRIBUTING は、取り込んだデータのライセンスを LICENSE のファイルに置くことを求めている
- **CLI の細部**：全体のヘルプに `--version` が載っていない。`help parse` と `help lsp` の golden のテストがない。オプションの `--name=value` の形を受け付けない。サブコマンドの間で、ヘルプの書き方と誤りの文言がそろっているかを、まとめて見直したことがない
- **生成物の再現性**：生成したモジュールの先頭のコメントと `{-# LINE #-}` に、`peg-hs gen` に渡した文法のパスと出力のパスがそのまま入る。絶対パスで生成すると、機械ごとに出力が変わる。リポジトリの生成物は、`scripts/regen-fixtures.sh` がパッケージのディレクトリから相対パスで生成しているので再現する。生成したモジュールは peg-runtime の内部のモジュール（`Peg.Runtime.Internal`）を import するが、どの版の peg-runtime が要るかは生成したモジュールに書かれない
- **ソースのアーカイブからのテスト**：CI はソースのアーカイブ（sdist）からビルドだけを行い、テストは動かしていない（[ADR 0009](0009-hackage-publication.md)）。テストの一部は、リポジトリの中のほかの場所のファイルを読み、無ければ飛ばす作りである
- **エディタの設定の例**：README の nvim-treesitter の設定の例は、`get_parser_configs()` を使っている。nvim-treesitter の現在の版で動くかは確かめていない
- **CI の時間**：[ADR 0042](0042-shard-peg-grammar-test.md) の後、ワークフローの時間を決めているのは package のジョブ（Haddock 43 秒、ソースのアーカイブからのビルド 41 秒、合計 121 秒）である（[計測](../benchmarks/2026-10-13-ci-shard-grammar.md)）
- **既知の制限**：利用者が知っておくべき制限が、ADR とベンチマークに散らばっている。`peg-hs parse` は `%env` の文法を扱えないこと（[ADR 0036](0036-parse-command.md)）、記法の文法の `%safe` が 21 個残ること（[ADR 0038](0038-label-check-precision-and-strip-labels-entries.md)）、tree-sitter の文法の制限（[ADR 0034](0034-syntax-highlighting.md)、[ADR 0045](0045-fixes-before-v0-1-0.md)）などである

## 実装すること

### 書き換えられる文書の最新化

対象は、コミットの後も書き換えられる文書である。README（日本語と英語）、CONTRIBUTING（日本語と英語）、docs/specifications.md、docs/syntax.md、`editors/` の README、各パッケージの `.cabal` の `synopsis` と `description` とする。
ADR、`docs/benchmarks/`、`docs/conformance/` のスナップショット、`docs/editors/` の記録は、コミットの後は変えないので対象にしない。

- **最新化**：各文書を、採択したすべての ADR の内容と、いまの実装に合わせる。実装と食い違う記述、実装しなかった機能の記述、古いコマンドの形（サブコマンドに分ける前の [ADR 0037](0037-cli-subcommands.md) より前の形など）を直す
- **丁寧さ**：ADR を読まなくても分かるように書く。各機能について、何をするものか、なぜそうなっているか、どう使うか、を書く。用語は最初に出るところで説明する。例は、そのまま動かせるものにする
- **README** は、次の順の節にする
  - 概要：peg-hs が何をするか、ほかのパーサー生成器との違い（左再帰、エラーからの回復、ロスレスな構文木、生成したモジュールが peg-runtime だけに依存すること）
  - 導入：GitHub の Release の実行ファイル、`cabal install`（[ADR 0044](0044-release-v0-1-0.md)）
  - 最初の文法：短い文法を書き、生成し、使うまでの一通りの手順
  - 生成したモジュールを使う（[ADR 0045](0045-fixes-before-v0-1-0.md)）
  - コマンドの一覧：`gen`、`fmt`、`lint`、`parse`、`lsp`、`help` の目的と主なオプション。詳しくは `peg-hs help COMMAND` に任せる
  - エディタ：シンタックスハイライトと言語サーバーの設定
  - 既知の制限（下の節）
  - 文書の案内：docs/syntax.md、docs/specifications.md、ADR、CONTRIBUTING
  - ライセンス
- **README の日本語と英語**は、同じ節の並びと同じ内容にする
- **CONTRIBUTING** は、開発の環境、ビルドとテスト、生成物の再生成、ADR の書き方と adr-guard、コミットの書き方、CI のジョブ、リリースの手順（[ADR 0044](0044-release-v0-1-0.md)）の順にする
- **docs/specifications.md** は、製品の仕様だけを書く（CLAUDE.md）。実装の詳細を書いている箇所があれば除き、ADR へのリンクに置き換える。未決事項に、VS Code の拡張機能の vsix の作成と Marketplace への公開（[ADR 0044](0044-release-v0-1-0.md)）を加える
- **docs/syntax.md** は、記法の各要素に、短い説明、例、よくある誤りとその警告を書く

### docs/syntax.md の例と反映している ADR

- 位置の節の例から古いコメントを除き、規則 `Num` を加えて、そのまま生成できる文法にする
- `%module` で始まる完全な文法の例（コードブロック）を、syntax.md と README から取り出し、解析と静的検査が通ることを確かめるテストを加える。断片の例は対象にしない
- [ADR 0029](0029-label-safety-implementation-deviations.md) の内容がラベルの安全性の検査の節と一致することを確かめ、冒頭の「反映している ADR」の一覧に加える

### CONTRIBUTING のコミットの言語

- コミットの件名と本文を英語で書くように改める（日本語と英語の両方）。`type(scope): description` の形と ADR の番号を添えることは変えない

### データのライセンス

- `conformance/data/whatwg-entities/LICENSE` に、CC BY 4.0 の告知と出典を置く

### CLI の細部

- 全体のヘルプに `--version` と `--help` を載せる
- `help parse` と `help lsp` の出力の golden のテストを加える
- オプションの解析（`packages/peg-cli/app/Options.hs`）で、値を取るオプションの `--name=value` の形を受け付ける。`--name value` の形はこれまでどおり受け付ける
- すべてのサブコマンドのヘルプと誤りを見直し、そろえる
  - ヘルプの節の並び（使い方、説明、オプション、例）と、オプションの説明の書き方をそろえる
  - 各サブコマンドのヘルプに、一つ以上の使い方の例を載せる
  - 使い方の誤り（知らないオプション、値の足りないオプション、知らないサブコマンド）の文言をそろえ、`peg-hs help COMMAND` を案内する一行を添える
  - 知らないサブコマンドが既知のサブコマンドに近い綴り（編集距離 2 以下）なら、候補を示す
- 見直しで見つけたほかの細部の食い違いも直し、実装の報告に一覧として挙げる

### 生成物の再現性と peg-runtime の版

- README と `peg-hs help gen` に、生成物を再現させる方法を書く。文法のパスと出力のパスを、生成したモジュールをコンパイルするパッケージのディレクトリからの相対パスで渡すことである。生成したモジュールが渡したパスを記録することと、その理由（GHC の誤りの位置を文法の行で示すため。cabal はパッケージのディレクトリで GHC を動かすので、そこからの相対パスなら、エディタが誤りの位置を開ける）を書く
- 生成したモジュールの先頭のコメントに、要る peg-runtime の版の範囲（`peg-runtime >=0.1 && <0.2` の形）を書く。範囲は peg-codegen が持つ定数とし、`Peg.Runtime.Internal` を変えて生成したモジュールとの互換が崩れるときに上げる
- `Peg.Runtime.Internal` の変更は、PVP の上でメジャーの変更として扱う。CONTRIBUTING にこの決まりを書く

### ソースのアーカイブからのテスト

- CI のソースのアーカイブからのビルドで、テストも動かす。リポジトリの中のほかの場所を読むテストは、ファイルが無いときに飛ばす作りなので、アーカイブだけで動く
- 飛ばしたテストの数が分かるように、飛ばすテストは理由を付けて報告する

### エディタの設定の例

- nvim-treesitter の現在の版で、README の設定の例を確かめ、動かなければ現在の設定方法に直す

### CI の package のジョブ

- package のジョブを、Haddock のジョブ（`haddock`）と、ソースのアーカイブからのビルドとテストのジョブ（`sdist`）に分ける。二つは並列に動く

### 既知の制限の一覧

- README（日本語と英語）に「既知の制限」の節を設け、上の制限を一か所にまとめる。各項目に、何ができないか、回避の方法があればその方法、ADR へのリンクを添える
- リリースノート（[ADR 0044](0044-release-v0-1-0.md)）は、この節へリンクする

## 実装しないこと

- 生成したモジュールに peg-hs の版を書くこと。版を上げるたびに、リポジトリのすべての生成物が変わり、生成物の一致のテストのために再生成が要る。peg-runtime の版の範囲は、互換が崩れるときにしか変わらない
- 生成したモジュールの中のパスを、生成器が相対パスに直すこと。GHC が動くディレクトリ（cabal ではパッケージのディレクトリ）を生成器は知らないので、正しい基準を選べない。渡されたパスをそのまま使い、相対パスで渡すことを文書で勧める
- 絶対パスを渡されたときの警告。ビルドの道具から絶対パスで呼ばれる使い方を妨げないため
- ADR、ベンチマーク、適合率、エディタの確認の記録の書き換え
- VS Code の拡張機能の Marketplace への公開と vsix の作成（[ADR 0044](0044-release-v0-1-0.md) と同じ）
- ラベルの自動の挿入（仕様書の未決事項）

## テスト設計

先に書き、失敗させてから実装する。

- **syntax.md と README の例**：完全な文法の例を取り出すテストが、いまの位置の節の例（`Num` がない）で失敗し、直した後に通ること
- **CLI のヘルプ**：全体のヘルプの golden に `--version` が載ること。すべてのサブコマンドの `help COMMAND` の golden があり、それぞれに例が載ること
- **`--name=value`**：`gen --output=out.hs`、`parse --format=cst`、`parse --ghc-arg=-isrc` が、空白で区切った形と同じに動くこと。`--debug-entry=x` のように値を取らないオプションに値を付けると、使い方の誤り（終了状態 2）になること
- **使い方の誤り**：知らないオプション、値の足りないオプション、知らないサブコマンドの誤りの golden。`peg-hs fnt` が `fmt` を候補に示し、`peg-hs xyz` が候補を示さないこと
- **生成物の再現性**：同じ文法を、別々の一時ディレクトリに置いたリポジトリの写しから相対パスで生成すると、出力がバイト単位で一致すること
- **生成したモジュールの peg-runtime の版**：生成したモジュールの先頭のコメントに版の範囲が入ること。codegen の golden（`Sum.hs.golden`）と、リポジトリのすべての生成物を再生成して確かめる
- **ソースのアーカイブからのテスト**：CI のジョブで、アーカイブから展開したパッケージのテストが通ること。飛ばしたテストが報告されること
- **CI の package のジョブ**：`haddock` と `sdist` のジョブが並列に動き、どちらも通ること。ワークフローの時間を計測し、`docs/benchmarks/` に置く
- **文書の最新化**：自動テストは書かない。実装の後に、各文書を読み、ADR と実装に合っていることを確かめる。README の手順（導入、最初の文法、生成したモジュールを使う）を、空のディレクトリで最初から実際に動かして確かめる。文書の中のリンクが切れていないことを確かめる
- **データのライセンス、CONTRIBUTING、README の既知の制限、nvim-treesitter の設定の例**：実装の後に、ファイルと文書を読んで確かめる。nvim-treesitter の設定の例は、実際の Neovim で読み込んで確かめる

## トレードオフ

- 文書を書き直すので、差分が大きくなり、レビューの手間がかかる。文書ごとにコミットを分けて、レビューしやすくする
- 文書を丁寧にすると長くなり、実装を変えたときに直す箇所が増える。README は案内にとどめ、詳しいことは docs/syntax.md と `peg-hs help` に任せて、同じことを複数の場所に書かないようにする
- syntax.md の例を検査するのは完全な文法に限るので、断片の例の誤りは見つからない。断片を完全な文法に埋め込んで検査する仕組みは、手間に見合わない
- 生成したモジュールに peg-runtime の版の範囲を書くと、範囲を上げるたびにすべての生成物が変わる。互換が崩れるときだけなので、頻度は低いと見込む
- 生成物の再現性を文書に頼るので、絶対パスで生成した利用者の生成物は、機械ごとに変わり続ける
- package のジョブを分けると、ジョブごとの準備の時間が増える（[ADR 0041](0041-split-test-jobs-and-cores.md) と同じ）
- ソースのアーカイブからのテストを動かすので、CI の時間が増える。並列のジョブなので、ワークフローの時間への影響は小さいと見込む
