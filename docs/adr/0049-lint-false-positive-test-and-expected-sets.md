# ADR 0049: lint の偽陽性のテストで比べる「失敗の報告」を定め直す

ステータス: 採択

## 文脈

[ADR 0033](0033-grammar-linter.md) は、lint の規則に偽陽性がないことをプロパティテストで確かめると定めた。
警告した選択肢を消した文法と、警告したラベルを外した文法が、短い入力の全列挙で元の文法と「同じ受理と同じ失敗の報告」を返すこと、である。

実装したテストは、受理したかどうかと最遠の失敗の位置だけを比べている。
失敗の報告のもう一つの要素である、最遠の位置で期待した字句の集合（[ADR 0005](0005-error-reporting.md)）は比べていない。
テストの解釈器が、期待した字句の集合を数えていないためである。

比べていないのは、手間の問題だけではない。
リテラルの接頭辞の規則では、期待した字句の集合は消す前と後で必ず変わる。
`S <- '=' { () } / '==' 'x' { () }` の後ろの選択肢は、決して成功しない。
前の選択肢 `'='` が先に成功するためである。
しかし入力が `=` で始まらないとき、後ろの選択肢も試されて失敗し、期待した字句の集合に `'=='` を加える。
空の入力の誤りは、消す前が `expected '=' or '=='`、消した後が `expected '='` である。
どちらの選択肢も同じ入力を受理しないので、消しても受理は変わらない。
変わるのは、誤りの文言に、決して成功しない字句が載るかどうかだけである。

つまり、[ADR 0033](0033-grammar-linter.md) の「同じ失敗の報告」を文字どおりに求めると、リテラルの接頭辞の規則は偽陽性のある規則になる。
しかしこの違いは、警告が指す問題そのものである。
決して成功しない選択肢を消すと、誤りの文言から、入力しても通らない字句の案内が消える。
警告に従って直した文法のほうが、利用者に正しい案内を出す。

そこで、規則を変えるのではなく、テストで比べる「失敗の報告」を定め直す。
あわせて、比べていなかった期待した字句の集合を、比べられる範囲では比べるようにする。

## 実装すること

### 「同じ失敗の報告」の定義

[ADR 0033](0033-grammar-linter.md) のテスト設計の「同じ失敗の報告」を、次のように定める。
元の文法を G、警告に従って直した文法を G' とし、同じ入力で比べる。

- **受理**：G と G' は、同じ入力を受理し、同じ入力を拒否する
- **最遠の位置**：拒否する入力では、最遠の失敗の位置が同じである
- **期待した字句の集合**：最遠の位置で期待した字句の集合を、規則ごとに次のように比べる
  - **必ず成功する選択肢の後の選択肢**、**重複した選択肢**、**効果のないラベル**：集合が同じである。消した選択肢は試されないか、前の選択肢と同じ字句を期待するだけなので、集合は変わらない
  - **リテラルの接頭辞**：G' の集合は G の集合に含まれ、G の集合から G' の集合を除いた残りは、消した選択肢の先頭のリテラルだけである。消した選択肢の分の字句が集合から抜けることだけを許す

### テストの解釈器

- テストの解釈器（`packages/peg-grammar/test/Lint.hs` の `run`）が、最遠の位置に加えて、その位置で期待した字句の集合を返すようにする
- 期待した字句の集め方は、peg-runtime と同じ規則に従う（[ADR 0005](0005-error-reporting.md)）。最遠の位置より手前の失敗は集合に入らず、より遠い位置の失敗が出たら集合を入れ替える。先読みの中の失敗の扱いも peg-runtime に合わせる
- プロパティテストの比べ方を、上の定義に改める
- テストの名前を、比べるものに合わせて改める

### 文書

- [docs/specifications.md](../specifications.md) と [docs/syntax.md](../syntax.md) の lint の説明に、リテラルの接頭辞の警告に従って直すと、誤りの文言から決して成功しない字句が消えることを書く
- [ADR 0033](0033-grammar-linter.md) のステータスを「採択→偽陽性のテストで比べる失敗の報告は ADR 0049」に変える

## 実装しないこと

- lint の規則を変えること。リテラルの接頭辞の規則は、決して成功しない選択肢を指すので、警告は実際の問題である
- 誤りの文言を比べること。文言は期待した字句の集合と最遠の位置から作られるので、二つを比べれば足りる
- 解釈器と peg-runtime の期待した字句の集合が一致することを、無作為な文法で確かめること。生成したパーサーをテストの中でコンパイルすることになり、peg-grammar のテストの時間が大きく延びる

## テスト設計

先に書き、失敗させてから実装する。

- **解釈器の期待した字句の集合**：手で選んだ文法と入力で、解釈器の最遠の位置と期待した字句の集合が、`peg-hs parse` の誤りの文言と一致すること。文言は手元で `peg-hs parse` を動かして得たものを、テストの期待値として書く。次の場合を含める
  - 選択肢のそれぞれが同じ位置で失敗する場合（集合が合わさる）
  - 手前の位置の失敗が、遠い位置の失敗に置き換わる場合
  - 先読み（`&e`、`!e`）の中で失敗する場合
  - リテラルの接頭辞の例（`S <- '=' { () } / '==' 'x' { () }` の空の入力）で、消す前の集合が `'='` と `'=='`、消した後の集合が `'='` であること
- **比べ方の境界**：リテラルの接頭辞の警告で、G の集合に消した選択肢の先頭のリテラル以外の字句が余分にあるとき、比べ方が違いとして報告すること。比べる関数の単体のテストで確かめる
- **プロパティテスト**：改めた比べ方で、[ADR 0042](0042-shard-peg-grammar-test.md) の分け方（3000 件を四つ）のまま通ること
- **ほかの規則**：必ず成功する選択肢の後の選択肢、重複した選択肢、効果のないラベルで、集合が同じであることを求めても通ること

## トレードオフ

- リテラルの接頭辞の規則では、集合が同じであることを求めない。そのため、この規則の誤りで、消した選択肢の先頭のリテラル以外の字句が集合から抜ける場合は見つかるが、消した選択肢の先頭のリテラルが本来抜けるべきでない場面で抜けても見つからない。消した選択肢は決して成功しないので、その字句を期待させる理由はない
- 解釈器を peg-runtime に合わせて保つ手間が増える。期待した字句の集め方を peg-runtime で変えたときは、解釈器も直す必要がある。手で選んだ例のテストが、食い違いを知らせる
