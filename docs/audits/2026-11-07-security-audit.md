# セキュリティ監査（2026-11-07）

対象コミット: `a429a19`（タグ `v0.1.0-rc5` の内容）。
ローカルの macOS / arm64 で、`~/.local/bin/peg-hs`（0.1.0.0）、リリースの wasm（`peg-hs.wasm`、`WebAssembly.Module.imports` が要求する WASI の関数だけを与える Deno 2.9.7 の harness）、`peg-hs lsp` に LSP のフレームを流し込む方法で確かめた。
製品コードと依存関係の修正は行っていない。

この監査は、前回（[2026-11-06](2026-11-06-security-audit.md)、[確かめ直し](2026-11-07-security-audit-recheck.md)、[ADR 0077](../adr/0077-fixes-of-the-security-audit.md) で解消）の後に入った新しいコード（`wasm/`、[ADR 0078](../adr/0078-grammar-analysis-in-wasm.md) と [ADR 0079](../adr/0079-stub-wasi-imports-outside-the-contract.md)）と、前回が範囲外とした領域を見た。
前回の四つの指摘（SEC-01 から SEC-04）は再掲しない。

## 結果

重大度は、この製品のローカル利用と、ブラウザのプレイグラウンドでの wasm の利用を前提にした監査上の評価であり、CVSS の算定値ではない。
文法に埋め込んだ Haskell（アクション、述語、`%{ }%`、`%env`）が利用者の権限で動くことは、前回と同じく設計上の信頼境界として扱い、脆弱性には数えない。

## 対象と前提

重点的に読んだのは、wasm reactor（`Peg.Wasm`、`wasm/reactor/Reactor.hs`、`wasm/stubs.wat`、`scripts/build-wasm.sh`）、FFI をまたぐメモリの扱い、untrusted な JSON の解析、生成器への注入（規則名、リテラル、文字クラス、ラベル、`@Constructor`、`%deriving`、ディレクティブの値、`LINE` プラグマへ渡るファイル名）、文法のパイプラインの資源枯渇（パーサー、テンプレート展開、検査、フォーマッター、言語サーバーの逐次解析）、言語サーバーの経路の走査とリクエストの不正、tree-sitter の外部 scanner、VS Code 拡張、CI とリリースの workflow である。
生成済みの巨大なパーサーの全行や適合性データを精査した監査ではない。

想定する入力境界は、第三者から取得した文法とリポジトリ、プレイグラウンドのページが wasm に渡す JSON のリクエスト、言語サーバーの標準入力に届くメッセージ、配布物を作る外部依存である。
プレイグラウンドのページは信頼できる作者が書くものとし、ページが wasm に渡す JSON のバイト列とリクエストの長さはページが決める。
攻撃者が握るのは、ページの `grammar` の文字列に入る文法の中身である。

## SEC-05: ディレクティブとファイル名の値が生成コードに注入される

重大度: 中・条件付き。

根拠: `packages/peg-codegen/src/Peg/Codegen.hs:203`（ヘッダーのコメントの行）、`:208`（`module` の行）、`:209` と `:250-253`（エクスポートの一覧）、`:155`（`LINE` プラグマのファイル名）。
`render` は、モジュール名を `"module " <> unLoc (grammarModule g)` と書き、エクスポートの一覧に `%export` の各項目を `map unLoc (grammarExports g)` でそのまま並べる。
ヘッダーのコメントの行は `"-- This module was generated by peg-hs from " <> T.pack (optSourceName opts) <> ". Do not edit it by hand."` で、`optSourceName` を `show` で囲まずに連結する。
`%module` の値に対する Haskell のモジュール名としての検査は、`Peg.Grammar.Assemble` にも `Peg.Grammar.Check` にもない。
`LINE` プラグマの中のファイル名は `show (optSourceName opts)` で、こちらは escape される。

前回の信頼境界は、文法に埋め込んだ Haskell のブロックだけを「コード」として扱うことを前提にしていた。
しかし `%module` と `%export` の値、および生成の元のファイル名（wasm の `sourceName`、`peg-hs gen` のファイルパス）は、埋め込みブロックの外にあるテキストで、どれも生成したモジュールにそのまま出る。
したがって、アクションも述語も `%{ }%` も `%env` も一つも持たない、見た目は「データだけ」の文法でも、生成したモジュールにトップレベルの Haskell の宣言を仕込める。
この注入が実際にコードを動かすのは、利用者が生成したモジュールをコンパイルしたときである。
`peg-hs gen` は `.hs` を書くだけでコンパイルしないので、注入だけでは動かない。

再現:
`%module M (parse) where evil = 1 {-` を持つ文法を `peg-hs gen` にかけると、生成物の先頭は次のようになった（[生成物](2026-11-07-inj-module.hs)）。

```text
-- This module was generated by peg-hs from inj-module.hpeg. Do not edit it by hand.
-- It needs peg-runtime >=0.1 && <0.2.
module M (parse) where evil = 1 {-
  ( parse
  , evil2) where evil2 = 2 {-
  ) where
```

`%export` の項目 `evil2) where evil2 = 2 {-` も、エクスポートの一覧にそのまま出た。
`lint` と `fmt` はこの文法を誤りとして報告しない（`lint` は終了コード 0）。
wasm の `analyze` に `sourceName` として `x.hpeg\nimport System.IO.Unsafe\ninjected = ...\n--` を渡すと、ヘッダーのコメントの行が改行で分断され、`import` と宣言の行が生成物のトップレベルに出た。
`@Constructor` は `'@' Ident`（`packages/peg-grammar/grammar/Peg.hpeg:181`）で lex されるので、識別子の文字しか入らず、ここからは注入できない。
`%language` と `%deriving` は `isExtensionName` と `isClassName`（`Assemble.hs`）で検査され、リテラルと文字クラスとラベルは `show` で escape されるので、ここからも注入できない。

対処:
`%module` の値を、ドットで区切った Haskell のモジュール名として検査する。
`%export` の各項目を、エクスポートの一覧の項目として検査するか、少なくとも改行と括弧を拒む。
ヘッダーのコメントの `optSourceName` を、制御文字を含まない名前に限るか、escape する。`show` で囲めば改行は `\n` に変わるのでコメントから抜け出せなくなるが、すべての生成物の先頭の行が変わる。
あわせて、`parse` だけでなく `gen` の説明にも、文法が利用者の権限で動くコードであり、`%module` やファイル名のような埋め込みブロックの外の値も生成コードに入ることを書く。

修正後の確認:
改行、括弧、`{-` を含む `%module` と `%export` の値、改行を含む `sourceName` を拒むか、無害な形で出すことを、`peg-cli` と `peg-codegen` のテストで固定する。

## SEC-06: 入れ子の深い入力が超線形の時間とメモリを使う

重大度: 中（プレイグラウンドの worker と言語サーバー）、低（CLI のローカル利用）。

根拠: `packages/peg-grammar/src/Peg/Grammar/Format.hs:146-176`（`walk` と `element`）。
フォーマッターは、入れ子になった構文木を `walk` と `element` でたどり、`element e ++ [Pop]` のようなリストの連結を各段で行う。
入れ子の深さに対して、イベントの列を作る連結と、その後のレイアウトの走査がともに超線形になる。
検査、分類、ラベルの安全性、コード生成も、入れ子の式を繰り返したどるため、深さに対して超線形である。
JSON のパーサー（`Peg.Lsp.JsonParser`、文法から生成した PEG パーサー）も、入れ子の深さに対して超線形である。

再現（計測は[計測のまとめ](2026-11-07-timings.txt)、入力は [reproduce-deep-nesting.sh](reproduce-deep-nesting.sh) が書く `p<N>.hpeg` と `dj<N>.json`）:
`%module M\nS <- ((...'a'...))` の形で、入れ子の群を N 段にした文法を使った。
`peg-hs gen` は N=8000（約 16 KB）で 6.0 秒かかり、常駐メモリは 517 MB に達した。
N=100000（約 200 KB）は 40 秒で終わらなかった。
`peg-hs fmt --check` は N=4000 で 10.2 秒、N=8000 は 30 秒で終わらなかった。
`peg-hs lint`（解析と lint だけ）は N=8000 で 0.36 秒だったので、パーサー自体はほぼ線形で、超線形なのは検査、ラベル、生成、そしてフォーマッターである。
リリースの wasm では、N=4000（8 KB の文法）の `analyze` が 14.6 秒、`format` が 15.6 秒かかった。
これは、単一の worker で動くプレイグラウンドが十数秒固まることを意味する。
`peg-hs lsp` に initialize と didOpen と formatting を流すと、N=4000 で 4.0 秒ブロックした。
深い JSON のリクエストを wasm の `analyze` に渡すと、入れ子 100000 段で 2.8 秒と 158 MB、1000000 段（約 2 MB）は 30 秒で終わらなかった。

影響の範囲:
プレイグラウンドでは、攻撃者が握るのは `grammar` の文字列なので、入れ子の深い文法を一つ書くだけで worker を固められる。
言語サーバーでは、入れ子の深い文法を開く、または整形を要求することで、エディタを数秒から無限にブロックできる。
JSON のパーサーは言語サーバーが受け取るすべてのメッセージの本文を解析するので、壊れたクライアントが [ADR 0077](../adr/0077-fixes-of-the-security-audit.md) の本文の上限（64 MiB）の中で入れ子の深い本文を送るだけで、CPU とメモリを大量に使わせられる。
上限は溜め込みを防ぐが、上限の中での解析の超線形の費用は防がない。

対処:
パーサーの段で入れ子の深さに上限を設け、超えた文法を誤りとして拒む（テンプレート展開に深さ 64 の上限があるのと同じ考え方）。
あるいは、フォーマッターのイベントの構築と、検査や生成の走査を線形にする。
JSON のパーサーにも入れ子の深さの上限を設ける。

修正後の確認:
深さの上限の境界を、`peg-grammar`、`peg-lsp`、`peg-wasm` のテストで固定し、上限の内側の入力が現実的な時間とメモリで終わることを確かめる。

## SEC-07: 範囲外の長さで reactor が終了する

重大度: 低（情報）。

根拠: `wasm/reactor/Reactor.hs:36-39`。
`serve f p n` は、`request <- BS.packCStringLen (castPtr p, fromIntegral n)` を `try` の外で行い、その後で `try (evaluate (forced ...))` に入る。
長さ `n`（`CInt`）が負、または線形メモリを超える大きさのとき、`packCStringLen` のコピーが範囲外を読むか巨大な確保に失敗し、例外が `foreign export` の外へ抜ける。
コメントは「あらゆる例外を捕えて wasm を動かし続ける」と書くが、要求のコピーと `fromIntegral` の変換はその `try` の外にある。

再現（[reproduce-wasm-length.ts](reproduce-wasm-length.ts)）:
`analyze` を正しい長さで呼ぶと JSON の応答が返り、reactor は生き続けた。
長さに `-1` または `0x7fffffff` を渡すと、どちらも `proc_exit 1` に至り、その後の呼び出しは失敗した（reactor が終了した）。

影響の範囲:
長さ `n` はページが渡す値で、文法の内容からは決まらない。
正しく実装したページは常に要求のバイト数を渡すので、この経路は攻撃者の文法からは到達しない。
reactor の頑健性の問題であり、攻撃経路ではない。

対処:
長さを検査し（負や、確保済みのメモリを超える値を拒む）、要求のコピーを例外の処理の内側に移す。
境界の値を渡したときに、reactor が終了せず JSON の誤りを返すことを、`peg-wasm` のテストで固定する。

## SEC-08: VS Code 拡張の実行ファイルのパスの scope と信頼

重大度: 低〜中。

根拠: `editors/vscode/package.json`、`editors/vscode/extension.js:8-15`。
拡張は、設定 `peg-hs.path` の値を言語サーバーの実行コマンドとして `LanguageClient` にそのまま渡す。
`peg-hs.path` の定義には `scope` がなく、既定の window（リソース）の scope になるので、ワークスペースの `.vscode/settings.json` が値を上書きできる。
`machine` や `application` の scope ではない。
`package.json` に `capabilities.untrustedWorkspaces` の宣言もない。

確認状況:
静的解析で、`peg-hs.path` に `scope` がないこと、`capabilities` が無いことを確かめた。
VS Code の信頼モデルからの推定として、`untrustedWorkspaces` を宣言しない拡張は制限モード（Restricted Mode）で無効になるので、利用者がワークスペースを信頼するまでは、悪意あるワークスペースの設定で言語サーバーは起動しない。
しかし利用者がワークスペースを信頼すると、そのワークスペースの `.vscode/settings.json` が `peg-hs.path` を任意のコマンド（リポジトリの中の相対パスの実行ファイルを含む）に上書きでき、`.hpeg` を開いた時点でそれが実行される。
実機の VS Code での再現は行っていないので、これは静的解析と VS Code の文書からの推定である。

対処:
`peg-hs.path` に `scope: "machine"` を付け、ワークスペースの設定が上書きできないようにする。
`capabilities.untrustedWorkspaces` を明示して、信頼していないワークスペースでの挙動を定める。
前回の監査が「追加改善」として挙げた項目（Workspace Trust と設定スコープの方針）に対応する。

修正後の確認:
`peg-hs.path` を設定したワークスペースの設定ファイルが、拡張の設定の解決で無視されることを確かめる。

## 防御として確認できた点

- 言語サーバーは、URI からファイルを読み書きしない。URI は開いている文書の地図の鍵として使うだけで、`didOpen` と `didChange` が送った文書のテキストだけを扱う。パストラバーサルの経路はない（`Peg.Lsp.Server`）。
- 言語サーバーは、`line` と `character` の負の値や範囲外の位置を、`max`、`min`、`drop`、`T.take` で丸めて扱う。メソッドや `id` を欠くメッセージは JSON-RPC の誤りで応答し、落ちない（`applyChange`、`locOf`、`receiveMessage`）。
- [ADR 0077](../adr/0077-fixes-of-the-security-audit.md) のフレームの上限（ヘッダー 64 KiB、本文 64 MiB）は入っている（`Peg.Lsp.Rpc`）。
- tree-sitter の外部 scanner は、直列化で状態を持たない（`serialize` は 0 を返し、`deserialize` は buffer を無視する）。固定長の配列へのコピーもなく、`lexer->advance` で一文字ずつ進むだけである。境界の問題はない（`editors/tree-sitter-hpeg/src/scanner.c`）。
- wasm reactor は、解析そのものの例外を `try` で捕え、非 UTF-8 の要求を `decodeUtf8'` で誤りにし、BOM を落とす（`Reactor.hs:39`、`Peg.Wasm`）。SEC-07 は、その `try` の外にある要求のコピーだけの話である。
- `@Constructor`、`%language`、`%deriving` の値は検査され、リテラルと文字クラスとラベルは `show` で escape される。
- CI の既定権限は `contents: read`、checkout は `persist-credentials: false`、公開のジョブだけが `contents: write`。wasm のツールチェーンは ghc-wasm-meta の flake の固定したコミットで、nix-installer が flake.lock とハッシュに対して取得物を検査する。リリースは `SHA256SUMS` を作る（`.github/workflows/`）。
