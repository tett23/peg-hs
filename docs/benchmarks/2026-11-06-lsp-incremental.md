# 言語サーバーの増分の構文解析と同期（2026-11-06）

[ADR 0071](../adr/0071-incremental-parsing-in-the-language-server.md) の実装の前と後で、[ADR 0070](../adr/0070-faster-checks-in-the-language-server.md) の段ごとの計測と、51 回の編集の計測を行った。
編集の場所は、文書の先頭、中ほど、末尾の三つに分けた。

`peg-hs lsp` と同じ実行時の設定（`-A64m`）で、1 回の編集（`didChange` の解読、検査、診断の符号化）は、変更の範囲だけを送る同期で、Memo.hpeg が約 2.4 ms、Golem の文法が約 3.5 ms になった。
編集の後の semantic tokens の要求（概要を含む）を加えても、どちらの文法でも約 10 ms である。
目安の 16 ms には、二つの値とも、二つの文法の三つの場所のすべてで届いた。

この値は下記の環境での計測であり、他の環境の値とは比べられない。
退行の判定には使わない（[ADR 0007](../adr/0007-performance-discipline.md)）。

## 計測の環境

- 機械：Apple M1 Max
- OS：macOS 27.0
- コンパイラ：GHC 9.10.3（`-O1`、cabal の既定）
- 文法：`conformance/bench/Memo.hpeg`（712 行）と、Golem の文法（`modules/golem-parser/grammar/Golem.hpeg`、723 行、Golem のコミット 89ae4b41）
- 「前」は [ADR 0071](../adr/0071-incremental-parsing-in-the-language-server.md) の ADR の文書だけを加えたコミット（92ffc20）、「後」は実装の後である。どちらの `peg-bench` にも、下の編集の計測を加えてある
- 計測の間、同じ機械で別の作業が動いており、ロードアベレージは 5 から 8 だった

## 編集の計測の作り

一つの編集は、規則の定義の行の前に `#` だけの行を挿入する。
場所は、` <- ` を含む行のうち、最初の行（先頭）、真ん中の行（中ほど）、最後の行（末尾）である。
挿入した行はコメントなので、文法は正しいままであり、診断は全体の解析に戻らない。
挿入した行より後の要素は、行の番号が一つずれる。

- 「全文」：`didChange` が文書の全文を持つ。前の実装は、この形しか受け取らない
- 「範囲」：`didChange` が挿入の位置と文字列（`#\n`）だけを持つ（`TextDocumentSyncKind.Incremental`）

criterion の計測は、編集の前の版を開いて概要を計算した状態から、毎回同じ一つの編集を適用する。
編集の前の版の断片は表にあるので、解析し直すのは挿入した行を含む断片だけである。

### 編集の段の内訳（後）

| 段 | Memo.hpeg（先頭、中ほど、末尾） | Golem.hpeg（先頭、中ほど、末尾） |
|---|---|---|
| 範囲の `didChange` の JSON の解読 | 48.49 μs、47.32 μs、47.35 μs | 46.35 μs、47.26 μs、46.60 μs |
| 断片ごとの構文解析（型付きの最上位の要素、`show` を含む） | 1.762 ms、1.748 ms、1.761 ms | 1.652 ms、1.686 ms、1.750 ms |
| 断片ごとの概要（`show` を含む） | 5.006 ms、5.012 ms、4.951 ms | 5.213 ms、5.195 ms、5.267 ms |

断片ごとの構文解析の約 1.7 ms は、文書の区切り、表の参照、変わった断片の解析、後の要素の行のずらしを含む。
全文の構文解析（下の表の `parseTops`）の約 13 ms に比べて、約 8 分の 1 である。
場所による差は誤差の範囲に収まった。
ADR のトレードオフに書いたとおり、行をずらす処理は構文解析よりずっと軽い。

全文の同期では、約 4 ms から 5 ms の JSON の解読が残る。
範囲の同期では、解読は 0.05 ms に縮み、文書に変更を当てる処理を含めても、編集の診断は全文の同期より約 4 ms 短い。

## 51 回の編集のセッション

`peg-bench --lsp-messages GRAMMAR DIR PLACE SYNC` で、initialize、didOpen、50 回の didChange、shutdown、exit のメッセージを一つずつのファイルにした。
didChange は、場所の定義の行の前に `#` の行を挿入し、続く変更でその行の末尾に `x` を一文字ずつ加える。
メッセージを 30 ms の間隔で `peg-hs lsp` の標準入力に書き、プロセスの CPU 時間（user と sys の和）を測った。
間隔が検査より長いので、どの変更も間引かれずに検査される。
3 回の計測の範囲を示し、括弧の中は 51 で割った値である。
CPU 時間は、起動と、最初の版の全体の解析を含む。

| 文法 | 場所 | 前（全文） | 後（全文） | 後（範囲） |
|---|---|---:|---:|---:|
| Memo.hpeg | 先頭 | 0.82 から 0.83 秒（16 ms） | 0.42 から 0.47 秒（9 ms） | 0.24 から 0.25 秒（5 ms） |
| Memo.hpeg | 中ほど | 0.82 から 0.84 秒（16 ms） | 0.43 秒（8 ms） | 0.25 秒（5 ms） |
| Memo.hpeg | 末尾 | 0.82 から 0.86 秒（16 ms） | 0.42 から 0.43 秒（8 ms） | 0.24 から 0.25 秒（5 ms） |
| Golem.hpeg | 先頭 | 0.90 から 0.91 秒（18 ms） | 0.48 から 0.50 秒（10 ms） | 0.25 から 0.29 秒（5 ms から 6 ms） |
| Golem.hpeg | 中ほど | 0.90 から 0.95 秒（18 ms） | 0.49 から 0.50 秒（10 ms） | 0.26 から 0.29 秒（5 ms から 6 ms） |
| Golem.hpeg | 末尾 | 0.94 から 0.98 秒（19 ms） | 0.50 から 0.52 秒（10 ms） | 0.27 から 0.32 秒（5 ms から 6 ms） |

このセッションは semantic tokens を要求しない。

全文の同期と範囲の同期で、最後の版の診断は同じだった。
すべてのメッセージを一つのファイルにして与えた場合（`peg-bench --lsp-session GRAMMAR OUT PLACE SYNC`）の出力を、前と後、全文と範囲で比べた（前の出力は `initialize` の応答の `"change"` の値だけが違う）。

すべてのメッセージを一つのファイルで与えると、言語サーバーは最後の版だけを検査する。
5 回の計測で、前（全文）は Memo.hpeg で 0.26 から 0.30 秒、Golem の文法で 0.28 から 0.32 秒、後（範囲）はどちらの文法でも 0.03 から 0.05 秒だった。
前の時間の大半は 50 回の全文の JSON の解読である。

## 目安

| 目安（16 ms 以内） | Memo.hpeg | Golem.hpeg |
|---|---|---|
| 1 回の編集の診断（範囲の同期） | 2.38 ms から 2.46 ms | 3.53 ms から 3.58 ms |
| 編集の後の semantic tokens の要求（概要を含む、診断との合計） | 9.98 ms から 10.10 ms | 9.92 ms から 10.41 ms |

どちらの目安にも、三つの場所のすべてで届いた。

ただし、次の場合は目安を測っていない。

- 構文の誤りのある版の診断は、文書の全体を解析する（[ADR 0071](../adr/0071-incremental-parsing-in-the-language-server.md) のとおり）。その版の編集の診断は、前の実装と同じく約 13 ms の構文解析を含む
- 構文の誤りのある版の概要は、誤りの断片の境界の読み方が全体の解析と食い違いうるときに、後の断片とつないで解析する。閉じていない括弧や文字列のように、どこまで読むか断片の中で決まらない誤りでは、文書の末尾までつなぐことがあり、その版の semantic tokens は前の実装に近い時間になる
