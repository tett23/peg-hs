# 言語サーバーの検査の段ごとの時間、速くした後（2026-11-06）

[ADR 0070](../adr/0070-faster-checks-in-the-language-server.md) の実装の後に、[実装の前の計測](2026-11-06-lsp-checks-before.md) と同じ段を測った。
`peg-hs lsp` と同じ実行時の設定（`-A64m`）で、1 回の編集（`didChange` の受信から診断の送信まで）は、リポジトリの文法で 36.74 ms から 15.80 ms に、Golem の文法で 47.83 ms から 17.32 ms になった。
目安の 16 ms には、リポジトリの文法では届き、Golem の文法では 1.3 ms 足りない。
[ADR 0070](../adr/0070-faster-checks-in-the-language-server.md) に書いた 20 ms には、どちらも届いた。

この値は下記の環境での計測であり、他の環境の値とは比べられない。
退行の判定には使わない（[ADR 0007](../adr/0007-performance-discipline.md)）。

## 計測の環境

- 機械：Apple M1 Max
- OS：macOS 27.0
- コンパイラ：GHC 9.10.3（`-O1`、cabal の既定）
- 文法：`conformance/bench/Memo.hpeg`（712 行）と、参考として Golem の文法（723 行）。実装の前と同じ
- 計測の間、同じ機械で別の作業が動いており、ロードアベレージは 3 から 7 だった

## 速くしたこと

時間の大半は二つの構文解析（`.hpeg` の構文解析と、`didChange` の JSON の解読）と、そのガベージコレクションだった。
検査の段（静的検査、ラベルの安全性の検査、lint）は、合わせて 2 ms に満たず、手を入れていない。

- **割り当て領域**：`peg-hs` を `-with-rtsopts=-A64m` で作る。構文解析は 1 回に約 40 MB を割り当て、既定の割り当て領域では時間の約 6 割がガベージコレクションだった
- **期待した字句の集合**：peg-runtime は、最も遠い失敗の位置で期待した字句の集合を、誤りを報告するときにだけ合併する。成功する構文解析は集合を読まないので、合併の計算が残らない。最も遠い失敗より手前の失敗は記録を作らず、リテラルは入力を切り出さずにバイトで比べる
- **構文解析を一度にする**：診断は、`parseTops` の結果を組み立てに渡し、同じ版の文法を二度解析しない。概要と診断は版ごとに一度だけ計算し、文書に持たせる
- **行の参照**：文書の行を連結リストからシーケンスに替え、診断と semantic tokens が行を対数時間で引く
- **JSON**：文字列を、エスケープの要らない文字の並びごとに書き出す。言語サーバーの JSON の文法は、字句の規則（`Ws`、`Unit`、`Hex`、`IntPart`、`Frac`、`Exp`）をメモ化しない。`conformance/bench/JsonNomemo.hpeg` と同じ指定である

Golem の文法で診断を JSON にする部分（診断の計算と、解読した通知からの編集の差）は、約 8 ms から、既定の設定で約 2 ms、`-A64m` で 1 ms 未満になった。
行の参照と文字列の書き出しを合わせた効果である。

## 51 回の編集のセッション

実装の前と同じ入力（`peg-bench --lsp-session`）を一つのファイルとして `peg-hs lsp` に与えると、言語サーバーはすべての変更を読んでから最後の版だけを検査する。
診断の送信は 51 回から 1 回になり、時間は Memo.hpeg で約 1.71 秒から約 0.27 秒、Golem の文法で約 2.19 秒から約 0.28 秒になった（5 回の計測のうち、最初の 1 回を除いた値）。
この値は間引きの効果を含み、1 回の編集の時間とは比べられない。

1 回ずつの編集の時間は、メッセージを一つずつ間を空けて送って測った。
`peg-bench --lsp-messages` で一つずつのファイルにしたメッセージを、間隔を空けて `peg-hs lsp` の標準入力に書き、プロセスの CPU 時間（user と sys の和）を 51 で割った。
間隔が検査より長いので、どの変更も間引かれずに検査される。

| 文法 | 間隔 | 前 | 後 |
|---|---:|---:|---:|
| Memo.hpeg | 30 ms | 1.70 秒（33 ms） | 0.81 秒（16 ms） |
| Golem.hpeg | 30 ms | 2.15 から 2.18 秒（42 ms） | 0.88 秒（17 ms） |
| Memo.hpeg | 100 ms | 1.93 秒（38 ms） | 1.08 から 1.11 秒（21 ms） |
| Golem.hpeg | 100 ms | 2.38 から 2.40 秒（47 ms） | 1.13 から 1.17 秒（22 ms） |

間隔を 100 ms にすると、どちらの実装でも 1 回の編集が数 ms 長くなる。
入力を待つあいだにプロセスが効率コアに移る、あるいはキャッシュが冷えるためと考えられるが、確かめていない。

打鍵が検査より速い場合として、Golem の文法のメッセージを 2 ms の間隔で送った。
実装の前は 51 回の診断を送り、2.16 秒かかった。
実装の後は診断を 14 回か 15 回送り、0.40 秒で終わった。

## 目安に届かなかった段

Golem の文法では、1 回の編集の 17.32 ms のうち、`.hpeg` の構文解析が約 12.7 ms、JSON の解読が約 4.3 ms を占める。
静的検査、ラベルの安全性の検査、lint は合わせて約 2.3 ms で、残りは診断の符号化である。
目安の 16 ms を超える 1.3 ms は、二つの構文解析のどちらかを速くしないと削れない。

構文解析をさらに速くする試みは、効果がなかった。
メモ表を連想配列から位置ごとの可変配列に替えても、peg-runtime と peg-grammar を `-O2` で作っても、`.hpeg` の構文解析の時間は変わらなかった。
プロファイラで見ると、時間は規則の評価ごとの失敗の記録の保存と復元、メモ表の参照、組み合わせの関数の呼び出しに広く散っており、目立って大きな一か所はなかった。

Golem の文法の lint が Memo.hpeg より約 1 ms 長いのは、どの規則にも `:: ()` と `{ () }` を書くため、lint の情報が 325 個出るからである。

## 増分の構文解析で縮みうる時間

増分の構文解析（[ADR 0070](../adr/0070-faster-checks-in-the-language-server.md) が実装しないとしたもの）を別の ADR で検討するための材料として、編集の時間の内訳を `-A64m` の値でまとめる。

| 処理 | Golem.hpeg | 1 回の編集に占める割合 |
|---|---:|---:|
| `.hpeg` の構文解析（`parseTops`） | 12.75 ms | 約 74% |
| JSON の解読 | 4.29 ms | 約 25% |
| 静的検査、ラベル、lint | 約 2.3 ms | 約 13% |
| 1 回の編集の全体 | 17.32 ms | 100% |

割合の和が 100% を超えるのは、段ごとに別々に測った値だからである。

- 診断だけなら、増分の構文解析が縮めうるのは `.hpeg` の構文解析の約 12.7 ms である。小さな編集で解析し直す範囲が狭ければ、1 回の編集は JSON の解読と検査の約 6 ms から 7 ms に近づく
- JSON の解読は、文書の全文を毎回送る同期（`textDocumentSync` の `change: 1`）による。差分を送る同期に替えれば、通知は小さくなる。ただし言語サーバーが全文を組み立て直す処理が要る
- semantic tokens を要求するエディタでは、概要（回復する構文解析と構文木）の約 30.5 ms が編集ごとに加わる。増分の構文解析を概要にも使えれば、この時間も縮みうる。いまは診断のための構文解析と概要のための構文解析が別々で、同じ版の文書を二つの文法で 2 回解析している

## peg-runtime のほかのベンチマーク

peg-runtime の変更は、言語サーバー以外の生成したパーサーにも効く。
同じ機械で、実装の前と後の `peg-bench` を続けて実行した（既定の実行時の設定）。

| ベンチマーク | 前 | 後 |
|---|---:|---:|
| JSON、801,683 文字 | 650.4 ms | 615.5 ms |
| JSON、`%nomemo` | 409.9 ms | 359.0 ms |
| JSON、`%syntax`、型付きの値 | 1.155 s | 901.6 ms |
| JSON、`%syntax`、構文木 | 1.151 s | 924.8 ms |
| JSON、型注釈とアクションなし、構文木 | 879.3 ms | 715.3 ms |
| CommonMark の仕様書の変換 | 653.0 ms | 433.9 ms |
| Lua のテストスイートの解析 | 1.947 s | 1.367 s |
| `Json.hpeg` の解析 | 1.923 ms | 1.470 ms |
| `Json.hpeg` の生成 | 1.576 ms | 1.289 ms |

最大の常駐メモリ（`peg-bench --memory VARIANT 10000`）は、変種によって増えたものと減ったものがある。

| 変種 | 前 | 後 |
|---|---:|---:|
| JSON、型付きの値（`typed`） | 264,740,144 バイト | 156,517,032 バイト |
| JSON、`%nomemo`（`nomemo`） | 91,732,080 バイト | 120,579,376 バイト |
| JSON、`%syntax`、型付きの値（`syntax`） | 297,103,320 バイト | 352,960,480 バイト |
| JSON、`%syntax`、構文木（`syntax-tree`） | 297,102,584 バイト | 352,960,224 バイト |
| JSON、型注釈とアクションなし（`untyped-tree`） | 296,624,816 バイト | 191,893,008 バイト |
| CommonMark | 247,307,592 バイト | 135,585,824 バイト |
| Lua | 38,080,152 バイト | 36,353,960 バイト |

期待した字句の集合を合併しないまま残すと、合併の計算の分だけ、メモ表の項目が未評価の式を持つ。
一方で、合併した集合そのものは作らない。
どちらが勝つかは文法によって違うと考えられるが、`%syntax` と `%nomemo` の変種で増えた理由は確かめていない。
最大の常駐メモリは主要なガベージコレクションの時点で測るので、割り当ての量が変わって収集の時点がずれたことも、値の差に効いている可能性がある。
